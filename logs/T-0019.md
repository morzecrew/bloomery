## D-105 — widening the enum silently rewrites twenty branches that read it

```divergence
decision: unlisted — what the existing readers of `Additivity` do with the members D1 adds
grade: UNLISTED
class: discovery
at: 2026-09-05T10:05:00Z
attempt: 1
claim: twenty sites branch on `Additivity`, all of them on NON_ADDITIVE or SEMI_ADDITIVE, so three new members join every `is not Additivity.NON_ADDITIVE` as a silent catch-all that mypy cannot see; reading them shows they do not ask about additivity at all — they ask whether a metric is a stored measure or is computed at query time from components, which is `yes` for SNAPSHOT and DISTINCT_COUNT and `no` for RATIO
evidence: `grep -rn "Additivity\." src/bloomery/ | grep -v ir/nodes.py | wc -l` -> `20`
action: decided
proposal: D1 gains a sentence — closing the enum obliges the commit that closes it to leave no member silently reachable. Here that is met by §12's own staging: the three new members are defined and *not minted by resolution*, with a canary pinning exactly which members resolution can produce, so the commit that first mints one fails at that canary rather than inheriting twenty branches written for a different meaning
```

- The alternative — routing all twenty through a materializability predicate now — was rejected
  for this phase: it rewrites emitter and planner branches for members nothing can produce,
  and the rewrite would be verified by no test, since no fixture can reach it. The canary is
  the smaller thing that fails at the right moment.
- This is the third decision the RFC did not settle, after D-102 and D-103. All three were
  derivable from §4's per-class rollup rules and D1's own text rather than needing the author,
  which is why execution continued rather than stopping at the readiness gate — but three is
  the gate's threshold and the count is recorded here for the author to weigh.

## D-106 — the corpus's liveness check assumed an RFC ships all at once

```divergence

grade: UNLISTED
class: spec-gap
at: 2026-09-05T10:40:00Z
attempt: 1
claim: T-0018 built D3's stable-rule machinery as a biconditional — a case is unguarded if and only if its cited RFC is still live in rfcs/ — and that identity is false for an RFC that ships in phases; RFC 0038 D1 and D2 now refuse cases 002 and 005 while §12 stages DistinctCount and Snapshot lowering, so the RFC is correctly still live and the rule is correctly built, and the check fails on a tree where nothing is wrong
evidence: `uv run pytest tests/execution/test_semantic_corpus.py -q` -> `AssertionError: 002-average-of-averages/naive is refused and cites RFC 0038 D2, which is live`
action: decided
proposal: none for RFC 0042's text — D3 is satisfied by the rule ID being stable and machine-readable, which it is. The defect is in the check built for it, and the fix is to weaken the biconditional to the half that survives: a *retired* RFC may own no unguarded case, since retirement is the human act declaring the work complete. A live RFC implies nothing, because a phased one has shipped some of its rules and not others
```

- **What is kept.** §8's gate still fires in the direction that matters: retire RFC 0038 while
  a case still says `unguarded` on it, and the suite goes red saying the document was
  declared complete without converting a case it owns. That is the failure the number cannot
  report, and it is why the check exists at all.
- **What is dropped, and why it was never load-bearing.** The other direction asserted that a
  `refused` case cites a shipped rule. What makes a case refused is that bloomery refuses it,
  which `test_bloomery_does_what_the_case_says` asserts directly against the error class —
  so the dropped half was a proxy for something already proven, which is the same shape D-101
  removed from the `unguarded` side one branch earlier.
- The phenomenon was visible before this: RFC 0037 is ✅ Complete and deliberately still in
  `rfcs/` because its dependents argue in its vocabulary. No corpus case cited it, so the
  biconditional passed while already being false in general.

## Findings — self-audit, 2026-09-05

Scope: the whole branch, 4 commits, 16 files, +781/−75 — source, tests, fixtures, docs and
this log. Gates re-run after every fix.

### 1 — the migration note described a refusal that does not exist

`CHANGELOG.md` and the error reference both stated the snapshot rule as "a measure whose
entity key carries a date", omitting the gate D-107 added: the mart must also offer that
column as a dimension. A reader would have expected refusals that never fire and, worse,
would have read the redundant-composite-key case as a bug. Both now state the mart half and
say why it is not a technicality. **The most serious of the four**, because it is the only
one a user meets.

### 2 — a claim about the planner asserted without checking it

The comment on `_NOT_REAGGREGABLE` justified excluding `count` with "counting counts is
`sum`, which the planner already knows". Nothing in `src/bloomery/planner/` implements that,
and the reason was wrong as well as unverified: the line is not idempotence but whether *any*
rollup operator over the stored value exists — `count` rolls up under a different operator,
which is why it stays out. The list was right for a reason the comment did not give.

### 3 — a docstring the same commit made false

`Additivity`'s docstring said every site branching on the enum tests `NON_ADDITIVE` or
`SEMI_ADDITIVE`. The commit carrying that sentence added an `ADDITIVE` branch to the
additivity guard, so it was false on arrival. Restated, and the exception now names itself:
that guard raises on the fall-through instead of inheriting it.

### 4 — the scope narrowing recorded in D-108 above

### What I would still distrust

- **The snapshot rule is a heuristic wearing a proof's clothes.** "Temporal determinant in
  the key, exposed by a mart" is not the same claim as "this measure is a snapshot". A
  monthly cohort table keyed `(cohort_month, segment)` is not a snapshot and would be
  refused; the author's remedy — declaring `semi_additive` — happens to be harmless there,
  but the message would be arguing something false. The honest fix is D6's authored origin
  grain, which D-107 deliberately did not build.
- **`RESOLVABLE` is guarded by one test.** It is the only thing standing between the three
  unminted members and twenty-two sites written for a different meaning, and what enforces it

  values — a template, a future spec form — would not cross that edge.
- **Three of RFC 0038's six sections are untouched**, now stated in D-108 rather than left to

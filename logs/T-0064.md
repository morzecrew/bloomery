### What the plan decided for itself

- **A merged entity re-delivers per branch.** One INSERT per source relation, filtered by
  `_source`, because an INSERT's target cannot be data-dependent and each branch already
  reads only its own reject rows (`src/bloomery/emit/lower/silver.py:791-800`).

### The decisions this plan needs that RFC 0060 does not settle

Four, and they are not details. The spike that settled D5–D10 ran on `scd2_as_of` and hand-fed
a row into bronze — a deliberate and correct choice for measuring *the framework*, stated in
its own plan (`logs/T-0057.md:47-55`) — which means it never met bloomery's own bookkeeping
on this route. That bookkeeping is where P1 lives.

**U1 — the re-delivery's `_source_row_id`.** Bronze carries the ingestion-metadata contract
`(_ingested_at, _load_id, _source_row_id)`, with `_source_row_id` NOT NULL and **unique per
source row**, absent which compilation refuses with `IngestionMetadataMissing`; the
uniqueness is a data fact no compiler can check, so it ships as a blocking audit
(`src/bloomery/quality/catalogue.py:88-93`). The reject table's identity is the pair
`(source_relation, _source_row_id)` (`src/bloomery/quality/reject.py:4`). An INSERT back into
bronze must therefore choose:

- **the same id** — and the row collides with the uniqueness audit the caller is told to
  run, and two bronze rows answer to one reject identity;
- **a new id** — and the reject row can never be matched again, so `resolved_at` is never
  stamped, and every subsequent replay re-delivers it. That is §5.1's "a row that re-enters
  the entity on every run forever, which looks exactly like a working feature" (§9), moved
  from a staging relation into the caller's landing zone.

RFC 0060 does not mention `_source_row_id`, and both branches break something that shipped.

**U2 — what `resolved_at` means when nothing entered the entity.** Statement 2 stamps a
reject row resolved by testing that its identity is now *in the entity*
(`src/bloomery/emit/lower/silver.py:2378-2409`). On this route nothing enters the entity
during replay; the framework admits the row on a later run of its own. So either replay
stops stamping — and the reject table loses the word for "handed back, awaiting the
framework" — or the state machine RFC 0016 §5.6 and D22 describe gains a state. Neither is
in RFC 0060.

**U3 — `raw` is not the delivery.** `raw` carries the bronze columns the mapping maps or
acknowledges as unmapped, **minus every `redact:` column**
(`src/bloomery/emit/lower/silver.py:300-325`). §5.2 says the row is "written back to the
bronze relation as a new delivery", and what is available to write is a lossy projection of
one: a bronze column nothing maps is absent, and a redacted column is absent by design. The
route would insert that projection into a relation other consumers read, and on a
redacting entity it would write a row whose redacted columns are NULL and whose provenance
says it was delivered.

**U4 — the posture, which the RFC deliberately left to a person.** §9's first risk says a
statement that writes to the caller's landing zone "should be written deliberately or not at
all", and row 7 is `ASSUMED` rather than `LOCKED` for exactly this reason: the measurement
ruled out route A and separated neither survivor, so what picks §5.2 is §5's ranking, which
a reviewer may weigh differently (`logs/T-0057.md`, the rows-accepted section). U1 and U3 are
the posture question arriving as consequences rather than as a preference.

### The gate

`flag-dont-flip`'s readiness gate is three or more load-bearing unsettled decisions. There
are four, and each one decides whether §5.2's route can be built without contradicting
something already shipped. **Halted, with no code written.** Executing anyway would not
produce an implementation of RFC 0060; it would produce a second design — the one where
these four questions were answered in a lowering function by whoever reached them first.

§9's third risk is the same sentence from the other side: *a partial fix is worse than the
refusal*, because the refusal at least says the combination is unbuilt, while a landed
half-route ships a suite that says it is fixed.

```divergence

claim: the re-delivery's `_ingested_at` cannot be a bare `CURRENT_TIMESTAMP` — every shipped engine's is zone-*aware*, so the value written into bronze carries an offset, and the project's own D21 audit refuses it. Measured on dbt/DuckDB: the emitted `customer_ingestion_metadata` test failed on `2026-09-17 19:18:21.796404+03`. proposal: ASSUMED — a new port hook, `utc_now()`, spelled `CAST(timezone('UTC', CURRENT_TIMESTAMP) AS TIMESTAMP)` on DuckDB and PostgreSQL and `CAST(at_timezone(CURRENT_TIMESTAMP, 'UTC') AS TIMESTAMP)` on Trino. action: decided
```
```divergence
proposal: ASSUMED — on a type 2 entity the evidence is a version **newer than the reject row's `last_seen`**, which is the diverted delivery's own clock: the old version predates it, and anything after it arrived because the row came back — through this re-delivery, or through the source delivering it cleanly again, which resolves the reject row just as truthfully. Type 1 keeps the plain membership test unchanged: its relation holds one row per key, and its merge writes the candidate with the reject row's own `_ingested_at` rather than a fresh one, so a recency comparison there would be false of every correctly admitted row.
```

### Open, and not this phase's to close

Writing the regression test for the entry above drove the project into a state P1 makes
reachable for the first time, and the **conservation audit fails there**: a source row that
was admitted and is later quarantined is counted in both legs, because `entity_rows` is
scoped to this run's survivor identities and a type 2 relation still holds the version that
predates the run.

```
5 of 8 FAIL 1 customer_conservation ... Got 1 result, configured to fail if != 0
```

It is not caused by the fix above — it fires at the build *before* any replay runs — and it
is not the reviewer's finding. It needs its own reproduction and its own answer: the law as
written is about a relation that holds one row per key, and the honest restatement over a
retaining relation is probably "each surviving bronze row is either the **current version**
of its identity or diverted", which is a different predicate rather than a narrower one.
Recorded here rather than fixed, because a second audit rewritten inside a review round is
how a phase stops being reviewable.

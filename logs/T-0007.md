## D-031 — the report is computed wherever a `Resolution` exists, not only at `COMPLETE`

```divergence
decision: RFC 0030 D5
grade: ASSUMED
class: spec-gap
at: 2026-08-28T11:05:28Z
attempt: 1
claim: D5's headline says "a refusal empties it", but its argument is about refusals inside the resolve stage, where no Resolution exists at all; a TYPECHECK, LOWER or GUARDRAILS refusal carries one, and `_partial` already reports `reachable` and `unreachable` off it
evidence: src/bloomery/evidence.py:262-278 — `_partial`'s two non-empty branches both build reachability from `progress.resolution`
action: departed
proposal: ASSUMED — `unresolved` and `provenance` are computed wherever the pipeline produced a `Resolution`, which is every stage after `resolve` succeeded. Cases (d) and (e) still lose the worklist, which is the whole of what D5's argument establishes
```

- **Touches:** RFC 0030 D5 (`ASSUMED`), §5.2's precondition
- **RFC said:** "The report is a `COMPLETE`-stage product; a refusal empties it", graded
  `ASSUMED` because "whoever builds this may find the loop needs the partial report".
- **Built:** the report on every `SpecEvidence` whose `Resolution` exists.
- **Because:** D5's reason and D5's headline do not cover the same set. The reason is
  (d)/(e) — a malformed recipe id refuses *inside* `resolve()`, so there is no graph, no
  reachability and therefore nothing to project; that part is untouched and still costs
  the round its worklist. The headline additionally empties the report for a spec that
  resolved cleanly and was refused two stages later on a transform chain, where the open
  decisions are computed, correct, and about a part of the spec the refusal does not
  concern. Suppressing them there would make `unresolved` the one field on this type that
  is empty for a reason `stage_reached` cannot explain — the exact misreading RFC 0022 D5
  exists to prevent, and the one §9's third risk names.
- **Consequence:** the stage-first rule keeps its ordinary meaning for the new fields —
  empty means "nothing open" at `COMPLETE` and "not computed" at `RESOLVE`, with the
  stages between reporting what resolve produced. A chooser that reads `stage_reached`
  first, which every consumer must, is unaffected either way.

## D-032 — an open decision names one linking field, and it is the first in sort order

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-28T11:05:28Z
attempt: 1
claim: §5.3 asks "does any entity field carry `canonical: <name>`?" and reads the answer as one field, but nothing refuses two fields of one entity both carrying the same link — reference validation checks only that the entity matches the catalog's, so `OpenDecision.field` has two candidates and D9 requires it to name one edit
evidence: src/bloomery/resolve/refs.py:98-115 — `_check_canonical_links` refuses an unknown canonical and a wrong entity, and never compares two fields with each other
action: decided
proposal: UNLISTED, proposed `ASSUMED` — where several fields of the entity carry the link, the entry names the first by `(entity, field)` sort order. Every one of them closes the gap when mapped, so the entry is a true instance of the edit rather than a choice among unequal options
```

- **Touches:** nothing in RFC 0030; §5.3 and D9 both assume the link is unique
- **RFC said:** `UNMAPPED` is "one does, and `entity`/`field` name it".
- **Built:** the first linking field in sort order, deterministically.
- **Because:** the D9 alternative — omitting the entry, as a multi-mapping entity's is
  omitted — is wrong here for the reason D9 gives. That omission exists because a
  merged entity's columns are per mapping, so *no* single document is the edit. Here every
  candidate **is** the edit: mapping any one of the linked fields produces the
  `canonical` edge and closes the gap. Withholding an actionable entry to avoid naming one
  of several equivalent edits would be a worklist that never clears, which is the failure
  D9 is written against rather than an application of it.
- **Consequence:** a caller that maps the named field closes the decision; the other
  linked fields stay unmapped and stay legal, and nothing reports them, because nothing is
  blocked on them. If a shape ever turns up where the several links are *not* equivalent,
  this is the entry that argues against it.

## D-033 — `bloomery resolve`'s table prints the open decisions

```divergence
decision: RFC 0030 D7
grade: OPEN
class: discovery
at: 2026-08-28T11:05:28Z
attempt: 1
claim: D7 leaves the human table to whoever builds it; the table already prints `unreachable`, and an open decision is that same fact with the edit attached, so withholding it prints the problem and suppresses the answer
evidence: src/bloomery/cli/render.py:88-97 — `render_evidence` already prints one row per unreachable metric with its missing leaves
action: decided
proposal: LOCKED — the table prints one row per open decision: the canonical, its gap, the field or entity to edit, and the recipe ids the catalog offers. It never prints a recipe's `requires`, which is what `--format json` is for
```

- **Touches:** RFC 0030 D7 (`OPEN`), §7's wording rule
- **RFC said:** either "the most useful line `bloomery resolve` could print or the one that
  turns a summary into a dump".
- **Built:** the rows, with the alias slots left to JSON.
- **Because:** the dump risk is bounded by the same fact that bounds the unreachable list —
  an open decision exists only for a canonical some metric requires, so the report is at
  most as long as the missing-leaf set the table already prints. What makes it a dump is
  `requires` per option, which is a three-document join a reader cannot use from a terminal
  anyway; the ids alone are what a person types into a mapping. RFC 0020 D4's promise is
  that JSON is not a *richer* surface than the table is honest about, and it keeps them.
- **Consequence:** the column headed `options` is a list of ids in catalog order and
  the page says so in those words (§7). If a catalog ever declares enough recipes for one
  field to wrap the line, the fix is a cap with a stated count, not a re-sort.

## D-034 — a step-produced relation's decision names the catalog's entity, and the docs name the wiring

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-08-28T12:11:40Z
attempt: 1
claim: §5.3 reads the two gaps off the entity model alone, and a canonical field can also be made available by a step wiring's `canonical:` block (RFC 0017 D49) — so an `UNLINKED` entry for a step-produced relation names the entity the catalog declares, while the edit that closes it is in `steps.yaml`
evidence: `identity_resolution` with its steps.yaml `canonical: {customer: {canonical_id: customer_ref}}` removed reports `OpenDecision(canonical='customer_ref', gap=UNLINKED, entity='customer', field=None, blocks=('customer_count',))` — and `customer` is a step output, absent from `entity_model.entities` entirely
action: decided
proposal: UNLISTED, proposed `ASSUMED` — the value is left as it is and the *documentation* carries the third edit. `entity` is what §5.3 specifies for `UNLINKED` — "where such a field would go" — and it is right; what a reader needs beside it is that a relation a step produces takes its link in the wiring rather than in the entity model
```

- **Touches:** RFC 0030 §5.3 and D9; no row covers a step-produced relation
- **RFC said:** ``gap`` is decided by "does any entity field carry ``canonical: <name>``?", asked
  of the entity model. It names two edits and the corpus has three.
- **Built:** the value unchanged, and the how-to's gap→document table carrying the third.
- **Because:** the entry is not wrong — the canonical *is* open, the metric *is* blocked and
  the options *are* the catalog's. What a caller would get wrong is which document to open,
  and that mapping lives in the docs rather than in the value: adding a third `Gap` member
  would make the report claim a producer for a relation, which is a fact about the step
  registry the caller assembled and not one this projection reads. D9's omission is the
  wrong instrument too — the entry is actionable, just not where a two-edit reading assumes.
- **Consequence:** `Gap` stays a two-member enum and `UNLINKED` means "nothing carries the
  link", which is exactly what it says. If a consumer ever has to branch on *which*
  document to edit rather than print it, that is the change this entry argues against
  doing silently.
- **Found by the self-audit** (pass 2, a wrapper against every state of what it wraps):
  the report was built against mappings and never asked what a step-produced relation does.

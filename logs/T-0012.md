# T-0012 · RFC 0024 P2 — the quality system on a merged entity

Executed on branch `feat/clean-a-merged-entity`. RFC 0024 §12 P2a, P2b and P2c: quality
rules, `dedupe:` and `quarantine:` on an entity built from more than one mapping. P2c is
also the execution of [RFC 0035](../rfcs/0035-the-reject-table-on-a-merged-entity.md), which
was written for this change because RFC 0024 D16 (`LOCKED`) requires reopening RFC 0016 D10
in its own document.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into either RFC's text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

| Class | Test | Meaning |
| --- | --- | --- |
| `discovery` | Could not have been known before code existed | Healthy — the RFC was right to be silent |
| `spec-gap` | Could have been known; the RFC was silent or at the wrong altitude | The design process missed something |
| `drift` | The RFC covered it and it was built otherwise anyway, **or** a claim was made that was not true when it was made | **A defect** |
| `irreducible` | No amount of design settles it | Stop and spike |

## Requirements met without a divergence

`flag-dont-flip`'s vocabulary has no action for "the locked condition was satisfied rather
than contradicted" — the four legal actions all presuppose a conflict. The case below is
recorded as prose, which is the shape `logs/T-0004.md` used for the same problem.

**RFC 0024 D31's demand gate opened.** D31 (`LOCKED`) holds P2's *code* until "a project
needs quality rules on a merged entity". The project's own lakehouse example is that
project: its pitch is dirty bronze cleaned on the way to silver
(`examples/lakehouse/README.md:1`), and a union merge that cannot be cleaned composes with
none of it. Nothing about the gate was weakened; RFC 0024's status line names the consumer
and dates the opening, so that a reader can tell an opened gate from an ignored one.

## D-062 — what "every mapping opts in, or none does" has to compare

```divergence
decision: UNLISTED — the comparison scope RFC 0024 D33 leaves unnamed
grade: UNLISTED
class: spec-gap
at: 2026-09-03T09:20:00Z
attempt: 1
claim: agreement on the opts_in *predicate* is not enough to make lower_quality's single-Mapping call honest — two mappings can both opt in and still declare different field-level quality blocks, and mappings[0] would silently win
evidence: src/bloomery/quality/lower.py:244-253
action: decided
proposal: LOCKED — the agreement D33 requires is over the whole authored quality surface per column (rule kind, disposition, parameters and repair), not over the boolean; disagreement is refused naming both source paths
```

- **Touches:** RFC 0024 D33 (`LOCKED`) — not flipped; the row below is the scope it does
  not name
- **RFC said:** "Every mapping of an entity opts into the quality system, or none does;
  disagreement is refused", and the consequence "`lower_quality` may go on taking one
  `Mapping`".
- **Built:** the refusal compares the authored `quality:` blocks column by column across
  every mapping of the entity, and refuses any difference — which includes the
  repair-recipe case D33 names, as D33 says it should.
- **Because:** D33's consequence is the load-bearing half, and it only follows from the
  stronger reading. `opts_in` is a *disjunction* over one mapping's fields, so two mappings
  can agree that the entity joined the system and still disagree about every rule in it: A
  declares `coercible` on `amount`, B declares `in_set` on `status`, both return `True`, and
  a rule set lowered from either one is missing half of what the author wrote. Under the
  weaker reading D33's own consequence is false.
- **Why `spec-gap`:** the distinction is visible in `opts_in`'s three-line body and did not
  need code to find.

## D-064 — P2a is not separately shippable: its own generated rule needs P2c

```divergence
decision: UNLISTED — §12's phase boundary between P2a and P2c
grade: UNLISTED
class: discovery
at: 2026-09-03T10:05:00Z
attempt: 1
claim: a merged entity that joins the quality system cannot compile with P2a alone — the implicit coercible rule's disposition defaults to quarantine, and an entity with a quarantine disposition is refused without a quarantine: block, which is P2c
evidence: `uv run pytest tests/unit/test_resolve/test_build.py -q` → "entity 'event' has quarantine dispositions (event_id_coercible, kind_coercible) but no quarantine: block"
action: decided
proposal: ASSUMED — §12's three phases are an order of *work*, not three shippable states; P2a and P2b are steps inside the change that lands P2c, and the refusals lift together
```

- **Touches:** RFC 0024 §12 (P2a/P2b/P2c), RFC 0016 §5.2 (the implicit rule's default)
- **RFC said:** three phases, each with its own gate — P2a "rule lowering becomes
  mapping-invariant", then P2b `dedupe:`, then P2c `quarantine:` behind D16's document.
- **Built:** all three in one change, in that order, with the three refusals lifted together
  at the end.
- **Because:** the implicit ``coercible`` rule carries ``on_fail: quarantine`` by default
  (RFC 0016 §5.2), and a guardrail refuses any entity holding a quarantine disposition
  without a ``quarantine:`` block. So the first merged entity to declare *any* rule needs a
  reject table, and P2a's refusal-lifting is unreachable until P2c's is. Shipping P2a alone
  would have lifted a refusal onto a second refusal — a capability announced and not
  reachable, which is worse than the honest P1 message.
- **Why `discovery`:** the coupling is between RFC 0024's phase boundary and RFC 0016's
  default disposition, two documents apart, and it shows up the first time a merged entity
  is compiled with a rule on it.

# Self-audit findings — 2026-09-03

Written after the branch was complete, re-entered adversarially. These are departures the
execution above did **not** notice; filing them apart from the ones it did is what stops the
two being counted together. Scope: the whole branch against `main` — 3 commits, 158 files,
+12078/−1069, of which 12 source files and 1013 added source lines.

The sweep that found the first two was **sabotage**, not the suite: every test passed, the
goldens had been re-stamped with the wrong body, and coverage was met. Eleven of fourteen
mutations were caught; the three survivors are all below, because a surviving mutant's
*why* is the finding.

## F-1 (highest) — RFC 0024 D34 never reached SQLMesh

The metadata audit's `PARTITION BY _source, _source_row_id` was implemented in
`metadata_audit_select`, which **only the dbt emitter called**. SQLMesh built the same audit
from a Jinja template with `PARTITION BY _source_row_id` written into it, so the one target
that supports `quarantine:` at all emitted the pre-D34 body.

The failure that causes is the one D13 names as the worst available to a generated audit and
D15 predicted verbatim: `_source_row_id` is unique within *one* source relation (RFC 0016
D21), so two shops with ordinary per-table row sequences collide on the first run, the
blocking audit fires, and correct data stops the pipeline.

**Why nothing caught it.** Two copies of one body, and every test written against the
shipped one. The golden re-stamped happily. The engine test I had written for exactly this
property asserted it with a **hand-written** `GROUP BY`, which proves something about my SQL
and nothing about bloomery's. And the DuckDB seed gave the two shops distinct row
identities, so even a correct test could not have fired.

**Fixed:** the SQLMesh envelope now renders `metadata_audit_select` like the collision audit
does — one lowering, both targets. The DuckDB seed now has the two shops share a row
identity, which is the ordinary case rather than a contrived one. Both tiers run the audits
**as emitted**, and the DuckDB one was verified red against the reverted partition.

## F-2 — the rule union was unexercised

`_merged_rules` unions the lowered rules over every mapping, because a column only one
mapping produces still contributes its rules. Replacing `mappings` with `mappings[:1]`
broke nothing: the fixture's *first* branch in lexicographic order maps every column, so the
union had nothing to add there. The one decision this branch made about rule *membership*
was unpinned.

**Fixed:** a test over the two-mapping model where the second branch alone produces `note`,
asserting both that its generated rule reaches the entity and that the branch which does not
map it carries no source paths for it. Verified red.

## F-3 — seven golden files nothing emits

`multi_source` briefly carried `quarantine:` while the fixture was being split, and its
reject model, replay, quality mart and three audits stayed in the corpus afterwards.
`pytest-snapshot` never sweeps, and each golden module asserts the compile's path list
rather than the directory's contents.

**Fixed:** deleted, and `assert_no_orphans` closes it on all four golden modules — itself
tested, since a guard nobody exercises is the next seven files.

## F-4 — the retention guardrail could pass by missing

Moving `_check_retention` onto the draft introduced `next(..., None)`, which reads a lookup
miss as "this entity has no rules" — the one direction that check must never fail in. It
raises now, like its sibling two hundred lines away.

## F-5 — three prose claims outlived D29

Two comments and a docstring said a merged entity carries no quality rules. The load-bearing
one justified `_source` not being a `ColumnIR` by "no rule can read it, because no rule
exists". Rules exist now; the conclusion survives for a different reason, and that reason is
pinned by a test rather than asserted.

## F-6 (pre-existing, fixed) — the D21 metadata audit fired on correct data on Trino

Found by running the emitted audits on a real engine, which nothing in this repository had
done before. Measured on `trinodb/trino:483`:

```
TRY_CAST('2024-03-10T00:00:00' AS TIMESTAMP)  ->  NULL
TRY_CAST('2024-03-10 00:00:00' AS TIMESTAMP)  ->  2024-03-10 00:00:00
```

The audit's third clause is `_ingested_at IS NOT NULL AND TRY_CAST(_ingested_at AS
TIMESTAMP) IS NULL` (RFC 0016 D25/D31). Bronze lands as **text** (D21), so a platform
writing ISO-8601 with a `T` — the most common spelling there is — makes a **blocking** audit
stop the run on every row of correct data. That is the failure RFC 0024 D13 names as the
worst available to a generated audit, and it reaches every entity that declares `dedupe:` or
`quarantine:`, merged or not.

**Not caused by this branch:** `_uncastable_ingested_at` is byte-identical to `main`. It is
reachable here because `tests/engines/test_merged_cleaning_engines.py` is the first test to
run that audit against Trino at all.

**Fixed, and the estimate above was wrong.** "Its own change, with an RFC 0016 amendment"
assumed the fix had to invent a normalization. It did not: RFC 0027 already built one.
`parse_ts: ISO8601` wraps the text it is about to cast in `ISO_TEXT_MARKER`, every dialect
port must rewrite that marker, and Trino's spelling is `REPLACE(…, 'T', ' ')` — so
`parse_ts` had been correct on Trino for a release. The audit asks *the same question of the
same text* and simply was not marked. One marker, and the ports were already written.

Two things the fix moved that the first version broke:

- **Trino's `replace` takes varchar and nothing else.** The marked operand is text in a
  transform chain, by `parse_ts`'s declared input type — but a bronze column is whatever the
  project landed, and the lakehouse example lands `_ingested_at` typed. Unguarded, the
  emitted audit did not plan there at all: *Unexpected parameters (timestamp(6), varchar,
  varchar) for function replace*. The port now casts to varchar first, which is a no-op on
  the chain's text and makes the spelling total over what it may be handed. The example is
  what caught it.
- **Only Trino's golden moved.** DuckDB and Postgres spell `strip_iso_text` as identity, so
  the fix is invisible where the cast already worked.

Verified on `trinodb/trino:483`: 18 engine tests pass with the marker and the audit reports
3 false violations without it. The xfail is gone rather than left as a permanent skip.

## F-7 — my own harness violated the bronze contract, and only Postgres said so

Both new tiers declared bronze `_ingested_at` as `TIMESTAMP`. RFC 0016 D21 lands bronze as
text, which is *why* the audit clause above exists at all, and every other harness in the
repository declares it `VARCHAR`. DuckDB accepted the wrong type silently; Postgres refused
with `function pg_input_is_valid(timestamp without time zone, unknown) does not exist`.

A seed that contradicts the contract under test makes every assertion over it worth less
than it looks — this one would have "proved" the pipeline against data no bronze layer
produces. Fixed in both tiers.

## F-8 — RFC 0024 D28's refusal is wider than its argument, and its argument names the wrong failure

Measured, not read. The refusal was disabled on a probe fixture — two mappings targeting one
entity, **both** declaring `direct:` for the same column, so they agree about everything D28
worries about — and the result was:

```
columns: ['item_id', 'net_price', 'net_price__direct', 'net_price__direct', 'quantity']
  shop__items       [... 'net_price__direct', 'net_price__direct' ...]
  warehouse__items  [... 'net_price__direct', 'net_price__direct' ...]
audits: [('reconcile', 'net_price', …), ('reconcile', 'net_price', …)]
```

Two conclusions, and they point opposite ways.

**The refusal is necessary today.** Lifting it naively duplicates the shadow column on the
entity *and on every branch*, emits the reconcile audit twice, and gives each branch the
other's extraction — `shop__items` projecting `$.unit_price`, which its bronze relation does
not have. So D28's conclusion holds even where its premise does not.

**But D28 names the wrong failure, and its refusal is wider than its argument.** D28 argues
from *disagreement*: "a merged entity can have a direct path on one source and none on
another … a NULL shadow is indistinguishable from a genuinely NULL direct value". That is a
real second-order problem and it is not the one that bites first. What bites first is that
`Derivation` is built per mapping (`guardrails/operands.py`) and carries no source, while
`_shadow` returns exactly one `SourceColumnIR` — the same per-mapping-fact-on-a-shared-node
shape D26 split for `expr` and D32 split for the rule inputs.

**It is therefore reducible, by machinery this branch already built:**

1. `Derivation` carries its mapping's source relation;
2. `path_conflict_amendments` groups by `(entity, field)` and builds one `ColumnIR` with one
   `SourceColumnIR` **per source**, exactly as `_column_pair` does;
3. disagreement — one mapping declaring `direct:` where another does not — is refused by
   D33's pattern rather than tolerated, which is what makes a NULL shadow mean "genuinely
   NULL" again.

**Not built here, and this is a `LOCKED` row.** D28 says P2 "chooses between one shadow
projection per source with a null-safe audit, and a coverage rule in D4's shape … this RFC
does not pick, because the choice is about what a reconcile check *means* across sources and
that deserves the argument". The measurement above says option 2 composes and option 1's
"null-safe audit" is unnecessary under it; it does not say the author has made that choice.
Halting rather than flipping.

**Proposed row (RFC 0024, for the author):** `ASSUMED` — `direct:` is allowed on a merged
entity when **every** mapping records one for the column, refused when they disagree; the
shadow is built per source like every other lowering (D26), and the reconcile audit is
unchanged because under agreement no branch's shadow is NULL for want of a path.

**Accepted by the author 2026-09-03 as RFC 0024 D36**, with §12 gaining a P2d that
deliberately does *not* fold it into this change. D28's row stands unamended, as the corpus
requires: its refusal is correct until D36 is executed, and the code still enforces it.

## F-9 — an offset-bearing ISO timestamp is silently truncated on Trino (open)

Raised in review, measured on `trinodb/trino:483`, and **not fixed** because the obvious fix
is worse and the honest one is a contract question.

What the current normalizer does, measured:

```
'2026-01-06T12:00:00'        -> 2026-01-06 12:00:00     ok
'2026-01-06t12:00:00'        -> NULL                    fixed on this branch
'2026-01-06 12:00:00'        -> 2026-01-06 12:00:00     ok
'2026-01-06T12:00:00Z'       -> 2026-01-06 12:00:00     ok — `Z` *is* UTC
'2026-01-06T12:00:00+01:00'  -> 2026-01-06 12:00:00     WRONG: the instant is 11:00Z
```

The offset case is the project's worst class: it parses, and the number is plausible and
wrong. The reviewer proposed parsing with Trino's ISO parser and normalizing to UTC.
Measured under a session zone of `Pacific/Kiritimati`:

```
COALESCE(TRY(CAST(AT_TIMEZONE(FROM_ISO8601_TIMESTAMP(x), 'UTC') AS TIMESTAMP)), …)
'2026-01-06T12:00:00'        -> 2026-01-05 22:00:00
```

`FROM_ISO8601_TIMESTAMP` attaches the **session zone** to a zoneless string, so that fix
reintroduces exactly the reader-dependence RFC 0028 removed — for the common case, in order
to repair the rare one.

**The real question is a contract question, and it is not this branch's to answer.**
`parse_ts` parses a *local wall clock* and `to_utc` is the only door into UTC (RFC 0028,
RFC 0029). Under that contract an offset-bearing input is out of contract: the spec says the
text is a local clock and the data says otherwise. Truncating it silently is wrong, but so is
converting it — that would make `parse_ts` mean two different things depending on the bytes.
The candidates are to refuse offset-bearing text at run time (a generated audit, like D21's)
or to give the spec a way to say the source stamps an instant. Both are RFC 0028/0029
amendments.

Only the lowercase `t` is fixed here: no semantics, ISO permits it, the other two ports
already accept it, and Trino returned NULL.

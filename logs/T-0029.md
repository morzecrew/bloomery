## Self-audit findings — 2026-09-09

Scope: the whole branch against `origin/main` at `0673a1d` — two source files, four corpus
cases, one shared test builder, two RFC status lines and the changelog. Sabotage sweep is
`scratchpad/sweep29.py`: nine mutations, **9 caught, 0 survived**, which measures the
mutations I thought of and is why the passes below ran anyway.

### 1. A proof took the caller's word for where a measure lives

`prove_additive_rollup` takes the grain to sum *from* as an argument and never checked it
against the measure's own. So a measure declared at the order and asked about from the line
proved:

```
AdditiveRollup(measure=revenue, from={order_item.line_id, order_item.order_id}, to={order.order_id})
```

Both existing obligations passed honestly — the route from line to order is a declared
`many_to_one`, and the measure is declared additive — and the conclusion was false. It is
case 001's fan-out with a proof attached: a measure copied onto a finer grain and summed
once per copy.

The sweep could not have found it. Every mutation I wrote broke a check that existed; this
was a check that did not, and nothing about the module's shape suggested it was missing.
What found it was pass 2's question — what does this wrapper trust about the state it wraps
— asked of the arguments rather than of the code.

Fixed: the source grain's entity must be the measure's declared grain, refused as
`not_the_origin_grain` with the origin named. One existing test had to move to a different
measure, and the move is itself the point — it was asserting a *refinement* refusal using a
measure that does not originate at the grain it asked from, so it had been passing through
the hole.

### 2. The silence check reports a clean run before the first commit

`log_check.py --base origin/main` diffs commits. On a branch with none it compares nothing,
finds no touched area, and prints `0 problem(s), 0 skipped` — which reads exactly like a
task whose every `LOCKED` area is accounted for.

I ran it four times during this task and believed it each time. Committing turned the same
command into six `Q1` problems: `RFC 0039 D1`, `D2`, `D6` and `RFC 0042 D1`, `D2`, `D3`, all
governing areas this branch edits, none with an entry.

T-0027's lesson was "write the task file before the work". That is necessary and not
sufficient: the check needs a task file *and* a commit, and before the second it is a
green light for the wrong reason. The close-outs above are what it asked for once it could
see anything.

### 3. A task file written first cannot name a file the work creates

`src/bloomery/semantic/additivity.py` did not exist when `tasks/T-0029.json` was written, so
no decision declares it and nothing in this branch's silence check governs the module the
branch is *about*. `RFC 0039 D3`'s paths name `semantic/closure.py` and
`guardrails/additivity.py`, and the new obligation went beside them rather than into either.

Not fixed by editing the task file, which would make "written before the work" a claim about
a document that was not. Recorded instead, because the blind spot is structural: a check
keyed to declared paths cannot see a path the declaration could not have known. What would
close it is a rule that a *new* source file under a spec's area owes an entry naming which
decision governs it — a gate, not a habit.

### Noted, not a defect

**RFC 0042 cannot retire even though §3's set is complete.** Two of the four new cases are
`unguarded` and cite `RFC 0042 D5`, and `test_a_retired_rfc_owns_no_unguarded_case` refuses
a retired RFC in that position. The document is held open by a gate it wrote for itself,
which is the gate working: an unguarded case names a decision that is still someone's to
answer, and a retired document cannot be answering anything. The status line says so.

**Drift count: 0.** (Findings 1–3 are defects and gaps in what this branch built and in how
it checked itself, not departures from what RFC 0039 or RFC 0042 decided.)

## Review findings — 2026-09-09

The PR review round on #92. Two defects fixed, five claims refused; the refusals are
recorded because a refused claim that leaves no trace gets re-litigated by the next
reviewer that reads the same lines.

### 4. A rewrap that was not one (fixed, `fd80a36`)

The status paragraph's new sentence was appended to the existing continuation instead of
ending its line, leaving line 12 of `rfcs/0042-semantic-bug-corpus.md` at 130 characters
against the file's ~90. Every other line of the edit wrapped; this one did not, because it
grew from a line already there rather than being written fresh.

### 5. A case named for something it is not (fixed, `d82430a`)

`009-null-denominator` carries RFC 0042 §3's name and a denominator of `0`, and nothing in
the case said why. The name is not the defect — §3 wrote it, the status line's claim that
the *names* did not drift depends on it, and renaming the directory would falsify that. The
defect was the silence: a reader meets "null" in the title and "0" in the rows with nothing
between them.

Verified rather than assumed: both spellings return the same 4.00 —
`SELECT SUM(c)/SUM(p) FROM (VALUES (90.00,30),(30.00,10),(40.00,NULL))` gives `4.0` in
DuckDB, because `SUM` skips the null. So the choice is about what the case *reads* as, not
about the number, which is what the new bullet now says.

### Refused, with the evidence

**A ratio metric whose `additivity` is not `RATIO`** (two reviewers, independently). True as
stated and unreachable: `guardrails/metrics.py:288-319` refuses `ratio:` under any other
word, verified by running `_check_shape` on all three spellings — `additive` and
`non_additive` raise `InvalidMetricShape`, `ratio` passes. The arm is skipped only for a
`derived:` metric, which line 257 already refuses beside `ratio:`. And R012's conclusion
does not read `metric.additivity`: the reconstruction is sound exactly when each operand
rolls up, which `prove_additive_rollup` checks. A guard there would check a field the claim
does not rest on — the shape this branch's finding 1 was about, in the other direction.

**RFC 0039's status line overstates the corpus evidence.** Claimed: only 008 evidences R012,
R011 converts nothing, 009/010/011 are unrelated. All four `expected/semantic_outcome.json`
name a rule in an accepted arm — 008 and 009 `R012`, 010 and 011 `R011` — and 010 has no
`unguarded` arm at all.

**RFC 0042's §§3, 9 and 11 disagree with the corpus** (three reviewers, one finding). They
do, deliberately. Line 13 of the document says so: *nothing below has been amended to agree
with what was built*. The drift is recorded in the status line, which is where current state
lives; retrofitting §3's case list or §11's "remaining five" is the edit `rfc-writer`
forbids, and it would destroy the only evidence that the numbering moved.

**010's "no `one_to_many` edge anywhere in the query" is factually wrong.** It is a
statement about declared cardinality, and both relationships are declared `many_to_one`; the
paragraph immediately after it says the path traverses the first edge backwards, which is

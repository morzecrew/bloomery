## The timezone case runs in the execution tier, and T-0018 asked to be told

```divergence
decision: RFC 0042 D7
grade: OPEN
class: discovery
at: 2026-09-08T21:08:00Z
attempt: 1
claim: D7 guessed that cases 003 and 010 might need the Docker-gated engine tier, and T-0018 answered it for 003 while explicitly deferring 010 to whoever built it. A timezone-boundary case needs a named-zone conversion and a truncation, and DuckDB has both, so nothing about the case requires an engine the default suite cannot start
evidence: `uv run python -c "import duckdb; c=duckdb.connect(); c.execute(\"SET TimeZone='UTC'\"); print(c.sql(\"SELECT DATE_TRUNC('day', TIMESTAMPTZ '2026-03-01 02:30:00+00' AT TIME ZONE 'America/New_York')\").fetchall())"` -> `[(datetime.datetime(2026, 2, 28, 0, 0),)]` — the previous local day for a UTC instant past midnight. The session zone has to be pinned: without `SET TimeZone`, the same statement answers in whatever zone the machine is in, which is the bug this case is about arriving in its own evidence
action: decided
proposal: D7 is answered for 011 as it was for 003 — execution (DuckDB), in the default suite, with the tier recorded in that case's `problem.md`. A corpus that does not run by default is a corpus that rots, and no case in §3's set now sits outside it. What the engine tier is still owed is the *dialect* question — whether the same conversion renders and returns the same instant on PostgreSQL and Trino — and that is RFC 0043's matrix rather than this corpus's job
```

## Additivity has never been a premise, and the rollup proof is where it attaches

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-08T21:16:00Z
attempt: 1
claim: `prove_rollup` proves the grain half only — R006 over R001-R005, with R007 as the axiom — and nothing in the semantic package reads additivity at all. So "additive rollup", which §3 lists as one of the seven rules, is not a refinement of an existing proof but a second obligation that has never had a premise in this package; the fact it needs lives on `MetricIR.additivity`, which RFC 0038 closed at six members
evidence: `grep -rn "Additivity" src/bloomery/semantic/ | wc -l` -> 0
action: decided
proposal: the additive obligation composes *with* `prove_rollup` rather than inside it: the grain proof answers "may values travel from this grain to that one", the additivity proof answers "may this measure be summed once they arrive", and a single rule conflating them could not refuse the second while granting the first — which is precisely case 002's shape. `can_roll_up` stays the decision about grain (RFC 0039 D3, `LOCKED`), and the new rule cites its proof as a premise rather than re-deriving it
```

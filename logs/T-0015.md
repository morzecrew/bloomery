## D-075 — what a project with no statable start gets

```divergence
decision: RFC 0054 D5
grade: OPEN
class: discovery
at: 2026-09-04T14:40:00Z
attempt: 1
claim: §5.3 offers three answers for a project that backfills by time and declares no date dimension — a config with the key commented, no config at all, or a refusal — and ranks none
evidence: src/bloomery/emit/sqlmesh/__init__.py:849
action: decided
proposal: no `config.yaml` at all for that project, which is today's behaviour exactly; the emitter returns `None` and the artifact is absent rather than incomplete
```

- **Touches:** RFC 0054 D5 (`OPEN`) — answered, not departed from.
- **Decided:** `_config_artifact` returns `None` when the start cannot be stated *and*
  something reads it. Two of the three cases still get a file: a project with a date
  dimension gets `dialect` and `start`, and a project that backfills by time nowhere gets
  `dialect` alone, because nothing there reads a start.
- **Because:** the RFC's own goal sentence decides it — "the emitted config states every
  value it contains and contains no value bloomery cannot state". A file whose missing
  start makes `sqlmesh plan` succeed over a single day is the M4 failure re-created one
  level up: it *runs*, which is worse than a directory that does not. The commented-key
  option was rejected for exactly that reason rather than for being untidy — a comment is
  read once and the plan is run every day. A refusal was rejected as disproportionate: it
  would refuse a project that compiles today over a file that did not exist yesterday.
- **Consequence:** the artifact set is a function of the catalog for the first time, which
  is stated in the emitter's docstring because "sometimes there is a config" is otherwise
  a surprise a reader meets in a diff.

## D-076 — the emitted config competes with the caller's gateway

```divergence
decision: UNLISTED — where a caller's SQLMesh gateway lives once bloomery emits config.yaml
grade: UNLISTED
class: discovery
at: 2026-09-04T15:05:00Z
attempt: 1
claim: dbt keeps project settings and credentials in two files and SQLMesh keeps them in one, so this artifact overwrites the caller's connection on every compile — a way `dbt_project.yml` never could, and §9 named the collision without noticing that it makes the emitted file's own advice wrong
evidence: tests/e2e/test_sqlmesh_replan.py:429
action: decided
proposal: the emitted header points at `SQLMESH__GATEWAYS__…` in the environment as the way to supply a connection, and says plainly that a gateway edited into the file is gone at the next compile
```

- **Touches:** nothing stated — RFC 0054 §9 names the collision as an ergonomic surprise
  ("an artifact appeared where I was writing my own") and stops there.
- **Found by:** this repository's own `test_sqlmesh_replan.py`, which wrote its gateway
  config and *then* the artifacts. Three fixtures went from passing on `main` to
  `ConfigError: No connection configured.` — the first caller to lose its gateway to this
  feature was in the tree, one commit after it landed.
- **Decided:** the artifact's guidance changes, not the artifact's existence. The header
  had offered two ways to supply a gateway — a `gateways:` block "below", or the
  environment — and the first is advice that works exactly once. It now names the
  environment and says why the file cannot hold one.
- **Because:** the alternative readings are worse. Not emitting the file returns the
  target to having no project at all; emitting it under another name is not open, since
  SQLMesh reads `config.yaml` or `config.py` and nothing else; and leaving the header's
  first suggestion in place would have every caller discover the overwrite by losing a
  connection rather than by reading a sentence.
- **Why `discovery`:** §9 reasoned about the collision from the artifact's side ("a file
  appeared") and never from the caller's ("and it holds the thing I need to run"). Nothing
  short of running the repository's own SQLMesh tier would have shown the difference.
- **Consequence:** `_write_project` in that test now writes the gateway *after* the
  artifacts, which is the overlay a caller has to perform, and its docstring says so
  rather than leaving the order looking incidental.

## D-077 — the predicate and its own docstring disagreed about what reads the start

```divergence
decision: RFC 0054 D5
grade: OPEN
class: drift
at: 2026-09-04T16:20:00Z
attempt: 2
claim: `_backfills_by_time` is documented as "whether any emitted model is INCREMENTAL_BY_TIME_RANGE" and did not ask that — it read `entity.materialization`, which `scd: type2` supersedes, so a partitioned SCD2 entity suppressed the project's config.yaml over a start its emitted kind never reads
evidence: src/bloomery/emit/sqlmesh/__init__.py:347
action: decided
proposal: ask `_kind_clause` — the function that decides the emitted kind — rather than restating its precedence rule in a second place
```

- **Touches:** RFC 0054 D5, whose answer (D-075) withholds the file only where the start
  is *read*. The predicate decided a wider set than that sentence describes.
- **Measured, not reasoned:** a SQLMesh project holding one `SCD_TYPE_2_BY_COLUMN` model
  and no `model_defaults.start` plans `[2026-09-03 - 2026-09-03]` — the same one-day
  window M4 punished — and lands **every** row, `valid_from` at `1970-01-01`. The window
  is bookkeeping there; nothing filters on it, because a snapshot kind has no time column
  to filter by. That is the difference M4 turns on, and it cannot be read off the plan
  output, which looks identical in both cases.
- **Decided:** `any(_kind_clause(entity).startswith("INCREMENTAL_BY_TIME_RANGE") …)`. The
  obvious repair — adding `entity.scd is not SCDKind.TYPE2` to the predicate — was
  refused: it copies `_kind_clause`'s precedence rule into a second place, and the two
  drift the first time a third kind supersedes a materialization. Marts carry no `scd`,
  so their materialization *is* their kind and they are left alone.
- **Why `drift`:** the docstring stated the right quantifier when it was written and the
  body never implemented it. A claim that was not true when it was made is a defect, not
  a discovery, regardless of the direction the code was wrong in.
- **Consequence:** the failure this removes is a refusal, not a wrong number — the project
  lost its `config.yaml` and would not load. The conservative direction, which is why it
  survived a suite that pins the wrong-number direction twice.

## D-078 — a year is an ISO field, and two artifacts were writing it as an int

```divergence
decision: UNLISTED — how `start_year` is rendered into an ISO date
grade: UNLISTED
class: spec-gap
at: 2026-09-04T16:35:00Z
attempt: 1
claim: `start_year` is `ge=1` and both the config's `start` and the date spine's GENERATE_SERIES interpolated it unpadded, so a legal catalog emits `start: '1-01-01'` — which SQLMesh does not reject, it reads as 2001-01-01
evidence: src/bloomery/spec/catalog.py:92
action: decided
proposal: `:04d` at both sites; the spine's was there before this RFC and is the same defect
```

- **Touches:** nothing stated. D2 settles *that* the start is emitted and *where* it comes
  from, never how a year becomes an ISO field — but a window silently starting two
  millennia late is the failure D2 exists to prevent, reached by a route the row does not
  cover.
- **Measured:** `to_datetime('1-01-01')` returns `2001-01-01`; `to_datetime('999-01-01')`
  raises. So the range `1..999` splits into a hard error and, worse, a **silent
  reinterpretation** — the plausible-but-wrong answer this project treats as its highest
  severity class, produced by a file bloomery wrote.
- **The spine had it too.** `CAST('1-01-01' AS DATE)` parses as year 1 on DuckDB and means
  whatever the engine's date style guesses elsewhere, so the two artifacts of one compile
  could disagree about the same year — the config reading 2001 while the dimension it
  describes starts at 1. Fixed in the same change rather than left: it is one field
  rendered into one format, and repairing the copy in front of me while the other kept the
  defect is how a fix lands in the emitter nobody was looking at.
- **Why `spec-gap`:** `ge=1` is stated in the spec and readable; the RFC wrote
  `f"{date_dimension.start_year}-01-01"` in §5.1 without asking what the field's own range
  allows. Nothing about running the code was needed to know it.

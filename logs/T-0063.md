# T-0063 · A ratio over one row set (RFC 0075)

Executing RFC 0075 against branch `feat/ratio-row-set`. §12 offers two commits and says one
is better than either if the work fits, because the two-commit order blocks any project
needing the inclusive reading in between. It fits.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here has
been folded back into the RFC's own text. The rows proposed below are put forward for the

## What the sweep found, and the discharge it forced

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-17T15:40:00Z
attempt: 1
claim: §5.1's three discharges refuse every ratio in this repository — eight projects, including corpus cases 002 and 008 that §6 says are untouched — because none of them restricts an operand and none declares a range rule; but five of the eight are counts, where the premise is true by construction and no declaration could add anything
evidence: `uv run python scratchpad/sweep75.py` — UndeclaredRatioRows on cross_mart_branches, ecom_basic, non_additive_aov, corpus 002/decomposed, 008/declared, 009/declared, examples lakehouse and targets
action: decided
proposal: LOCKED — a fourth discharge: the denominator **counts** a column that cannot be NULL (`agg: count` over a field the entity declares `required`, or one a `not_null` rule removes the row for). A count counts the very rows the numerator sums, so a row contributing to the numerator contributes 1 — the premise holds by construction and there is nothing for an author to declare. Without it the rule refuses `revenue / order_count`, which is the most common correct ratio there is, and §9's claim that a well-declared project is not inconvenienced is false for every project in this tree. `count_distinct` is deliberately *not* included: no fixture exercises one and the argument differs, so it stays refused rather than waved through.
```

## A correction to the count discharge

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-17T15:55:00Z
attempt: 2
claim: excluding `count_distinct` from the count discharge was wrong, and the refusal it produces is nonsense on its face — "nothing restricts line_discount and shipping_count to rows with a non-zero 'customer_id'" about a *string* column, with a fix that tells the author to filter `customer_id > 0`
evidence: `uv run pytest tests/unit/test_planner/test_metricflow_planner.py::test_a_distinct_count_is_planned_on_one_mart_and_explained_as_one -q` — refused with `UndeclaredRatioRows` naming `customer_id`, which `entity_model.yaml` declares `{type: string, required: true}`
action: decided
proposal: LOCKED — `count` and `count_distinct` over a column that cannot be null both discharge. The earlier entry excluded the second on the grounds that "a distinct count is about the group rather than the row", which is true and is not the premise: what R019 refuses is a denominator whose *per-row contribution* can be zero while the numerator's is not, and that is a property of a **sum over a numeric column**. A count of either kind is at least one for any non-empty row set, and "discount per distinct customer" is a metric with no zero-denominator row to declare anything about. Admitting it on the evidence of the message it produced, rather than on the resemblance the first entry refused.
```

## Leg 2 compares dimensions, and two marts spell one dimension twice

```divergence

grade: UNLISTED
class: spec-gap
at: 2026-09-17T16:05:00Z

claim: comparing the operands' restrictions by the dimension *name* refuses a correct cross-mart ratio — the flattener prefixes a joined column, so the order-items mart calls the order's region `order_region` while the orders mart calls it `region`, and a ratio restricted to EU on both operands cannot be written with one spelling
evidence: `uv run pytest tests/unit/test_planner/test_coverage.py::test_a_component_carrying_its_own_restriction_declines_the_composed_path -q` — filtering both operands on `order_region` is refused with "mart 'orders' does not flatten [it] as a categorical dimension; known: [... 'region']"
action: decided
proposal: ASSUMED — leg 2 compares restrictions by the **entity column** each dimension resolves to, through the marts that carry the operand, and falls back to the authored name where no mart carries it. §5.2 says identity is over the canonical restriction; a mart's dimension name is not canonical, because prefixing is what makes a joined column addressable. Without this the leg refuses exactly the ratios that span two marts, which are the ones whose operands are most likely to be restricted at all.
```

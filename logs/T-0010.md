# T-0010 · RFC 0023 §5.4 — currency as a declared relation

Executed on branch `feat/currency-conversion`. RFC 0023's last unlanded half: the FX
rate relation, the grammar change `convert` could not avoid, and the lowering that turns
both into an as-of rate lookup. With §5.3 already landed this completes the RFC, which
is retired in the same change.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the RFC's own text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

| Class | Test | Meaning |
| --- | --- | --- |
| `discovery` | Could not have been known before code existed | Healthy — the RFC was right to be silent |
| `spec-gap` | Could have been known; the RFC was silent or at the wrong altitude | The design process missed something |
| `drift` | The RFC covered it and it was built otherwise anyway, **or** a claim was made that was not true when it was made | **A defect** |
| `irreducible` | No amount of design settles it | Stop and spike |

## D-044 — `convert` names both currencies and an anchor, positionally

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T12:10:00Z
attempt: 1
claim: §5.4 says only that "whatever the final spelling, the transform must name its anchor"; it leaves the rest of the signature open
evidence: src/bloomery/transforms/_builtins.py:779
action: decided
proposal: The `convert` signature is `{convert: [<from>, <to>, <anchor>]}` — source currency, target currency, and the name of a date or timestamp field of the same entity.
```

§5.4 requires the anchor and says nothing about the source currency, which the
implementation needs and cannot get anywhere else. The amount arrives from a bronze
JSON path, which carries no currency; the *destination* field's canonical declaration
carries one, but reading `from` out of it would mean the source currency is whatever the
target is declared as, which is backwards. RFC 0021 closes inference, so it is declared.

Positional rather than a mapping (`{convert: {from: EUR, to: USD, as_of: paid_at}}`)
because the transform grammar has one shape for arguments and adding a second for one
transform would be a spec-surface change larger than the feature.

## D-045 — the anchor is re-lowered, not referenced by name

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T12:25:00Z
attempt: 1
claim: §5.4 describes the anchor as something the transform "names", without saying what a name resolves to at lowering time
evidence: src/bloomery/resolve/build.py:1644
action: decided
proposal: A `convert` anchor names a sibling field of the same mapping, and lowers to that field's own expression rather than to a reference to the column it will be projected as.
```

Could not have been known from the design: it is a fact about where the conversion sits
in the emitted SELECT. The converted column and its anchor are two projections of one
branch SELECT, so the anchor's silver name does not exist yet at the point the
conversion is built. Referring to it by name would resolve against **bronze**, where
there is a JSON payload and no `paid_at`. DuckDB would accept a lateral column alias;
Postgres and Trino reject it, so the portable form is to lower the chain twice.

Consequence, stated as a refusal rather than left implicit: the anchor must be a direct
`from:` field. A recipe or macro anchor would splice its whole derivation into every
converted column, and that is a cost worth naming before paying.

## D-046 — a correlated scalar subquery, not a join

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T12:40:00Z
attempt: 1
claim: §5.4 says "conversion is the as-of join again with a different right-hand side", which reads as a join
evidence: src/bloomery/emit/lower/silver.py:373
action: decided
proposal: A conversion lowers to a correlated scalar subquery over the rate relation, not to a join in the silver SELECT's FROM clause.
```

The *predicate* is the as-of join's, exactly, and is now literally one function shared
with it (D6's "one construct" made mechanical). What differs is the shape it sits in.

`convert` is a transform, and a transform is a scalar expression inside one projection.
Putting the rate relation in the FROM clause would mean teaching four other shapes about
it: the union across sources, the dedupe QUALIFY, the reject table, and replay. A scalar
expression needs none of them to change — and replay in particular keeps working
*because* it re-runs this same expression against the reject payload (RFC 0016 §5.6).

## D-047 — the rate relation is a bare name, resolved through the naming policy

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T12:50:00Z
attempt: 1
claim: §5.4's YAML shows `relation: silver.fx_rate` — a namespaced name written into the catalog, but no decision row settles the spelling
evidence: src/bloomery/emit/lower/silver.py:404
action: decided
proposal: `fx_rates.relation` is a bare relation name, resolved at emit through the naming policy at the silver layer, exactly as a mart's join target is.
```

A departure from the RFC's illustrative YAML, and the only one here. A hard-coded
`silver.fx_rate` would pass `PrefixNaming` unchanged, so a project whose every other
relation was scoped into its own namespace would read this one from outside it — which
is the single thing a naming policy exists to prevent (RFC 0008 §5.1). Pinned by a test
that compiles the fixture under `PrefixNaming` and asserts the unprefixed form is
absent.

## D-048 — a rate miss is NULL, not `unknown_member`

```divergence
decision: RFC 0023 D11
grade: LOCKED
class: spec-gap
at: 2026-09-02T13:00:00Z
attempt: 1
claim: D11 says a gap in the rate table is "a *miss*, taking D9's `unknown_member` disposition, rather than silently resolving to a neighbour"
evidence: tests/execution/test_currency_convert.py:118
action: halted
proposal: D11's substance — a gap is a miss, never a neighbouring rate — is implemented. Its mechanism reference is not applicable and is proposed for amendment: `unknown_member` rewrites a foreign key to a reserved string member and cannot apply to a decimal amount.
```

The locked part of D11 is honoured exactly: both interval ends are required and a gap
resolves to nothing rather than to an adjacent rate. What could not be done is the
mechanism the same row cites. `unknown_member` (RFC 0016) is a *referential rule*
disposition that rewrites an unmatched foreign key to a reserved string member; the
result of a conversion is `decimal(12,4)`, and there is no string to rewrite it to.

So the miss is NULL, which propagates and stays visible — a converted total simply
excludes it. This is the same reasoning that produced D-039 on the §5.3 side, where a
join miss was left as a `LEFT JOIN` miss rather than reusing the same disposition. Graded
`halted` rather than `departed` because the behaviour D11 locks is what shipped; it is
the citation that needs amending, and this execution does not amend it.

## D-049 — the refusal survives, narrowed to "no rates declared"

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T13:15:00Z
attempt: 1
claim: D4 locks the refusal for the state where no rate relation exists and names a dialect capability as what clears it; what clears it once §5.4 ships is settled by no row
evidence: src/bloomery/emit/lower/silver.py:459
action: decided
proposal: The emit refusal stays where D4 put it and keeps its class; what changes is its condition and its message. It fires when the catalog declares no `fx_rates:`, and names that declaration as the fix.
```

D4 anticipated the refusal being cleared by a *dialect* declaring a capability. What
actually clears it is a *catalog* declaring rates, which is better placed: D14 already
recorded that a dialect flag would have been claimed by default by all three shipped
dialects and encode the opposite of the fact. Nothing about conversion was ever a
dialect's problem — the predicate is `>=`, `<`, `IS NULL` and `OR` — and the missing
piece was always the rate data, which is exactly what the catalog now supplies.

## D-050 — `CurrencyMismatch` gains no escape, only a better message

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T13:25:00Z
attempt: 1
claim: D5 removed `_CONVERT_MARKER` and made `CurrencyMismatch` unconditional "until §5.4 ships", which settles the state before shipping and not the state after
evidence: src/bloomery/guardrails/arithmetic.py:159
action: decided
proposal: Shipping §5.4 does not restore the marker. A converted amount satisfies the currency rule by being declared in the target currency, not by carrying a token that waives the rule.
```

"Until §5.4 ships" invited reading the marker back in once conversion existed. It should
not be, and the reason is the one that removed it: a token that waives a guardrail is a
compile-time "yes" that asserts nothing about the value. What conversion provides is not
an escape but an *answer* — the converted amount is written into a field the catalog
declares in the target currency, and two operands in one currency were never a
violation. The rule stayed unconditional; only the advice moved, because telling an
author to derive upstream when a rate relation is right there sends them to rebuild what
the compiler would do for them.

Added with it, because the same reasoning makes it reachable: converting into a field
whose canonical declares a *different* currency is refused. Without that check the
guardrail would reason about the column in a currency it is not in, which is precisely
how a wrong number passes every check.

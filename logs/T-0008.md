## D-035 — the identity is bound in `validate_document`, not in `load_project`

```divergence
decision: RFC 0032 D3
grade: LOCKED
class: spec-gap
at: 2026-08-30T19:42:00Z
attempt: 1
claim: §5.1 says "load_project sets it at construction"; binding it there leaves every caller that reaches validate_document directly with a Mapping it cannot construct, which is 101 failing tests and a public function that cannot be called with its own model
action: decided
```

D3 is `LOCKED` and this does not depart from it — D3 says *the loader* sets the field and
that an authored value is refused, and both remain true. What moves is **where in the
loading path**, which §5.1 stated in prose and no decision graded.

Binding it in `load_project` failed immediately and widely: `validate_document(Mapping, …)`
is the shape-checking entry point, it is public, and the corpus calls it directly in
several test modules. A `Mapping` whose required field only one caller can supply is a
model that cannot be validated except through one door.

`validate_document` is the better place on its own merits, not merely the convenient one:
**it already takes `document`**, because that name prefixes every refusal raised from the
document (RFC 0002 §5.3). Binding the identity from the same argument is what stops the
coordinate a report sends a reader to and the coordinate a refusal names from being two
different values that can disagree. The refusal of an authored `document:` moves with it.

Effect on the count: 101 failures → 7.

**Proposed row.** `| 8 | ASSUMED | The identity is bound in validate_document, which already
receives the document name as the prefix for this document's refusals (RFC 0002 §5.3) —
not in load_project, which would leave a required field only one caller could supply.
Consequence: every path that parses a mapping gets an identity, including a caller that
reaches the shape check directly. Added by execution 2026-08-30 — see logs/T-0008.md
(D-035, attempt 1). |`

## D-036 — the exported schema would have demanded the key the loader refuses

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-30T20:10:00Z
attempt: 1
claim: adding a required field to Mapping puts it in the JSON Schema `bloomery schema` exports, whose audience is a spec author — so the schema would mark `document` required while the loader refuses an authored one
action: decided
```

The RFC's scope line claims "no golden moves". `tests/golden/test_spec_schemas.py[mapping]`
moved, and it was **not a stamp to update**: the exported schema listed `document` in both
`properties` and `required`. That schema exists for an editor to validate a spec against
(RFC 0020), so it would have demanded the one key D3 refuses — the exported contract
contradicting the compiler, on the surface whose whole job is to agree with it.

Decided: `document: SkipJsonSchema[str]`. The schema describes the **authored vocabulary**,
and D3 already says this field is not part of it; the annotation makes that true on the
exported surface rather than only in prose. The golden then does not move, and the RFC's
scope line becomes true rather than nearly true.

This is `spec-gap` rather than `discovery`: RFC 0020's schema export is a documented public
surface and §3 could have named it. It did not, and §6's test list had no case for it.

**Proposed row.** `| 9 | LOCKED | document is SkipJsonSchema — absent from the schema
bloomery schema exports. That schema's audience is a spec author and D3 says this field is
not theirs to write; a required document there would have an editor demand the one key the
loader refuses. Consequence: the model and the exported schema deliberately disagree about
one field, which test_document_is_in_the_model_and_not_the_schema records where the other
measured divergences live. Added by execution 2026-08-30 — see logs/T-0008.md (D-036,
attempt 1). |`

## D-037 — `FieldProvenance` sorts by `(entity, field, mapping)`

```divergence
decision: RFC 0032 D7
grade: OPEN
class: discovery
at: 2026-08-30T20:35:00Z
attempt: 1
claim: D7 delegates the sort order and says to decide it against the corpus rather than reason about it
action: decided
```

D7 is `OPEN` and asks execution to look at `multi_source`'s four recovered facts and pick.
Looked at:

```
order_line.quantity   mapping_legacy
order_line.quantity   mapping_platform
order_line.sku        mapping_legacy
order_line.sku        mapping_platform
```

`(entity, field, mapping)` keeps a field's two answers adjacent, which is the comparison a
reader of a merged field is making — *how is `quantity` built, and do the two documents
agree?* `(entity, mapping, field)` groups by document and interleaves them, so the two rows
that exist to be compared sit apart with another field between them.

Decided as §5.4 argued, and the argument survives contact: the report is read per field,
not per document. Recorded here because D7 asked for the look, and the look is the evidence
— the prose alone would have been a preference.

## Completion — 2026-08-31

D-035, D-036 and A-1 accepted by the author as D8, D9 and D10; the decision table is
append-only, so they are appended rather than folded into the rows they amend. Status
flipped to ✅ Complete.

**The document is not retired in this change, and that is a mechanical exception rather
than a judgement.** `rfcs/INDEX.md` says to retire in the same change that flips the
status, and `tools/check_rfc_corpus.py` enforces what a retirement row must name: a commit
that **holds the document** *and* that **a fresh clone can reach**. Both, together.

The convention assumes an RFC that already lives on `main` — for those, the branch point
satisfies both. RFC 0032 was authored *and* executed in one branch, so no commit satisfies
both yet: `main` at the branch point (`13d2049`) does not hold the document, and the branch
commit that does is not an ancestor of `origin/main`. Attempted rather than assumed:

```
RETIRED.md: 0032 is listed as retired, but rfcs/0032-*.md is in the tree
RETIRED.md: 0032 names `8e95b49`, which is not an ancestor of origin/main —
            a fresh clone cannot reach it
```

So the retirement is the change immediately after this lands, citing the merge commit. Two
alternatives were rejected: leaving the status at 📝 Draft, which is simply false once the
design is the code; and writing the row anyway, which produces exactly the unfollowable
citation RFC 0025 §5.4 exists to prevent — the module docstring records that this has
happened once already.

**Correction, 2026-08-31 (R-2).** The paragraph that stood here claimed `INDEX.md` had no
case for an RFC born and completed in one change. It has one, forty lines below the
retirement section, in the status vocabulary: 🚧 In progress is defined as "either partially
shipped, **or fully shipped and waiting on a retirement commit the mainline can reach**",
and ✅ is described as transient — "a row reaching either status is retired in the same
change". The convention had already answered this exactly; the status was simply wrong, and
the reported gap did not exist. Status corrected to 🚧 In progress in the header and the
index. Nothing about the deferred retirement itself changes — that reasoning held.

## Review round 1 — 2026-08-31

Four findings, all valid, all reproduced before being fixed.

### R-1 — `FieldProvenance` accepted the old positional call and rebound it

```divergence
decision: RFC 0032 D5
grade: ASSUMED
class: drift
at: 2026-08-31T00:40:00Z
attempt: 1
claim: D5 said a positional caller "gets a TypeError on arity rather than the silent rebinding"; recipe_id carries a default, so the old four-argument call satisfies arity and binds provenance into mapping
action: departed
```

`drift`, not `spec-gap`: the claim was false when it was written, and it was the whole
argument for the field's placement. Reproduced:

```python
FieldProvenance("order_item", "quantity", Provenance.DIRECT, None)
# FieldProvenance(entity='order_item', field='quantity',
#                 mapping=<Provenance.DIRECT: 'direct'>, provenance=None, recipe_id=None)
```

No error — an entry whose `mapping` is a `Provenance` and whose `provenance` is `None`.
Fixed with `kw_only=True`, which restores the loud failure and keeps the reading order the
row wanted; accepted as D11. The lesson is the cheap one: *a claim about what a signature
refuses is a thing to run, not to reason about.* One line in a REPL would have caught it
at design time.

### R-2 — the "gap in the retirement convention" did not exist

See the correction in the completion section above. `INDEX.md`'s status vocabulary already
defines 🚧 In progress as covering "fully shipped and waiting on a retirement commit the
mainline can reach", and describes ✅ as transient. The retirement *reasoning* held; the
status was wrong, and the reported gap was a section I had not read forty lines further
down. Reading a convention's neighbourhood is part of following it.

### R-3 — the refusal used a non-standard source path

`f"{document}.document"` produced `mappings/orders.document` where every other validation
path is `<document>: <field>` via `source_path_from_loc`. The two formats sat next to each
other in this branch's own test and the mismatch was still not noticed:

```python
assert paths == ["mappings/orders.document", "mappings/orders: fields.f.simple.from"]
```

Now `source_path_from_loc(document, ("document",))`. Found independently by two reviewers,
which is what a coordinate a reader copy-pastes deserves.

### R-4 — `evidence.py`'s docstrings still described the pre-RFC contract

Three statements, none of them in this branch's diff and all of them made false by it:
`SpecEvidence`'s sort-key table said `provenance` sorts by `(entity, field)`; the
`provenance` field comment said a merged entity's field "appears once however many mappings
build it"; and `OpenDecision` gave "an entry keyed on the canonical cannot say which
document to edit" as the omission's reason, which is precisely the half RFC 0032 removed.
All three updated — the third to the reason that actually survives, that a merged entity's
gap may be closable in any one document, so an entry per mapping would be an over-count.

**Pass 7 of the audit missed all three**, because it read the diff and these lines are
outside it. A change that redefines a published contract has to re-read the prose that
*describes* that contract, not only the prose it touched.

## Retired — 2026-08-31

RFC 0032 is retired: the document deleted, its `INDEX.md` row dropped, and a row appended
to `RETIRED.md` naming `3f7b574` — the commit that merged PR #59 into `main`.

That is the commit the deferred retirement was waiting for, and it satisfies both halves of
what `tools/check_rfc_corpus.py` demands, which nothing before it did:

- it **holds the document** — `git show 3f7b574:rfcs/0032-mapping-identity.md` prints it;
- it is **reachable from the mainline**, being on `main` itself.

The status never passed through ✅ in the tree. `INDEX.md` calls ✅ and ❌ transient — "a
row reaching either status is retired in the same change" — so 🚧 In progress went straight
to a `RETIRED.md` row, which is the shape the convention actually describes. The earlier
flip to ✅ was the error R-2 records; this is what it should have been all along, one change
later than the convention's usual case because the document was born and executed in a
single branch.

Nothing else moves. The design is now the code, the tests and the how-to, and the 27
prose citations of `RFC 0032` across the source remain followable through the `RETIRED.md`
row rather than through a file.

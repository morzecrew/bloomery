# T-0016 · RFC 0052 — dbt as a complete quality target

Executed on branch `feat/dbt-quality-parity`. §12's four phases: the P1 spike that can
invalidate a `LOCKED` row, the reconcile model, the reject table with its replay, and the
quality mart whose refusal falls once the other two land.

**Drift count: 3.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the RFC's text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

| Class | Test | Meaning |
| --- | --- | --- |
| `discovery` | Could not have been known before code existed | Healthy — the RFC was right to be silent |
| `spec-gap` | Could have been known; the RFC was silent or at the wrong altitude | The design process missed something |
| `drift` | The RFC covered it and it was built otherwise anyway, **or** a claim was made that was not true when it was made | **A defect** |
| `irreducible` | No amount of design settles it | Stop and spike |

## D-079 — P1: `ref()` resolves at the floor, so the fallback body is dead

```divergence
decision: RFC 0052 D3 — the body, which the row leaves open ("how it names relations is not" locked)
grade: OPEN
class: discovery
at: 2026-09-04T16:20:00Z
attempt: 1
claim: §9 records that `ref()` inside a run-operation was read about rather than run, so D3 locks the macro form and delegates the body; it resolves at both ends of the supported range, and §9's naming-policy fallback is the body on no supported version
evidence: `dbt run-operation replay_thing` under dbt-core 1.10.8/dbt-duckdb 1.9.6 -> `ref() resolved to: "p1"."main"."thing"` / `rows via ref(): 2` / `after txn: z`; identical under 1.12.3/1.11.0
action: decided
proposal: the macro names relations through `ref()` unconditionally; the naming-policy fallback is not built, and §9's first risk closes rather than narrowing to a version range
```

- **Touches:** RFC 0052 D3 (`LOCKED` on the form, open on the body) and §9's first risk,
  the one the RFC put P1 first to settle.
- **Measured, at both ends of `dbt-core>=1.10.8,<2`:**

  | | dbt-core | dbt-duckdb | `ref()` in run-operation | `BEGIN`/`COMMIT` via `run_query` |
  | --- | --- | --- | --- | --- |
  | floor | 1.10.8 | 1.9.6 | `"p1"."main"."thing"` | rolls back |
  | ceiling | 1.12.3 | 1.11.0 | `"p1"."main"."thing"` | rolls back |

  A macro doing `{% set rel = ref('thing') %}` then `run_query("SELECT COUNT(*) FROM " ~ rel)`
  returned the right count on both. So does the write path: an `UPDATE` through the same
  relation took effect and was visible to a following `SELECT`.
- **D14 measured with it, because the same spike could.** D14 asserts the three replay
  statements are atomic under an explicit `BEGIN`/`COMMIT`, which rests on successive
  `run_query` calls sharing one connection — a claim the RFC also made from reading. Two
  probes, both ends: an explicit `ROLLBACK` after an `UPDATE` restored the prior value,
  and a *failing* statement between `BEGIN` and `COMMIT` left the earlier `UPDATE` in the
  same macro unapplied (`'b'`, the original, not `'partial'`). The transaction is real and
  a mid-macro failure does not half-apply.
- **Why this needed running:** the two possible answers are not "works" and "errors". A
  `ref()` that silently rendered as an unquoted string, or a `BEGIN` that autocommitted
  per statement, would both produce a macro that *runs* and leaves the reject table
  half-updated — the failure mode D14 exists to prevent, arriving through the mechanism
  meant to prevent it.
- **Consequence:** P1 produces no code. What it removes is a branch: §9's fallback is not
  written, and the compatibility range in D3 is the dependency pin, not a narrower one.

## D-080 — no fixture isolates a reconcile check, so P2 cannot prove itself end to end

```divergence
decision: RFC 0052 §12 P2 — how a phase the corpus cannot reach is proven
grade: UNLISTED
class: spec-gap
at: 2026-09-04T16:30:00Z
attempt: 1
claim: §12 says P2 "removes one refusal on its own", which is true of the code and false of the corpus — every fixture declaring `reconcile:` also declares `quarantine:`, so all three stay refused until P3 and no fixture compiles for dbt because of this phase
evidence: `grep -rln "reconcile:" tests/fixtures/` -> quality_precedence, semi_additive_inventory, dirty_corpus; all three also match `grep -rln "quarantine:"`
action: decided
proposal: P2 is proven by unit tests over a directly-built ProjectIR, and the e2e build proof arrives with P3 rather than a fixture being added to carry it alone
```

- **Touches:** RFC 0052 §12's phase ordering. The phases are correct; what the sentence
  misses is that the corpus cannot observe the boundary between them.
- **Decided:** build the project in the test rather than add a corpus fixture. A new
  fixture is goldens across three dialects and four targets, and it would exist to prove
  an intermediate state that lasts one commit — the corpus would then carry a
  reconcile-only project forever to document a phase boundary nobody can reach again.
- **Because:** the same reasoning `_entity_test_artifacts` already records for its
  `fail_audits` leg (`logs/T-0003.md` D-014) — a lowering that is right and unreachable is
  covered by a test that builds the IR directly, so it is not discovered to be wrong on
  the day it becomes reachable.
- **Consequence:** `test_dbt_refuses_reconcile_naming_the_checks` becomes
  `test_dbt_no_longer_refuses_a_project_for_its_reconcile_block`, asserting on the
  **source path** rather than on the fact that something raised. "Refused for some reason"
  is what would let this refusal quietly return while `quarantine:` still fires.

## D-081 — a `ref()` in a quoted string is not a `ref()`

```divergence
decision: RFC 0052 D3 — the macro's body
grade: OPEN
class: discovery
at: 2026-09-04T17:10:00Z
attempt: 1
claim: §5.2 says the macro "issues `replay_statements(entity, ctx)` in order through `run_query`" without saying how a statement reaches `run_query`, and the obvious form is wrong — Jinja does not render `{{ ... }}` inside a string literal, so a quoted statement arrives at the engine with `{{ ref('order_line') }}` in it verbatim
evidence: `dbt run-operation blockset_probe` -> `quoted string stays: UPDATE {{ ref('thing') }} SET label = 'literal' WHERE id = 2` beside `statement rendered as: UPDATE "p1"."main"."thing" SET label = 'blockset' WHERE id = 1`, identically on dbt-core 1.10.8 and 1.12.3
action: decided
proposal: each statement is captured by its own `{% set statement_N %}…{% endset %}` block, whose body Jinja *does* render, and the variable is what `run_query` receives
```

- **Touches:** RFC 0052 D3, whose locked half is the macro form and whose body §9 left to P1.
- **Why this is not a detail:** the two forms are one line apart and produce artifacts that
  look equally correct in a golden. Nothing that reads bytes can tell them apart, and the
  failure is at run time in someone's warehouse.
- **Consequence:** the e2e tier runs the macro rather than only emitting it
  (`test_replay_admits_the_row_a_corrected_delivery_fixes`), which is the only check that
  distinguishes the two. Sabotaged: rendering the statements as quoted strings leaves every
  unit and golden test green and fails exactly that one.

## D-082 — the quality mart named the reject table literally

```divergence
decision: RFC 0008 D20
grade: LOCKED
class: drift
at: 2026-09-04T17:25:00Z
attempt: 1
claim: `_reference_map` was extended for the reconcile models and not for the reject tables, so `quality_mart_select`'s count over the reject relation reached the artifact as a literal `silver.<entity>__reject` — no dependency edge for dbt to order by, and a FROM naming a schema the model was not materialized into
evidence: `dbt build` on multi_source_quality -> `Binder Error: Table "incumbent" does not have a column named "reject_id"`, because the test tier's seeding had created `silver.order_line__reject` as though it were a bronze source
action: halted
proposal: every relation this target emits is registered in the reference map, reject tables included; a unit test asserts the mart's `{{ ref(...) }}` rather than only its run context
```

- **Touches:** RFC 0008 D20 (`LOCKED`) — "a body that reached a file with a literal
  relation name is exactly the defect D20 closes". Halted and fixed rather than departed
  from: the row is right and the code disagreed with it.
- **Why `drift`:** D20 is explicit, `_render`'s own docstring says a new artifact kind
  forgetting the rewrite is how the defect comes back, and this change added two artifact
  kinds and remembered one.
- **Found by the build tier and by nothing else.** The unit tests passed, the goldens
  passed, `dbt parse` and `dbt compile` both passed — a literal relation name is
  well-formed SQL and resolves to *a* table. What surfaced it was a downstream symptom in
  the test tier's own seeding, which read the literal as a bronze source and created it.
  That is RFC 0009 D22's original finding arriving a second time by a second route.
- **Consequence:** the reject relation's `ref()` is asserted in
  `test_dbt_emits_the_quality_mart_with_its_own_run_context`, positively and negatively —
  a test that only looked for `{{ ref(...) }}` somewhere in a mart full of them would not
  have failed.

## Self-audit — 2026-09-04

Scope: the whole branch against `main` at `588e1e6` — 8 commits at the time of the sweep,
4 source files (+335 −63), 37 test files, 15 docs. RFC 0052 re-read first; the ten passes
run in order; three rounds, converging on the third.

**Five findings, all fixed. One of them was a missing check rather than a wrong one, and
it is the reason this section exists.**

### F1 — the conservation audit was missing on dbt (severity: high)

`_entity_test_artifacts` skipped it and stated the reason in its own docstring: "it needs
a reject table, and `_refuse_quarantine` has already run". The reject table landed in this
branch and the refusal was deleted, so the condition evaporated and the skip stayed.

Every audit family reached parity except the one that checks the *split itself*: every
bronze row lands in the entity, an unresolved reject, or the deduped count. So dbt built
both sides of the routing split and never checked they add up — and that absence is
invisible from everywhere else. Every model materializes; every other test passes; a
silently dropped row is precisely what nothing else looks for.

Found by comparing the two targets' audit sets by hand while checking a *different*
question (whether a quarantining SCD2 entity emits the same families on both targets — it
does). Nothing in the suite compared them, which is why the fix is a set-equality
assertion over four quality fixtures rather than a test for this one audit.

`conservation_audit_select` gained the `relation` parameter its siblings already had.
Fixed in `eba4cb7`.

### F2 — three prose claims describing a refusal that no longer exists (severity: medium)

- `Target`'s docstring called dbt "minimal but honest" — RFC 0008 §5.5's phrase for an
  emitter that produced no audits at all.
- `step_output_body` said "Only SQLMesh reaches the wrap today".
- `pages/docs/reference/errors.md` said a `quarantine:` block or `reconcile:` check
  compiled for dbt "lowers neither in this wave".

Each is the class RFC 0051 already found twice in this repository: a statement that was
true when written, describing a guard that has since gone. Fixed in `2404487`.

### F3 — the dbt module's artifact list omitted the four new families (severity: medium)

The module docstring is where a reader goes to find out what this emitter writes, and it
named none of `<entity>__reject.sql`, `macros/replay_<entity>.sql`,
`<check>__reconcile.sql` or `mart_data_quality.sql`. RFC 0052 §7/D10 asks for the coverage
claim to be restated where a reader will find it; the docs page was updated and the
source-side statement was not.

### F4 — two self-referential claims in one docstring, both now false (severity: low)

`_entity_test_artifacts` said "Three, and they are the three"; it is four. And its
`fail_audits` paragraph said the leg is "never non-empty" because the quarantine refusal
raises first, and that it "goes live the day dbt grows a reject model". That day was this
branch — `quality_precedence` emits three of them and `dirty_corpus` a fourth — and the
paragraph still said the leg never fires. The prediction was right and outlived its own
correctness.

### F5 — a computed value the envelope discards (severity: low)

`_reconcile_artifacts` passed `reconcile_keys(check, ir)` to `_config_line`, whose `FULL`
branch ignores its key argument entirely. Harmless at run time and misleading to read: it
looks like the comparison's grain reaches the artifact, and it does not — SQLMesh states
the grain in the model header and dbt has nowhere to put it.

### What the sweep checked, and what it produced

- **Sabotage, eight in total across the branch**, each killing only its own test: the
  incremental strategy set to `append`; the `COALESCE` preservation removed; the replay
  statements emitted as quoted strings; the transaction dropped; the conservation audit
  removed (twice, before and after the parity test was widened); the conservation audit
  left on `@this_model`; and the `start`-line case carried over from T-0015's method.
  The fourth killed **nothing** on its first attempt, which is what produced the
  emitted-bytes assertion for D14.
- **Patch coverage, full profile:** 100% (32/32 added source lines), measured after the
  fixes.
- **Decision-table conformance:** every `LOCKED` row verified against the emitted bytes
  rather than by reading — D1, D2, D3, D5, D7, D9, D11, D14 checked directly; D6's
  severity checked in both directions. RFC 0052 has no `OPEN` rows; the one delegated
  half (D3's body) is D-079 and D-081 above.
- **Round two** re-audited round one's fixes and found F4 and F5 inside them. **Round
  three** found the parity assertion was fixture-specific luck — it holds for
  quality-carrying fixtures and legitimately fails for `path_conflict`, where a reconcile
  audit is a row predicate and dbt writes it as a `schema.yml` generic test. Widened to
  four fixtures, with the exclusion's reason written down rather than left as a shape
  that happened to pass.

### Residue — closed

The three items this section first listed were taken up rather than left. Two were
defects and one was an untested combination that turned out to be a third; all are
D-083 through D-085 above.

- **The quarantining SCD2 entity** was not a coverage gap but a hole in replay's design,
  and it is now a refusal (D-083). Measuring it is what found the other two.
- **The equivalence leg's excluded column** was excluded on an unverified sentence, and
  `raw` matches. The column list is derived from `REJECT_COLUMNS` now, so the exclusion
  cannot recur by omission (D-085).
- **The replay e2e** was crediting replay for the model rebuild's work (D-084).

### Residue — what I would still distrust

- **The refusal in D-083 narrows what compiles**, and the narrowing is now handled rather
  than noted. The CHANGELOG entry moved from *Added* to *Removed* — a breaking refusal
  filed under Added is a breaking change shipped silently, which is the thing the PR
  template's own rule forbids — and it names what to write instead in both directions,
  since which half a reader gives up depends on which they need. RFC 0060 carries the
  design for giving up neither: three candidate routes, the measurement that decides
  between them, and the two `OPEN` rows it cannot answer from a desk. The refusal's
  docstring and the docs block both say *unbuilt* rather than *wrong*.

  What remains a scope call: a user's spec carrying both stops compiling at this release
  rather than at the one that fixes it. The alternative was leaving a merge that reports
  success and inserts an invisible row, and the project's stated rule decides between
  those — but it is still my call, and it is reversible.
- **`dbt source freshness`-style commands are untested here** because nothing emits for
  them yet — RFC 0057's subject, named so the absence is not read as coverage.
- **A sabotage that kills through a different assertion than the one under examination**
  reports a live test and proves nothing about it. Re-checking the branch's sabotages
  against that standard found a second case: the quoted-string sabotage (D-081) killed
  the e2e at `assert result.success`, because the emitted project stops building — an
  honest kill, but a generic one — and the **unit** test that claims to pin the block-set
  form *passed under it*. Its assertion looked for `{{ ref(...) }}` surviving into the
  file, and `{% set x = '…{{ ref(...) }}…' %}` contains that too. It now asserts the
  opening tag in both directions. The remaining six were re-read and each kills through
  the assertion naming its own claim.

## D-083 — replay and native SCD2 have never composed

```divergence
decision: UNLISTED — whether `quarantine:` and `scd: type2` may be declared on one entity
grade: UNLISTED
class: discovery
at: 2026-09-04T18:40:00Z
attempt: 1
claim: replay's merge admits a row by the entity's own columns (RFC 0016 §5.6), and a type 2 relation carries the validity interval its framework maintains as well — so the merge inserts a version with valid_from, valid_to and dbt_scd_id all NULL, and reports success
evidence: `MERGE INTO silver.customer_snapshot ... WHEN NOT MATCHED THEN INSERT` run against a built dbt snapshot -> `('c2', Decimal('99.99'), None, None, None)` for (customer_id, lifetime_value, dbt_scd_id, valid_from, valid_to)
action: decided
proposal: refuse the pair at resolve, on every target, naming both halves and what a reader can give up
```

- **Touches:** nothing stated. RFC 0052 is about which target lowers what, and this is
  about a lowering neither target's shape supports. It surfaced only because this branch
  gave dbt a replay macro and the audit asked whether an SCD2 entity got the same artifact
  set on both targets — it does, and both are wrong.
- **Why it was never seen:** no fixture declares `scd: type2` and `quarantine:` together,
  and nothing refused the pair, so the corpus has never emitted a replay merge against a
  historical relation. SQLMesh has had this hole since RFC 0016; the branch did not
  introduce it, it made it reachable on a second target and then looked.
- **Why a refusal rather than a fix:** the missing columns cannot be filled by a
  compiler. `dbt_scd_id` is a hash dbt computes and owns, and writing bloomery's guess of
  it is this package inventing another framework's bookkeeping — the coupling
  `emit/lower/` exists to prevent. `valid_from`/`valid_to` could be guessed and should not
  be: a version interval invented by a merge is a history that says something nobody
  declared.
- **The failure mode is the severe one.** The merge does not error. The row lands, is
  queryable, and is skipped by every as-of join — which is what a type 2 relation is
  *for*. An operator running the artifact bloomery emitted gets a success line and a
  silently invisible row.
- **Consequence:** `_snapshot_quarantine` in `resolve/build.py`, beside the merged-`type2`
  refusal it is not the same as. A `scd: type2` entity with only `flag` rules still
  compiles — it diverts no row, emits no reject table and gets no replay macro — and that
  is pinned, because a refusal that read its own message rather than its own condition
  would take the flagging case with it.

## D-084 — the replay e2e credited replay for the model's work

```divergence
decision: RFC 0052 §6 — "Replay, executed"
grade: UNLISTED
class: drift
at: 2026-09-04T18:55:00Z
attempt: 2
claim: `test_replay_admits_the_row_a_corrected_delivery_fixes` delivered a corrected row to bronze, rebuilt, then replayed and asserted the row was in the entity — but the rebuild had already put it there, so the assertion held whether or not the macro did anything
evidence: `dbt build; <corrected delivery>; dbt run; SELECT _source_row_id, quantity FROM silver.order_line` -> `[('s1', 2), ('s2', 7)]`, taken *before* `dbt run-operation replay_order_line` was invoked at all
action: decided
proposal: delete the bronze delivery, widen the *spec* so the reject row's stored `raw` now passes, and assert the entity lacks the row before the macro and has it after
```

- **Touches:** RFC 0052 §6's replay leg, which asks for the macro to be executed and does
  not say what its effect should be measured against.
- **The mechanism I had wrong:** replay re-runs the current mapping over the `raw` each
  reject row stores. It is not the path by which a corrected *delivery* reaches the
  entity — the entity model re-reads bronze on the next run and does that itself. Replay
  is for a row whose **spec** changed, or whose bronze delivery has aged out of the
  incremental window. The docs page already said so; the test did not.
- **Why the sabotage sweep did not catch it:** rendering the replay statements as quoted
  strings made this test fail — but at `assert result.success`, because the macro errored.
  A sabotage that kills a test through a different assertion than the one under
  examination reports a live test and proves nothing about the claim in its name. The
  useful sabotage is the one that leaves the macro *working* and removes only the effect:
  dropping the merge statement, and separately not widening the spec at all. Both now run.
- **Consequence:** the test is `test_replay_admits_a_row_the_widened_spec_now_accepts`,
  and it asserts the entity's contents **before** the macro as well as after. The seed
  moved from a coercion failure to an `in_enum` one, because a spec change can relax an
  enum chain and relaxing a coercion rule means changing the column's type.

## D-085 — `raw` was excluded from the equivalence comparison on an assumption

```divergence
decision: RFC 0052 D12
grade: ASSUMED
class: drift
at: 2026-09-04T18:20:00Z
attempt: 1
claim: the equivalence leg compared 13 of the 14 reject columns and excluded `raw` on the stated ground that "it is a JSON payload whose two engines may key it differently" — which was never measured, and is false
evidence: `assert from_dbt == from_sqlmesh` with `raw` included -> passes
action: departed
proposal: derive the compared column list from `REJECT_COLUMNS` rather than typing it, so no column can be excluded by omission and a column added to the schema joins the comparison automatically
```

- **Touches:** D12, which asks for the reject tables to be compared "row for row". A
  comparison with a hand-typed column list is row-for-row over the columns someone
  remembered.
- **Why `drift`:** the exclusion carried a reason, the reason was checkable, and it was
  not checked. That is a claim that was not true when it was made.

## The plan

### What arrives, and how

D2 is `LOCKED` that what crosses is the upstream's **compiled IR**, and D8 that how it
reaches the compile is the caller's, "exactly as a `StepRegistry` is". A `StepRegistry` is an
in-process object, so the upstream arrives as a `ProjectIR` keyed by the alias the downstream
calls it:

```python
compile_project(project, target=…, dialect=…, upstream={"platform": platform_ir})
```

**Not a serialized form**, and this needed checking rather than assuming: §5.2 says "its IR,
serialized", and there is no IR deserializer in the tree — `ir/fingerprint.py` hashes a
`ProjectIR` and nothing reads one back. §5.2's point is about *what* crosses (what was built,
not what was written), which a `ProjectIR` satisfies exactly; a wire format is a separate
feature D8 assigns to the caller.

The keyword threads `compile_project → build_project_ir → pipeline → check_guardrails`, which
is the path `steps: StepRegistry = EMPTY_REGISTRY` already takes through the same four
signatures.

### The declaration

```yaml
imports_version: 1
imports:
  platform:
    entities: [customer]
    marts: [customer_360]
    metrics: [active_customers]
```

Its own spec kind, mirroring P1's `exports_version` for D1's reason — a kind is invisible to
a project that does not use it. The key is the **local alias**, which is what makes the
`upstream=` mapping addressable, and the three lists mirror `Exports` so the two documents
read as one boundary from two sides.

### The refusals

| Refusal | Class | Precedent |
|---|---|---|
| a declared alias has no IR supplied | `UnknownUpstream` | `UnknownStep` — a spec references what the caller-supplied registry does not hold, and the message names what *was* supplied |
| an imported name is not on the upstream's export list | `UnexportedImport` | §4's own goal: "refused, naming the export list" |
| a local name and an imported name are the same | `ImportCollision` | §2 names this as the payoff; `check_lineage_names`'s shape |

**No `ProjectIR.imports`, and therefore no version bump or regolden.** P1 put the *export*
list on the IR because D2 makes it the thing that crosses. An import list is the opposite:
purely local, read by this project's own guardrails, and never read by a further downstream —
which reads *this* project's exports, not its dependencies. P3's lineage and P4's fingerprint
may want it; neither is this phase, and adding a field on the chance is what D2 of S-0007
argues against one document over.

## Self-audit

Branch `feat/import-declaration` against `main`: one new spec kind, one new guardrail, three
error classes, a keyword threaded through four signatures, and no IR change. Scope walked
whole — the document, the loader wiring, the schema registration, the guard, the threading,
the docs rows, the fixture, and both test suites. Findings ranked; all fixed on the branch
before this was written.

**1. The collision guard was blind to the entities the spec layer never sees.**
`_declared_locally` read `project.entity_model.entities`. A step output is an entity too,
named after the last segment of the relation its wiring binds (S-0034/emission-and-the-dag), and it never
appears in the authored model. Measured on `step_resolution`: the entity model declares
`customer_raw` and the draft carries `customer`, `customer_raw` and `customer_xref` — so a
project whose step produces `customer` could import another project's `customer` and compile
clean. That is `check_lineage_names`'s argument verbatim, and it was available to be read
before this guard was written.

Entities now come from the draft; marts and metrics stay on the authored documents, because
a mart that failed to flatten is absent from the draft while very much declared. **The split
is not a compromise**: the two guards this one sits between already make it in opposite
directions for those exact reasons, and the module docstring says which and why.

**2. Two upstreams supplying one name was not a collision at all.** §5.4 names "a local name
colliding with an imported one" and stops there. Measured: two upstreams both exporting
`gross_revenue`, both imported, compiled clean — and every later reference to it belongs to
whichever lookup runs first. It is the same ambiguity as the local case and **worse**,
because neither upstream's author can see it: each file is correct on its own. `_claimed_twice`
now refuses it, once per colliding name and naming every alias that supplies it, because a
refusal per pair says the same thing three times for three upstreams.

Proposed as a row below: §5.4's sentence covers the case somebody noticed, not the case.

**3. `kind[:-1]` spells `entities` as `entitie`.** Caught by reading the first refusal it
produced. Replaced with a written-out singular table — which is also what stops a kind being
added to one side of the boundary and silently unchecked on the other. The sweep then found
the assertion I wrote for it was in the wrong test (M11 below).

**4. An unreachable refusal would have been written.** §12 lists grain conflict among P2's
refusals; a mart cannot name an imported entity until P3 resolves imported names, so the
guard would have had no input that could redden it except by neutering the resolver that
fires first. Entered before building rather than discovered after, and proposed as a row.

### What was not done, and why

- **No `ProjectIR.imports`, no version bump, no regolden.** Measured rather than asserted:
  the golden diff is one new file, `tests/golden/schema/imports.json`, and not one fingerprint
  moved. An import list is local — read by this project's own guardrails and never by a
  further downstream, which reads this project's *exports*. P1 put the export list on the IR
  because D2 makes it the thing that crosses; the mirror argument does not hold here, and
  adding a field for P3 and P4's convenience is what S-0007/D-2 argues against.
- **No cycle check.** The close-out entry above: under D2 a cycle among freshly compiled
  projects cannot be handed to `compile_project`, and the stale case needs a project identity
  that does not exist.
- **No grain conflict.** Moved to P3 with its input.
- **The `cross_project` fixture is nested and excluded.** A project carrying an imports
  document cannot compile without an upstream, so it must not be reachable by the sweeps that
  compile every top-level fixture directory. `fixture_sources` globs one level, the property
  tier's schema sweep uses `rglob`, and `NON_SPEC_FIXTURES` names it for the third.

## Review round 1

Five findings, all from one reviewer, all valid. Four fixed; one is real, is the design, and
is recorded rather than built.

| # | Finding | Verdict |
|---|---|---|
| F1/F2 | the published schema accepts an imports document the loader rejects — no upstreams, or an upstream reading nothing | valid, fixed |
| F3 | `patternProperties` without `additionalProperties: false` lets a non-identifier alias through the schema | valid, fixed |
| F4 | the CLI cannot compile a project with imports | valid, **out of scope** — see below |
| F5 | `evaluate()` and the timeline call `pipeline` without `upstream` | valid, fixed, and the worst of the five |

**F5 is the one that mattered, and it is a rule I already had.** `pipeline` has three callers
and I threaded one. Reproduced: the same project that compiles clean through
`build_project_ir(upstream=…)` came back from `evaluate()` with a `guardrails` stage and a
`UnknownUpstream` refusal — a surface reporting a refusal the compiler does not. The timeline
was the same, and worse there, because every refusal propagates and an importing project
would have had **no timeline at all**.

`SpecVersion.steps` carries the argument for the fix verbatim: "a project declaring `steps:`
is refused with `UnknownStep` against the empty registry, so a history of any step-wiring
project would have no timeline at all. It is the same caller-assembled compile input." Swap
two nouns and it is this. `evaluate()` and `SpecVersion` both gained `upstream`, and the new
test asserts the property — *every surface that compiles can supply one* — rather than the
three instances, so a fourth caller fails there instead of reporting a phantom.

**F1–F3 are one defect with three faces: the published schema was looser than the loader.**
S-0037/D-10 makes the schema a pre-filter and the parser the authority, so the schema may be
*stricter* and never looser — a document it accepts and the loader rejects is one a proposal
loop emits, a user pastes, and neither artifact explains. All three came from the generator's
defaults: `patternProperties` constrains only the keys that match, so a non-identifier alias
falls through to `additionalProperties: true`; and three arrays with defaults make
`minProperties` useless, since `{"marts": []}` has a property and reads nothing.

**The same gap was in `exports.json` and shipped with P1.** Fixed here too, and the expansion
is deliberate rather than silent: the two documents mirror each other, the rule is one line
per file, and a tree where two mirrored schemas disagree about strictness is worse than
either. The goldens move additively — `+66`, `-0`, two files, no fingerprint.

**F4 is right and is the phase's shape.** `bloomery compile` calls `compile_project` with no
`upstream`, so a project with an imports document is refused through the CLI. There is nothing
for the CLI to pass: §5.2 says the upstream arrives "serialized" and no IR deserializer
exists — noted in this log's plan before any of this was built. Nothing regresses, because
the only projects affected are ones using a document that did not exist yesterday. It is a
gap the RFC does not name, and the row proposed below names it.

# T-0011 · RFC 0034 — metrics over time

Executed on branch `feat/period-over-period`. The whole of RFC 0034: derived metrics,
offsets, cumulative windows and metric filters — the four constructs that made "revenue
vs. the same month last year" unexpressible. The RFC was written and executed in one
change, so it stays live for one more (`rfcs/INDEX.md` says why).

**Drift count: 2.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the RFC's own text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

| Class | Test | Meaning |
| --- | --- | --- |
| `discovery` | Could not have been known before code existed | Healthy — the RFC was right to be silent |
| `spec-gap` | Could have been known; the RFC was silent or at the wrong altitude | The design process missed something |
| `drift` | The RFC covered it and it was built otherwise anyway, **or** a claim was made that was not true when it was made | **A defect** |
| `irreducible` | No amount of design settles it | Stop and spike |

## D-053 — `filter:` is refused on a derived metric

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T18:55:00Z
attempt: 1
claim: §9 lists per-*input* filters as out of scope and is silent on a filter written on the derived metric itself, which MetricFlow does accept
evidence: src/bloomery/guardrails/metrics.py:189
action: decided
proposal: A `filter:` on a `derived:` metric is refused (`InvalidMetricShape`). Filtering a derived metric restricts the measures one level down, not the metric the filter is written on — which is a post-aggregate filter, §9's explicit non-goal.
```

Two arguments, and they agree. The semantic one: MetricFlow applies a derived metric's
`filter` to the measures its inputs aggregate, so `revenue_yoy` filtered to `status =
paid` is not "the year-over-year change in paid revenue restricted afterwards" — it is
the change computed from paid rows, which is a *different metric* and one the author can
write directly by filtering `revenue` and deriving from that. A filter that means
something other than what it reads is the silent-wrongness class this project refuses.

The structural one: D9 checks a filter's dimension against the marts listing the metric
among their measures, and a derived metric need not be listed on any (D4). Checking it
would have meant reaching for the ownership rule, which lives a layer above the
guardrails. Refusing costs nothing an author cannot express another way.

## D-054 — a metric filter names a categorical dimension, never a date role

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T19:05:00Z
attempt: 1
claim: D8 says a filter is `{dimension, op, values}` and says nothing about which dimensions are filterable
evidence: src/bloomery/guardrails/metrics.py:114
action: decided
proposal: A metric filter's dimension must be a categorical dimension of the mart; a date-role bucket is refused with a message routing to `cumulative:` and `offset:`.
```

Found by building the renderer. A date-role dimension is not spelled `{entity}__{column}`
in a MetricFlow where-filter — it is `{entity}__{role}_day__{grain}`, and that rule lives
in `planner/names.group_by_name`, in a layer above the emitter. Emitting a filter on
`sold_month` would have needed either a second spelling of that rule in `emit/` or an
inverted import.

Refusing is not a workaround for that, though: a metric restricted to one period is a
*constant*, and the two constructs this RFC adds are exactly how a time relation is
expressed instead. The layering made the question visible; the semantics answered it.

## D-055 — Cube refuses by existence, not per mart

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T19:20:00Z
attempt: 1
claim: D11 says Cube "refuses derived and cumulative metrics per construct with UnsupportedByTarget" and does not say what triggers the refusal
evidence: src/bloomery/emit/cube/__init__.py:328
action: decided
proposal: The refusal fires when such a metric *exists in the project*, not when a mart names it in `measures:`.
```

Cited as `unlisted` rather than against D11: that row settles *what* is refused and is
silent on *when*, and the trigger is the part that had to be decided. Nothing here
departs from D11 — it answers a question D11 does not ask.

The existing Cube precedent tests `for name in owned`, i.e. metrics a mart names. That
cannot work here: RFC 0034 D4 says a derived metric need not appear in any mart's
`measures:` at all, so the per-mart test would let the common spelling through and Cube
would emit a complete-looking model quietly missing the metric. A missing metric is an
approximation of the metric set, and RFC 0008 D3 says fail loud rather than approximate.

The cost is real and worth stating: a project carrying one derived metric cannot emit
Cube at all. That is the same shape as `semi_additive: {rule: avg}`, which makes a whole
manifest unemittable on MetricFlow today — so the asymmetry is symmetric, and the message
names the construct and where the metric does live.

## D-056 — `period_agg` is pinned to MetricFlow's own default

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T19:30:00Z
attempt: 1
claim: the RFC does not mention `period_agg`, which decides what a cumulative metric means when the request asks for a grain coarser than the accumulation
evidence: src/bloomery/emit/metricflow/__init__.py:705
action: decided
proposal: Pin `PeriodAggregation.FIRST` explicitly — MetricFlow's own default — rather than leaving it implicit or choosing differently.
```

Found by reading `PydanticCumulativeTypeParams`: it is the one field there with a
non-`None` default. Month-to-date revenue queried *by month* under `FIRST` reports the
first day's value, which reads as surprising, and `LAST` is arguably what a person means.
Pinning `LAST` would make bloomery's cumulative metrics mean something different from
every other MetricFlow and dbt project's, which is a worse surprise and a silent one.
Pinned explicitly rather than defaulted, so the choice is visible where it is made, and
the emitter's own convention — every optional field written out — is kept.

## D-057 — §8's "nothing else in the planner changes" was false

```divergence
decision: RFC 0034 §8
grade: LOCKED
class: drift
at: 2026-09-02T19:40:00Z
attempt: 1
claim: §8 says "Nothing else in the planner changes", having checked `_measure_type` and generalized from it
evidence: src/bloomery/planner/explain.py:152
action: halted
proposal: §8 should have named `explain.py`. `_measure_explanation` raises `PlannerError` for a non-additive metric with no ratio, so every derived-metric plan failed there until it grew a branch.
```

`halted` rather than `departed`, and the distinction is the whole content of this entry:
nothing in §8 was flipped. §8 described the blast radius and described it wrongly; the
implementation did what the RFC intended and this proposes the correction to the text.

**The drift, and it is a claim rather than an implementation.** The check behind the
sentence was real — `_measure_type` does answer `decimal(38,9)` for a non-additive metric
— and the sentence generalized from one function to a package. `explain.py` was one grep
away: it reads `metric.ratio` and refuses when it is `None`, which is precisely what a
derived metric is.

It failed loudly rather than silently, which is luck rather than design: the first
`revenue_yoy` plan raised `PlannerError: non-additive metric 'revenue_yoy' has no ratio`.
The rule worth keeping is the one that has now cost twice: **a claim of the form "nothing
else changes" is a search, not an inference.** The previous branch's version of it was
"the fingerprints that matter are the ones that did not move".

Two more things came out of fixing it, neither of which the RFC asked for and both of
which belong to the same argument. A cumulative metric explained as `additive — SUM`
describes a metric that aggregates per period, which is the exact wrong number
`cumulative:` exists to prevent; and a filtered metric explained as its unfiltered sibling
is a number the reader has no way to question. Both now say what they are.

## D-058 — D4's "legal and inert" is false: a mart refuses a derived metric

```divergence
decision: RFC 0034 D4
grade: ASSUMED
class: drift
at: 2026-09-02T21:40:00Z
attempt: 1
claim: D4 says naming a derived metric in a mart's `measures:` "stays legal and inert, as it is for a ratio"
evidence: src/bloomery/marts/flatten.py:533
action: departed
proposal: Strike the sentence. A derived metric declares no grain — it has no measure to have one — and the grain guardrail requires a measure's grain to equal the mart's exactly (RFC 0010 D2), so naming it is a `GrainViolation`.
```

**The second drift, and the same shape as the first.** D4 reasoned from the ratio
precedent without checking that the precedent had ever run: **no fixture in the corpus
lists a grainless ratio in `measures:`**, so "as it is for a ratio" described behaviour
nobody had exercised. It was checkable before code — the mart flattener
compares `metric.grain` against the mart's, and a metric with no `grain:` carries `""`.

Found by writing the test for the claim, which is the only reason it was found at all:
the fixture deliberately does *not* name its derived metrics, so every other test in the
branch agrees with D4 by never touching the case.

The refusal itself is right and stays — a mart cannot serve a metric it has no grain
agreement with, and the message's first remedy ("remove it from this mart's measures")
is the correct fix. What is wrong is only the RFC's sentence. The first half of D4 — that
a derived metric *need not* be named — is unaffected and is what the fixture relies on.

## D-059 — `semi_additive` and `cumulative:` together are refused

```divergence
decision: RFC 0034 D6
grade: LOCKED
class: discovery
at: 2026-09-02T23:10:00Z
attempt: 2
claim: D6 settles that a cumulative metric is additive and keeps its own measure, and says nothing about the semi-additive case, which the guard therefore allowed
evidence: src/bloomery/guardrails/metrics.py:290
action: halted
proposal: Refuse `cumulative:` on a `semi_additive` metric. Add the row; the combination has no reading.
```

Found by closing the audit's own residue rather than by review. The residue said
this combination "compiles, emits and plans, and is not asserted to be
*meaningful*". Asserting it meant running it, and running it produced **2707 on a
day whose revenue was 100, in a month totalling 257**.

The mechanism is not subtle once seen. A semi-additive metric declares that it may
not be summed along its `over` dimension, and the emitter resolves that dimension
to a date role — always, by construction. A cumulative window accumulates along
the date. So the two constructs address one axis with opposite instructions:
MetricFlow lowers the `last` rule as a self-join against the measure's MAX over
the date, and the window then sums the rows that join fanned out.

`halted` rather than `decided`: D6 is `LOCKED` and this is a row it should have
had. Nothing was flipped — the guard simply grew the case D6 does not cover, and
the proposal is for the author to add it.

**Worth naming for the process, not only the defect.** "Compiles, emits and plans"
was offered in an audit report as a description of something *unverified*, and it
read as reassurance. Three of those four verbs were true and the number was
garbage. A residue entry that says a thing runs should not be written until
someone has looked at what it returns.

## D-060 — `period_agg` is authored, and defaults to `last`

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-03T00:05:00Z
attempt: 3
claim: D-056 pinned `PeriodAggregation.FIRST` on the argument that bloomery should not diverge from the ecosystem default
evidence: src/bloomery/spec/metrics.py:295
action: decided
proposal: Add `period_agg: first | last | average` to `CumulativeSpec`, defaulting to `last`. The ecosystem argument justifies a *default*; it does not justify pinning the value and removing the key.
```

**This entry replaces its own second attempt, and the correction is the point.**

Attempt 2 measured what `FIRST` does — `revenue_mtd` by month reporting 100 on a
month that totalled 257 — and concluded that the answer was a test and a sentence.
That was wrong, and the flaw is exactly locatable: D-056 argued *"bloomery does not
invent a divergence from the ecosystem"*, and the ecosystem it was deferring to
**exposes this as a key**. dbt's author writes `period_agg` on the metric; bloomery
hardcoded it. So the deference was to a default while removing the choice the
default belongs to — and it kept the half that makes a metric named `revenue_mtd`
report a number that is not month-to-date under any reading.

Measured, all three, on the fixture's March 2024 (revenue 257):

| `period_agg` | 2024-03 |
| --- | --- |
| `first` | 100 — the running total on the 1st |
| `last` | **257** — the accumulation at the month's end |
| `average` | 217.61… |

`last` is the default because it is the only value that makes the metric's own name
true, and because there is nothing to be compatible with: the construct is
unreleased, so no spec anywhere relies on `first` arriving by default. An author who
wants first-point semantics writes `period_agg: first` and gets exactly what
MetricFlow would have imposed.

Refusing the coarser request was considered again and rejected again, and that half
of attempt 2 stands: first-point semantics is a legitimate thing to want, and
refusing a valid question because its *default* surprised us would be over-reach.
What was wrong was the default, not the permission.

The general rule, which has now cost twice on this branch: **deferring to an
ecosystem convention means adopting its shape, not just its value.** A default
copied without the key it defaults is not deference, it is a decision taken quietly.

## Self-audit — 2026-09-02

Scope: the whole branch, 2 commits / 131 files / +4361−276 lines. Ten passes. Findings
below are ranked by severity and were fixed on the branch; the two that could not be
fixed here say so.

### A1 — a metric filter's dimension reached a template unquoted (security)

`MemberName` is deliberately unpatterned, and `RelationName`'s docstring records the
reason: *a field name reaches SQL through SQLGlot, which quotes and escapes it*. RFC 0034
breaks that premise. A filter's dimension is interpolated into
`{{ Dimension('<entity>__<name>') }}` on MetricFlow and `{CUBE}.<name>` on Cube, and
neither is SQLGlot.

Probed rather than reasoned about. A field named `evil') }} = 1 OR 1=1 --`, filtered on,
emitted:

```
{{ Dimension('sale__evil') }} = 1 OR 1=1 --') }} = 'paid'
```

The filter matches every row. A metric declared as a restricted subset silently returns
the whole population — the failure class this compiler exists to refuse, arrived at
through the one construct in the branch that touches a template.

**Fixed** by typing the reference `DimensionName` — `IDENTIFIER_PATTERN`, one constant
now shared with `RelationName` rather than a second spelling of it. Refused at parse,
which also puts the pattern in the exported JSON schema. Regression test verified red.

The residue: the pattern is the fix rather than per-target escaping, so filtering on a
column whose name is not a bare identifier is not expressible. That is the same trade
D13 makes for values, and it is stated in the docs rather than left to be discovered.

### A2 — a filter on a ratio metric compiled clean and was silently dropped

Found by pass 2, crossing the new constructs against every state of the additivity
vocabulary they wrap. The guard refused a filter on a `derived:` metric (D-053) and said
nothing about a `ratio:` one — and the RATIO lowering pins `filter=None`, while Cube's
calculated measure emits no `filters` at all. A "paid AOV" metric compiled, emitted, and
returned the unfiltered AOV.

Exactly the defect D-053 was written to prevent, missed because the entry reasoned about
`derived:` rather than about *metrics with no measure*.

**Fixed** by making the predicate the additivity: `non_additive` is precisely the class
that never emits a measure — ratio, derived, and the expression-over-components form
alike. One rule where there were one-and-a-hole. Test verified red first, and the
parametrization now covers both shapes.

### A3 — three prose claims that were not true

- `_ISO_DATE_LENGTH` carried a comment saying the length check and the quality layer's
  ISO regex "are checked against the same corpus by the type-conformance tier". No such
  check exists. Rewritten to say what the length test is *for* — a fit test, not a
  validity test — and to claim nothing about the two agreeing.
- Both semantic emitters open with a list of "deterministic choices pinned here", and
  neither mentioned the four constructs this branch adds. A list that stops being
  exhaustive is worse than no list, because it reads as one.
- `specs-and-catalog.md` said all three new forms need the catalog's `date_dimension`. A
  filter does not.

### A4 — the entity key was spelled in three modules

`mart.grain` is the dunder prefix of every group-by item. It was written out in the
emitter's `_entities`, again in the metric-filter lowering this branch added, and a third
time in `planner.names.entity_key`. The name has to match what was emitted or every
group-by resolves against nothing.

**Fixed**: one `entity_key(mart)` in the emitter that writes the manifest, which the
planner now delegates to. This is the fourth instance of the same pattern in three
branches — a constant two modules must agree on, defined at neither.

### A5 — untested crossings, and a claim nobody had exercised

Pass 2's matrix left three cells with no test: a cumulative metric that is also filtered,
a semi-additive metric that is also filtered, and D4's "naming a derived metric in
`measures:` is legal and inert". The first two are handled correctly and now have tests.
The third turned out to be false and is D-058 above — found *only* because the claim was
written down and then tested, since the fixture deliberately never names them.

### A6 — an unlogged narrowing of the RFC's own checklist

§12 item 1 says the time-grain and filter-operator vocabularies go in `spec/common.py`.
They are in `spec/metrics.py`, because both readers are metric-shaped and `common.py`
holds cross-kind grammar. Defensible, and it was never recorded — which is the finding.
The injection fix later put `IDENTIFIER_PATTERN` and `DimensionName` in `common.py`
after all, on the rule the file actually states: a name that leaves SQLGlot's quoting.

### A7 — a dedicated refusal the RFC predicted differently

D6 says a `non_additive` metric carrying `cumulative:` "would trip
`NonAdditiveWithoutComponents` with nothing to decompose into". True only when it has no
ratio; with one, it compiled. A dedicated `InvalidMetricShape` now names it. Beyond D6
rather than against it, and recorded here rather than nowhere.

### Verification, honestly

- **Suite:** 3460 passed, 5 skipped across unit / golden / property / execution.
  `just quality -s` green; `just build-docs` "No issues found". Coverage floors met —
  99.3% global, 100% guardrails, 92.5% steps — and **patch coverage is 100%
  (324/324 added source lines)**, measured with the full test profile rather than
  unit-only.
- **Verified red:** both fixes with a behavioural claim have a test demonstrated to fail
  without them. The ratio filter's was written and run red *before* the fix. The
  injection pattern's was written after — the defect itself was demonstrated by probe
  first — so it was verified by removing the pattern again and watching the test fail,
  which is the same evidence arrived at in the other order. The prose fixes have no test
  and none is claimed.
- **Sabotage:** seventeen mutations of the load-bearing checks, each run against the
  whole default tier set. **Sixteen caught, each by a different and relevant test** —
  which is the shape a real sweep has, and the shape the three broken attempts below did
  *not* have.

  **The survivor was the interesting one.** Dropping the plural in
  `parse_time_window` — so `"7 days"` yields the grain `"days"` — broke nothing. The
  reason is not a blind test: MetricFlow's own manifest transformer normalizes `"days"`
  to `"day"`, so the emitted artifact is byte-identical either way, and every assertion
  in the branch reads the manifest. The place it *is* observable is the IR, where
  `TimeWindow(grain="days")` and `TimeWindow(grain="day")` fingerprint differently — so
  two spellings of one window would have reported a change where none exists (RFC 0003
  §5.4). Not an equivalent mutant; an untested invariant, one layer below where everyone
  was looking. Two tests now pin it, both verified red against the mutation, and the
  fingerprint one is the only assertion in the branch that could ever have seen it.
- **What went wrong with the sabotage, twice.** The first two sweeps were killed
  mid-mutation. `SIGTERM` runs no `finally`, so a mutated file survived; the next sweep
  snapshotted *that* as its original and faithfully restored it; every verdict after was
  measured against a red tree, and every mutation looked "caught" by the same unrelated
  test. Then the third sweep was invalidated a different way: tests were edited while it
  ran, so later mutations were measured against a suite the baseline never saw. The rule
  that came out of it, and it is not a small one: **a mutation sweep measures the tree
  and the suite together, so both are part of the apparatus and neither may move while it
  runs.** The final sweep runs a green-baseline gate first, raises on `SIGTERM` so
  `finally` restores, and hashes each file after restoring.

### Residue — what was not audited, and what stays uncertain

- **The e2e and engine tiers were not run** (they need Docker). Nothing in this branch
  emits SQL to an engine that the execution tier does not already run against DuckDB, but
  Postgres and Trino have not seen a cumulative or offset query.
- **`period_agg` is pinned to `FIRST` and its consequence is untested.** Querying a
  month-to-date metric *by month* returns the first day's value under that setting. It is
  MetricFlow's own default and D-056 argues for keeping it; nothing here proves what a
  user expects.
- **Semi-additive plus cumulative compiles, emits and plans.** Probed, not refused, and
  not asserted to be *meaningful*: accumulating a last-value measure over time is a
  question this branch does not answer.
- **A two-clause filter is never executed**, only emitted. That MetricFlow's where-filter
  intersection is an AND is taken from its own model.

### Residue — closed, 2026-09-03

Appended rather than written over the section above, which stands as it was: this log is
append-only, and a residue entry's *original wording* is the evidence for how it read at
the time. Every one of the four turned out to be closable, and two of them were not gaps
in the testing but defects hiding behind it.

- **"The engine tiers were not run."** Closed by
  `tests/engines/test_period_over_period_engines.py`: eight requests — both offset forms,
  both cumulative windows, the period collapse, a string filter, a decimal-and-date
  filter, and a timestamp filter — planned per dialect and executed against real
  PostgreSQL and real Trino, against the DuckDB tier's expectations written once and
  asserted three times. This is the one surface no golden can pin: the query is
  MetricFlow's, rendered per dialect at request time.

  **It found two defects immediately.** Every metric filter on a non-string column was
  broken on Trino — `Cannot apply operator: decimal(12,4) <= varchar(5)` and
  `date <= varchar(10)` — and rescued on the other two only by implicit cast. And an ISO
  timestamp literal carries a `T`, which Trino refuses to cast at all
  (`INVALID_CAST_ARGUMENT`); the audit-bound path had that second one too, pre-existing
  and unexercised, and the fix is now shared by both.

- **"`period_agg` is pinned to `FIRST`."** The pin was the defect — D-060. It reported
  100 on a month totalling 257, and the argument that pinned it deferred to a default
  while removing the key the default belongs to. `period_agg` is authored now and
  defaults to `last`.

- **"Semi-additive plus cumulative compiles, emits and plans."** All three verbs were
  true and the number was garbage: **2707** where the day was 100. Refused — D-059.

- **"A two-clause filter is never executed."** Executed: 257 in March, 207 of it paid,
  100 of it paid *and* on the web channel. An OR would report 257.

What remains uncertain: the engine tier runs those eight requests and not every shape of
them — a derived metric over a *ratio* is planned nowhere but DuckDB — and the audit-bound
half of the ISO-separator fix is corrected but still has no fixture asserting a `min`/`max`
on a timestamp column.

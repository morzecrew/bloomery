# T-0011 · RFC 0034 — metrics over time

Executed on branch `feat/period-over-period`. The whole of RFC 0034: derived metrics,
offsets, cumulative windows and metric filters — the four constructs that made "revenue
vs. the same month last year" unexpressible. The RFC was written and executed in one
change, so it stays live for one more (`rfcs/INDEX.md` says why).

**Drift count: 1.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the RFC's own text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

| Class | Test | Meaning |
| --- | --- | --- |
| `discovery` | Could not have been known before code existed | Healthy — the RFC was right to be silent |
| `spec-gap` | Could have been known; the RFC was silent or at the wrong altitude | The design process missed something |
| `drift` | The RFC covered it and it was built otherwise anyway, **or** a claim was made that was not true when it was made | **A defect** |
| `irreducible` | No amount of design settles it | Stop and spike |


Logged even though the amendment landed in the document rather than in a departure,
because the two are only distinguishable if someone says which happened. **Nothing had
been built when this was noticed** — the RFC was drafted and not yet executed — so
correcting it is drafting, not laundering: the rule the corpus works to is that an RFC's
prose is never edited *to match what was built*, and there was nothing built to match.
A reader diffing this branch will see D13 already saying "at parse", and this entry is
how they can tell that the sentence was rewritten rather than obeyed.

The substance did not change: braces are refused, and the argument for refusing rather
than escaping per target is unaltered. Only the stage moved, and it moved to the stage
whose whole definition it already fitted.

## D-053 — `filter:` is refused on a derived metric

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T18:55:00Z
attempt: 1
claim: §9 lists per-*input* filters as out of scope and is silent on a filter written on the derived metric itself, which MetricFlow does accept
evidence: src/bloomery/guardrails/metrics.py:189
action: decided
proposal: A `filter:` on a `derived:` metric is refused (`InvalidMetricShape`). Filtering a derived metric restricts the measures one level down, not the metric the filter is written on — which is a post-aggregate filter, §9's explicit non-goal.
```

Two arguments, and they agree. The semantic one: MetricFlow applies a derived metric's
`filter` to the measures its inputs aggregate, so `revenue_yoy` filtered to `status =
paid` is not "the year-over-year change in paid revenue restricted afterwards" — it is
the change computed from paid rows, which is a *different metric* and one the author can
write directly by filtering `revenue` and deriving from that. A filter that means
something other than what it reads is the silent-wrongness class this project refuses.

The structural one: D9 checks a filter's dimension against the marts listing the metric
among their measures, and a derived metric need not be listed on any (D4). Checking it
would have meant reaching for the ownership rule, which lives a layer above the
guardrails. Refusing costs nothing an author cannot express another way.

## D-054 — a metric filter names a categorical dimension, never a date role

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T19:05:00Z
attempt: 1
claim: D8 says a filter is `{dimension, op, values}` and says nothing about which dimensions are filterable
evidence: src/bloomery/guardrails/metrics.py:114
action: decided
proposal: A metric filter's dimension must be a categorical dimension of the mart; a date-role bucket is refused with a message routing to `cumulative:` and `offset:`.
```

Found by building the renderer. A date-role dimension is not spelled `{entity}__{column}`
in a MetricFlow where-filter — it is `{entity}__{role}_day__{grain}`, and that rule lives
in `planner/names.group_by_name`, in a layer above the emitter. Emitting a filter on
`sold_month` would have needed either a second spelling of that rule in `emit/` or an
inverted import.

Refusing is not a workaround for that, though: a metric restricted to one period is a
*constant*, and the two constructs this RFC adds are exactly how a time relation is
expressed instead. The layering made the question visible; the semantics answered it.

## D-055 — Cube refuses by existence, not per mart

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-09-02T19:20:00Z
attempt: 1
claim: D11 says Cube "refuses derived and cumulative metrics per construct with UnsupportedByTarget" and does not say what triggers the refusal
evidence: src/bloomery/emit/cube/__init__.py:328
action: decided
proposal: The refusal fires when such a metric *exists in the project*, not when a mart names it in `measures:`.
```

Cited as `unlisted` rather than against D11: that row settles *what* is refused and is
silent on *when*, and the trigger is the part that had to be decided. Nothing here
departs from D11 — it answers a question D11 does not ask.

The existing Cube precedent tests `for name in owned`, i.e. metrics a mart names. That
cannot work here: RFC 0034 D4 says a derived metric need not appear in any mart's
`measures:` at all, so the per-mart test would let the common spelling through and Cube
would emit a complete-looking model quietly missing the metric. A missing metric is an
approximation of the metric set, and RFC 0008 D3 says fail loud rather than approximate.

The cost is real and worth stating: a project carrying one derived metric cannot emit
Cube at all. That is the same shape as `semi_additive: {rule: avg}`, which makes a whole
manifest unemittable on MetricFlow today — so the asymmetry is symmetric, and the message
names the construct and where the metric does live.

## D-056 — `period_agg` is pinned to MetricFlow's own default

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-02T19:30:00Z
attempt: 1
claim: the RFC does not mention `period_agg`, which decides what a cumulative metric means when the request asks for a grain coarser than the accumulation
evidence: src/bloomery/emit/metricflow/__init__.py:665
action: decided
proposal: Pin `PeriodAggregation.FIRST` explicitly — MetricFlow's own default — rather than leaving it implicit or choosing differently.
```

Found by reading `PydanticCumulativeTypeParams`: it is the one field there with a
non-`None` default. Month-to-date revenue queried *by month* under `FIRST` reports the
first day's value, which reads as surprising, and `LAST` is arguably what a person means.
Pinning `LAST` would make bloomery's cumulative metrics mean something different from
every other MetricFlow and dbt project's, which is a worse surprise and a silent one.
Pinned explicitly rather than defaulted, so the choice is visible where it is made, and
the emitter's own convention — every optional field written out — is kept.

## D-057 — §8's "nothing else in the planner changes" was false

```divergence
decision: RFC 0034 §8
grade: LOCKED
class: drift
at: 2026-09-02T19:40:00Z
attempt: 1
claim: §8 says "Nothing else in the planner changes", having checked `_measure_type` and generalized from it
evidence: src/bloomery/planner/explain.py:152
action: halted
proposal: §8 should have named `explain.py`. `_measure_explanation` raises `PlannerError` for a non-additive metric with no ratio, so every derived-metric plan failed there until it grew a branch.
```

`halted` rather than `departed`, and the distinction is the whole content of this entry:
nothing in §8 was flipped. §8 described the blast radius and described it wrongly; the
implementation did what the RFC intended and this proposes the correction to the text.

**The drift, and it is a claim rather than an implementation.** The check behind the
sentence was real — `_measure_type` does answer `decimal(38,9)` for a non-additive metric
— and the sentence generalized from one function to a package. `explain.py` was one grep
away: it reads `metric.ratio` and refuses when it is `None`, which is precisely what a
derived metric is.

It failed loudly rather than silently, which is luck rather than design: the first
`revenue_yoy` plan raised `PlannerError: non-additive metric 'revenue_yoy' has no ratio`.
The rule worth keeping is the one that has now cost twice: **a claim of the form "nothing
else changes" is a search, not an inference.** The previous branch's version of it was
"the fingerprints that matter are the ones that did not move".

Two more things came out of fixing it, neither of which the RFC asked for and both of
which belong to the same argument. A cumulative metric explained as `additive — SUM`
describes a metric that aggregates per period, which is the exact wrong number
`cumulative:` exists to prevent; and a filtered metric explained as its unfiltered sibling
is a number the reader has no way to question. Both now say what they are.

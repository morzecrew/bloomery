## D-070 — what "every mapping" has to range over

```divergence
decision: RFC 0024 D36
grade: ASSUMED
class: spec-gap
at: 2026-09-03T17:40:00Z
attempt: 1
claim: D36 says `direct:` is allowed "when **every** mapping records one for the column", and taken literally that refuses the shape §5.2 rule 3 exists to allow — a mapping that does not map the field at all has no field mapping to hang a `direct:` on, so the requirement is unsatisfiable rather than merely unmet
evidence: src/bloomery/resolve/build.py:1338-1345
action: departed
proposal: the requirement ranges over the mappings that **produce** the column, not over every mapping of the entity — the same scoping D33's rule agreement already uses, for the same reason and in the same words
```

- **Touches:** RFC 0024 D36 (`ASSUMED`) — departed under the grade's own licence, and the
  departure is narrowing rather than widening: every shape D36 admits is still admitted.
- **RFC said:** "`direct:` is allowed on a merged entity when **every** mapping records one
  for the column, and refused when they disagree."
- **Built:** among the mappings that produce the column, all record a path or none does.
  A mapping that does not map the field is not consulted.
- **Because:** §5.2 rule 3 lets a source omit an optional field, and the merge NULL-fills
  it for that source's rows. Such a mapping derives nothing for the column, so there is
  nothing for a shadow to disagree with — and `direct:` is a key of a *field mapping*, so
  the fix the literal reading would demand cannot be written. D33 met this exact case one
  decision earlier and answered it the same way; D36's consequence ("disagreement is
  refused by D33's pattern") is what points at the answer, and its prose is one clause
  short of stating it.
- **Why `spec-gap`:** `_rules_over` and `_produced` were written for D33 and are on the
  screen above D36's own refusal. Nothing about the code was needed to see it.

## D-071 — one shadow, N projections, and the arity nothing named

```divergence
decision: UNLISTED — the arity of the path-conflict amendment on a merged entity
grade: UNLISTED
class: discovery
at: 2026-09-03T17:10:00Z
attempt: 1
claim: `path_conflict_amendments` appends per *derivation*, and a merged entity has one derivation per mapping for the same field — so the fan-out D36 asks for is not "return a list instead of a pair", it is a regrouping, or the entity gets two columns of one name and the reconcile audit twice
evidence: src/bloomery/guardrails/conflict.py:118-140
action: decided
proposal: ASSUMED — the amendment is grouped by `(entity, field)` into a `Shadow` carrying one `ColumnIR` and a projection per source relation; the reconcile audit is emitted once per field, and `guardrails.stage` reads each branch's own projection by relation
```

- **Touches:** nothing stated — D36 names `Derivation` carrying its source and
  `path_conflict_amendments` fanning out "per source, exactly as `_column_pair` does", and
  is silent on the grouping that makes those two compatible.
- **Built:** a frozen `Shadow(column, projections)`, one per `(entity, field)`.
- **Because:** `_column_pair` is called once per mapping *from inside a per-mapping loop*
  that appends to that mapping's own projection list, so "exactly as `_column_pair` does"
  does not transfer to a function iterating derivations across every mapping of an entity.
  The schema half is per entity — a merged entity's columns are what every mapping agrees
  on (D26) — and only the lowering is per source. Appending both per derivation would put
  two `net_price__direct` columns on one entity and two identical reconcile audits, which
  is the two-writers-at-one-path shape D8 refuses for relations and which an entity's
  schema cannot express at all.
- **Why `discovery`:** the mismatch is in how the two functions are *called*, not in what
  either says. It needed the call sites side by side.

## RFC 0036 — executed without a divergence

No entry above covers RFC 0036 because building it turned up nothing its document did not
already say. Two things are worth recording as prose, both of them confirmations rather
than departures:

- **D3's single site held.** The guard went into `strip_iso_text` and every port carried it
  with no port-side edit, which is what D3 claims. The claim was checkable before the code
  existed and is now measured: three ports, three renderings, one function.
- **D5's detection window survived the corpus.** `SUBSTRING(x, 11)` plus two `LIKE`s was
  chosen for portability, not for precision, so the risk was a false refusal. Swept over
  the `dirty` corpus's twenty-one date specimens it moved exactly one disposition —
  `offset_positive`, which is the specimen this exists for — and the corpus's own note had
  recorded the question and asserted the answer that was wrong.

## Self-audit findings — 2026-09-03

Adversarial pass over the whole branch (3 commits, 71 files, +2678−645; source is 5 files
and +266−67). Scope walked: RFC 0036 §5 and its decision table, RFC 0024 D28/D33/D36, the
three source diffs, the docs, and the retirement. Ranked by severity; findings the
executor did not notice, filed apart from the departures above.

### F-1 — the offset guard would not compile the one audit it most had to reach (fixed)

`_without_offset` took its window over the marked operand raw: `SUBSTRING(x, 11)`. The
marker has two callers, and only one of them hands it a transform chain. The other is
RFC 0016 D21's metadata audit, which puts it on `_ingested_at` — a bronze column, typed
however the project landed it. Measured on DuckDB against a real `TIMESTAMP` column:

```
Binder Error: No function matches the given name and argument types
'substring(TIMESTAMP, INTEGER_LITERAL)'
```

So the guard did not refuse a value, it refused to **compile the audit** — on the one
column no `coercible` rule can reach, which is why D21 generates an audit for it at all.
The Trino port had already bought exactly this totality with the `CAST(… AS VARCHAR)`
before its `replace`, and pinned it in a test whose docstring names the same shape; a
guard one node above it undid that. Fixed by casting inside the guard, pinned per port in
`tests/unit/test_dialects/test_base.py` and executed on DuckDB in
`tests/execution/test_zoneless_utc.py`. RFC 0036 gains D7, since D5 spelled the predicate
without the cast.

**Found by the discipline pass**, not by the tests: every tier was green, because every
test of the guard passed it an untyped `exp.column`.

### F-2 — `InvariantViolated` on a legal spec (fixed)

A merged entity where one mapping records `direct:` for an optional field and another does
not map that field at all is legal — D-070 above is the decision that keeps it legal — and
it raised:

```
InvariantViolated: expected a 'kind__direct' projection for source 'src_z' of entity
'event' … This is a bug in bloomery, not in the spec
```

The refusal correctly did not fire, and nothing filled the branch, so `guardrails.stage`
looked up a projection that was never built. Fixed by `_fill`, which gives such a branch
the typed NULL the builder's `_filled` already gives it for the derived column: the shadow
is NULL beside a derived value that is also NULL, and `IS DISTINCT FROM` reports nothing —
the true statement about those rows. Verified red before the fix.

**The shape is worth naming**: the refusal and the amendment were written from the same
sentence of D36 and *scoped differently* — one to the mappings that produce the column,
the other to every source of the entity. Two readers of one decision, and the gap between
them is where the crash lived.

### F-3 — DuckDB's plain `CAST` raises on a lowercase `t` (open, pre-existing)

Measured while writing the execution test:

```
CAST('2026-01-06t12:00:00' AS TIMESTAMP)      -> Conversion Error: invalid timestamp field
TRY_CAST('2026-01-06t12:00:00' AS TIMESTAMP)  -> NULL
```

ISO 8601 permits the lowercase separator, PostgreSQL and Trino both read it, and the
previous branch fixed Trino on the stated ground that "the other two ports already accept
it". DuckDB accepts it only under `TRY_CAST` — so on a quality-carrying entity it is a
quarantined row and on a bare entity `parse_ts: ISO8601` **aborts the run**. Untouched
here: it is RFC 0027's separator question, not RFC 0036's offset one, and fixing it moves
every DuckDB golden. Recorded in the new test's docstring so the gap is visible where
someone would otherwise add the row back.

### F-4 — the `__direct` shadow is a hard cast on a quality-carrying entity (open, pre-existing)

Measured, not read:

```
item_id            TRY_CAST(id AS TEXT)
net_price          TRY_CAST(total / qty AS DECIMAL(12, 4))
net_price__direct  CAST(price AS DECIMAL(12, 4))
```

An entity in the quality system lowers every mapped column NULL-on-failure so `coercible`
can see the failure. The shadow does not: `guardrails.conflict` has always built it with a
plain `exp.cast`, on `main` as here. So a `direct:` path whose value does not cast aborts
the run on an entity whose whole point is that bad values are routed rather than fatal.

Pre-existing and untested — no fixture combines `direct:` with `quality:`, which is why
nothing has caught it. **Not fixed here**, and that is a scope call rather than a
judgement that it is fine: it is an RFC 0006 × RFC 0016 interaction neither RFC 0036 nor
D36 decided, and this branch would be changing emitted SQL for a shape it did not come to
build. It is cheap — the guardrail stage has the entity and `entity.quality` says whether
it opted in — and it is now reachable on merged entities too, which is what makes it worth
raising rather than leaving in the code.

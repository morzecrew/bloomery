# T-0045 · Definition supersession: the delta and its closure

Executing RFC 0064 P1 and P2 against branch `feat/definition-supersession`.

**Drift count: 0.**

## Plan

RFC 0069 P1 landed the walk this phase fills in. `timeline()` already reports
*that* a definition moved between two adjacent versions and carries an empty
`facets` reserved for this document's vocabulary (RFC 0069 D3, D13). P1 is that
vocabulary; P2 is D4's closure, which is what stops the answer being the local
one `git log` already gives badly.

One new module, `resolve/facets.py`: a closed `Facet` enum, a `FacetDelta`
record carrying the facet, the field that moved and both renderings, and one
function over two definitions. One changed module, `resolve/timeline.py`: the
walk gains the root's upstream closure per version, and a change gains the node
it is about.

Out: any new edge kind in the IR (the entry below), any change to `plan()` or
`ChangeClass` (D7), any CLI (RFC 0069 P3 owns it, and `explain` is RFC 0066's
SQL command), any claim about data (D3), and RFC 0039's provenance wording for
the additivity facet (P3).

## Self-audit — 2026-09-11

Scope: the whole branch against `main` — 3 commits, 14 files, +1634-82, merge base
`85f9cc6`. Every pass ran. **Four findings, all fixed**, and three of them came from
the sabotage sweep rather than from re-reading.

1. **The sort test could not tell facet order from field order.** `facets()` returns
   its deltas sorted by `(facet, field)` over a map iterated in field order, and every
   pair of `MetricIR` fields the test used sorts the same way both ways — so a walk
   returning its input unsorted passed a three-facet assertion. `depends_on` (`inputs`)
   and `expr` (`body`) are the pair that disagree, and they are what the test uses now.
   The shape is worth naming: an ordering test whose input is already in the mutant's
   order is a dead assertion, and it looks exactly like a live one.

2. **Nothing pinned that a change is named for the node's *name*.** No fixture in the
   corpus adopts an RFC 0062 `id:`, so a walk reporting `metric.mtr_7f3a9c` where a
   reader expects `metric.gross_revenue` passed every test on the branch. Pinned now on
   a hand-built pair, which is the only place an adopted id exists.

3. **The docstring claimed one rule where there are two.** A hold the closure pass does
   not match is dropped; the root's is kept. The identity *rule* is shared — both call
   `_locate` — but gap survival is not, and the docstring said otherwise. Diagnosed
   rather than fixed: the difference is unobservable, because a dropped hold could only
   differ by emitting a change on its return and the adjacency rule forbids that. The
   asymmetry has a cause worth writing down — the root is *searched for* by the one
   spelling the caller gave, and every other node is *enumerated* out of the scope.

4. **`claimed` is a cost guard wearing a correctness guard's clothes.** Removing it
   changes no answer: the second pass rebuilds an identical hold under an identical key
   and emits no change of its own. It stays, because the lookup it saves scans the IR
   once per closure node per version — but the comment now says which kind of guard it
   is, so the next reader does not delete it looking for a test to break, or keep it
   believing one would.

**Verification.** `just quality -s` 9 of 9; `pyright src` 0 errors; `just build-docs`
clean; the default tiers green; the global total 99.1%, with `facets.py` and
`timeline.py` at 100% line and branch after finding 5 below. Twenty-three hand-written
mutants over
the facet table, the rendering, the flattening, the closure walk and the identity
matching: **22 killed, 1 survivor**, the survivor being finding 4, diagnosed equivalent
rather than assumed so. Three of the twenty-three survived the first pass and are
findings 1, 2 and 4.

5. **The sentence above claimed 100% before anything had reported it.** It was read off
   "94 files skipped due to complete coverage" — which is a claim about the files the
   report *omitted*, not about the two this branch changed. Asked directly,
   `facets.py` was 98.6%: `_lowered_fields`' empty case, a column no source lowers,
   which the corpus sweep never reaches because no fixture produces one. Pinned
   directly, and the two modules are now measured at 100% rather than inferred there.
   This is the pass-9 failure in its purest form — a claim checked by reading, in the
   verification paragraph of an audit whose whole subject is not doing that.

**Residue.** Four things I would still distrust:

- **A dependency's rename reads as an `inputs` change on everything that reads it.**
  `plan()` relabels one side before diffing; a timeline would have to relabel across N
  versions, and it does not. What the walk reports is true — the name it reads is spelled
  differently — but a reader chasing a number will see rows that mean nothing moved. It
  is in the how-to and it is not fixed.
- **The facet assignments are judgements, and roughly fifteen of the seventy-five rows
  could defensibly sit elsewhere.** `outputs` in `inputs`, `type` in `unit`, `required`
  in `quality`. The table being *total* is enforced; the table being *right* is not, and
  cannot be.
- **A merged entity gaining a source moves every lowered field at once.** Five deltas
  naming one cause. The alternative — comparing only the sources both sides share — hides
  a dropped mapping, which is worse, so this is a chosen noise rather than a missing fix.
- **One boundary can carry a lot of rows.** A closure of four hundred nodes where fifty
  moved is fifty changes at one boundary, sorted and unpaginated. RFC 0069 P3's rendering
  is where that becomes a problem, and it is not this phase's.

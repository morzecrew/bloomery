## D-153 — the waiver D3 replaces was deleted before D3 was written

```divergence
decision: RFC 0038 D3 — units participate in type checking; currency becomes a proof-producing rule rather than a waiver
grade: LOCKED
class: spec-gap
at: 2026-09-06T23:05:00Z
attempt: 1
claim: D3's stated reason is that "a waiver and a proof are indistinguishable at the call site". There is no waiver. RFC 0023 D5 removed the `CONVERT_CURRENCY` marker that used to permit mixed-currency arithmetic, and the arithmetic guard's own docstring records why — it "bought a compile-time pass that asserted nothing about the value". What stands in its place is not a waiver and not a proof: after conversion both operands declare one currency, and two operands in one currency were never a violation. So the thing D3 asks to be replaced is already gone, and what replaced it is a declaration the guard reads rather than a suppression it honours
evidence: src/bloomery/guardrails/arithmetic.py:14-23
action: halted
proposal: D3 is superseded by a row that says what is true of the tree — the mixed-currency refusal is unconditional and unwaivable, and what is missing is not a proof replacing a waiver but a fact the spec language cannot yet express (D-155)
```

## D-154 — the checkable half of a conversion is already checked

```divergence
decision: RFC 0038 D3 — currency becomes a proof-producing rule
grade: LOCKED
class: discovery
at: 2026-09-06T23:15:00Z
attempt: 1
claim: `{convert: [<from>, <to>, <anchor>]}` makes two assertions, and resolution already refuses one of them. A chain whose `to` disagrees with the column's declared currency is a `ResolutionError` before any guardrail runs. So a rule proving "this column is in the currency the catalog declares" would re-derive a refusal that exists, at a later stage, with no new obligation discharged
evidence: `uv run python scratchpad/probe_ccy.py` -> "honest EUR->USD under currency: USD: COMPILED CLEAN" / "LYING EUR->GBP under currency: USD: refused -> ResolutionError: convert produces 'GBP' but column 'amount_usd' is declared 'USD' in the catalog"
action: halted
proposal: any R009 must name an obligation neither `resolve/build.py:2320` nor the arithmetic guard already discharges. On the evidence below there is one, and it is not provable under the current spec language
```

## D-155 — the unchecked half has no fact to be checked against

```divergence
decision: RFC 0038 D3 — currency becomes a proof-producing rule
grade: LOCKED
class: irreducible
at: 2026-09-06T23:25:00Z
attempt: 1
claim: the `from` argument is an authored claim about the column's *input*, and nothing verifies it. Declaring `{convert: [JPY, USD, paid_at]}` on a column whose values are euros compiles clean and applies the yen rate to euros — a plausible wrong number, which is the class this project exists to refuse. It cannot be proven or refuted, because `currency:` is declarable only on a canonical field and a mapping's `from:` is a JSON path into bronze that declares nothing. There is no fact in the system for the claim to be checked against, so no rule RFC 0039 permits can close it: `DECLARED` is the strongest provenance available and a proof whose only leaf is the assertion under test restates it rather than discharging it
evidence: `uv run python scratchpad/probe_ccy.py` -> "LYING JPY->USD under currency: USD: COMPILED CLEAN"; `grep -n currency src/bloomery/spec/catalog.py` -> 63, 65 (canonical fields only), and no hit in `spec/sources.py` or `spec/mapping.py`
action: halted
proposal: making this provable is a spec change before it is a proof rule — a source column able to declare its currency, so the conversion's input has a declared fact to agree with. That is RFC 0038 §3's "origin" question wearing a different hat and is bigger than "add a rule"; it needs a row of its own, or its own document
```

## D-156 — D3's unit clause names a route that does not exist

```divergence
decision: RFC 0038 D3 — units participate in type checking; incompatible arithmetic is refused without an explicit declared conversion
grade: LOCKED
class: spec-gap
at: 2026-09-06T23:35:00Z
attempt: 1
claim: §5 gives `Distance<km> + Distance<m> -> refusal or explicit conversion` alongside the currency case, and the clause reads on both. There is no unit conversion: `convert` is currency-only by signature and by its `fx_rates:` backing, and `Unit` is a two-member enum — `currency` and `count`. So for units the decision has only its refusal half, and "without an explicit declared conversion" names a thing an author cannot write
evidence: src/bloomery/transforms/_builtins.py:799-806
action: halted
proposal: either D3's unit clause is scoped to the refusal it already has, or a declared unit conversion is designed — a dimension system with declared factors, which is a document rather than a row
```

## Citations corrected — 2026-09-07

Appended, not edited: T-0024's entries stand as written. Two statements in them are no
longer true of the tree they ship in, and one was not true when it was made.

**D-155's evidence read a failed command as a negative result.** It cites
`grep -n currency src/bloomery/spec/catalog.py -> 63, 65 (canonical fields only), and no hit
in spec/sources.py or spec/mapping.py`. There is no `src/bloomery/spec/sources.py` — the
grep that produced "no hit" for it exited with *No such file or directory*, and an error was
read as an answer. The claim D-155 makes is still right, and the way it was evidenced was
not: what shows a source path declares no currency is that the *mapping* and *entity*
schemas carry no such key **at the commit the halt was called on**. Two numbers, because
one cannot say it: `git show 03d3ade:src/bloomery/spec/mapping.py | wc -l` returns `256`
and `... | grep -c currency` returns `0`. The second alone is worthless — a `git show`
against a commit that is not there prints nothing, `grep -c` counts an empty stream and
also says `0`, so the count cannot distinguish "no such key" from "no such commit". That is
the same error this section is correcting, and it took a reviewer to see it here. The line
count is what makes the zero mean something.

`03d3ade` is reachable from the mainline — `git merge-base --is-ancestor 03d3ade
origin/main` succeeds — so the reference survives this branch merging, which a base SHA on a
squash-merged branch would not.

Pinned rather than run against the tree, because the branch this ships in adds
`currency_in` to that very file: `grep -c currency src/bloomery/spec/mapping.py` now
returns `7`, which is the halt working rather than the claim failing. This is the same failure as T-0023's D-149, a command's output answering a
different question than the sentence quoting it.

**And the unpinned form of that locator was itself the fourth instance**, written into the
correction for the third — see `logs/T-0025.md`'s corrections section. A rule read and
reasoned around four times, once inside its own repair, is not a rule: the check it needs is
that an entry whose `proposal` edits the file its `evidence` names cites that file at a
commit.

**The readiness gate's last bullet is stale, by this PR's own work.** It says corpus case
004's converted arm pins `"rule": "RFC 0023 D11"`, which was true at `03d3ade` and is not
now: `rg -n '"rule"' tests/fixtures/semantic_corpus/004-currency-mix/expected/` returns
`R009` for `converted` and for the `mislabelled` arm this PR added, and `RFC 0006 D4` for
`mixed`. The halt argued that no rule id existed to point at; RFC 0061 minted one, which is
what the halt asked for. Both statements are historical and correct as history.

**`src/bloomery/spec/mapping.py` now declares `currency_in`** — `rg -n currency_in
src/bloomery/spec/mapping.py` — so D-155's "the input side of a conversion has no
declaration anywhere in the spec language" describes the tree the halt was called on, not
the tree it ships in. That is the halt working: the entry names the gap and the branch that
ships beside it fills it.

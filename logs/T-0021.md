## D-117 — a group-by grain is not a grain, and does not need to be

```divergence
decision: RFC 0040 §5 — Aggregate(input_grain=Order, output_grain=CustomerCountry)
grade: UNLISTED
class: spec-gap
at: 2026-09-05T20:10:00Z
attempt: 1
claim: §5's accepted example names an output grain of `CustomerCountry`, and RFC 0037's GrainRef is key identity — `country` is not part of `customer`'s key, so `can_roll_up` refuses that target as `unknown_grain`. Taken literally the example needs vocabulary RFC 0037 does not have; taken as RFC 0039 §7 renders the same argument, it needs none: prove the rollup to the dimension's *key* grain and the column is determined by that key, which is step 3 of that worked example
evidence: `uv run python -c "...can_roll_up(grain('order','order_id'), grain('customer','country'), CORPUS)"` -> `RollupRefusal unknown_grain`, while the key-grain question returns `RollupProof` and `ColumnRef('customer','country')` is in its closure
action: decided
proposal: §5's `output_grain` is a *display* name for "the target key grain, projected to these columns", and §4's Aggregate carries the key grain plus the projected columns rather than a grain that does not exist. No new vocabulary; RFC 0037's GrainRef stays identity-only, which is what D1 there locks
```

## D-120 — "beside" makes the proof vocabulary public API

```divergence
decision: RFC 0040 D7 — whether SemanticPlan lowers to the existing QueryPlan, replaces it, or sits beside it
grade: OPEN
class: discovery
at: 2026-09-05T21:05:00Z
attempt: 2
claim: D-118 chose "beside" on migration grounds and the choice has a consequence neither the RFC nor that entry saw — a field on `QueryPlan` is a public signature, so the closure check requires every type reachable through it to be exported from the top-level package. Attaching the plan therefore promotes RFC 0039's whole vocabulary — `SemanticPlan`, `PlanNode`, `Proof`, `SemanticFact`, `SemanticJudgement` — from `bloomery.semantic` to `bloomery`, which is a wider API surface than P1 sounds like it should own
evidence: `uv run pytest tests/unit/test_signature_closure.py -q` -> `AssertionError: not exported from bloomery: PlanNode (via SemanticPlan.nodes), Proof (via Proof.premises, SemanticPlan.proofs), SemanticFact (via Proof.facts, Proof.leaves), SemanticJudgement (via Proof.conclusion), SemanticPlan (via QueryPlan.semantic)`
action: decided
proposal: D7's "beside" is kept and the promotion accepted rather than worked around. The alternative — an opaque handle, or the plan reachable only through a method — would hide the value RFC 0040 §6 exists to hand to target adapters, and a plan a caller cannot destructure is a plan they cannot lower. D7 gains a sentence: choosing "beside" publishes the plan vocabulary, which is a decision about API surface and not only about migration
```

- Worth recording because the closure check found it rather than the design: an executor
  reading D7's three options would not see that one of them widens the public API, and the
  next phase's author choosing between "lowers to" and "replaces" now has that on the table.

## Findings — self-audit, 2026-09-05

Scope: the whole branch, 4 commits, 12 files, +989/−9 — source, tests, the determinism
guard, the package surface and this log. Gates re-run after every fix.

### 1 — nothing consumes the plan, and the module said the opposite

`grep -rn "\.semantic\b" src/bloomery/` returns exactly one line: the construction site.
MetricFlow still plans from the request, so the plan is built beside the SQL and read by
nobody — which is correct for P1 and is **not** what the module docstring implied when it
said §6 asks for "bloomery decides, targets lower" and "this is the value it decides into".
A reader would reasonably take a plan's presence as evidence it produced the query beside it.

Now stated, and pinned: a test asserts structurally that no module reads the plan, since
being unread is precisely why P1 changes nothing and there is therefore no behaviour to
observe. Verified red by adding a reader.

### 2 — an empty plan constructed and reported itself valid

`SemanticPlan(())` passed `check`, because an empty sequence satisfies "every multiplying
node carries a proof" perfectly. A plan with no nodes computes nothing, so the empty case is
decided now rather than inherited from the reduction — the same shape as `Proof.closed`
returning `True` for a proof resting on no facts, one branch earlier.

### 3 — a field comment describing a case that cannot arise

`Aggregate.proof` was documented as `None` "only where the input and output grain are the
same relation and nothing was rolled up" — which is every P1 aggregate, all of which do
carry a proof. It now says what is true: optional on the type, always present on what the
builder produces.

### What I would still distrust

- **The parity suite's refusal side is thin where it matters most.** 76 of its 108 refusals
  are one fixture failing wholesale, so what varies by request shape is 32 across three
  classes. Strong against a phase that changes an outcome; weak against one that changes a
  reason, which is what P2 will mostly do.
- **D2 is vacuous and D4 unenforceable at P1**, both by construction rather than by
  oversight, and both now carry canaries that fail when P2 makes them real.
- **R008 is asserted, not derived.** It cites the mart contract that `check_grain` enforces
  at compile time, and nothing here re-checks it: if that guardrail were wrong, the proof
  would faithfully report the wrong thing.

## D-026 — `BOTH` carries the edges the walks traversed, not the induced subgraph

```divergence
decision: RFC 0031 D4
grade: OPEN
class: discovery
at: 2026-08-27T09:41:29Z
attempt: 1
claim: D4 says the renderer settles BOTH's shape, and having built the renderer it does not — an edge list draws a merged sub-DAG perfectly well, because each edge carries its direction in src to dst. What actually decides it is that an induced subgraph over the union of the two walks contains edges neither walk traversed
evidence: `base -> mid`, `mid -> top`, `base -> top` over metric.mid — the two walks traverse {(base,mid),(mid,top)}; inducing over their union adds (base,top), an edge that does not touch the root at all
action: decided
proposal: LOCKED — `Direction.BOTH` returns one `Lineage` whose `nodes` and `edges` are the union of the upstream and downstream walks' results. `direction` records `BOTH`. The rule is "edges some walk traversed"; for one direction that is the induced subgraph, and for `BOTH` it is not
```

- **Touches:** RFC 0031 D4 (`OPEN`), §5.1's `edges` contract
- **RFC said:** merged or a pair, "settled by whoever builds that renderer" — because a
  tree drawn from a merged DAG "has no root direction".
- **Built:** one merged `Lineage`, edges from the walks.
- **Because:** D4's stated tiebreaker is void. It assumed a *tree*, and
  [`T-0005`](T-0005.md) D-019 replaced the tree with a deterministic edge list before this
  phase began — an edge list needs no root direction, so the renderer stopped forcing an
  answer. The ground that does decide it is the bypass edge: with `base → mid`,
  `mid → top` **and** `base → top`, the union of the two walks from `mid` is
  `{(base,mid), (mid,top)}`, while inducing over the same node set adds `(base,top)` — an
  edge that touches neither the root nor any walk, and would make a caller counting
  `mid`'s connections wrong. The shape is reachable: `requires_metrics` is metric → metric,
  so a composed metric requiring both an intermediate and what that intermediate requires
  produces exactly it.
- **Not an inconsistency with P1:** measured over a diamond, a chain and the bypass graph,
  in both directions, from every node — for a **single** direction the induced subgraph and
  the walked edges are the same set. Every edge between two ancestors of X lies on some
  path to X, so the walk reaches it. P1 implemented the rule as "induced" because the two
  coincide; `BOTH` is the case that reveals which rule was meant. This entry changes no P1
  behaviour and adds no field.
- **Consequence:** `Lineage.edges` stops being expressible as "every graph edge whose
  endpoints are both carried", which is how §5.1 words it. The wording holds for the two
  directional cases and is wrong for `BOTH`; the proposal above restates it once for all
  three.

## D-027 — the CLI follows the shipped convention, not §5.5's sketch

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-27T09:41:29Z
attempt: 1
claim: §5.5 sketches `-d DIR` and `--format text|json`, and neither exists on this command line — every subcommand takes `directory` as a positional through `_add_spec_directory`, and `_add_format` offers `table|json`. Following the sketch would make `lineage` the only one of seven commands shaped differently
evidence: src/bloomery/cli/__init__.py:341
action: decided
proposal: ASSUMED — `bloomery lineage <dir> --node <id> [--direction upstream|downstream|both] [--max-depth N] [--catalog F] [--format table|json]`. The spec directory is positional and the format vocabulary is `table|json`, as on every other command; the node is a flag because that is how `explain` names its subject
```

- **Touches:** RFC 0031 §5.5; no decision row covers the CLI's shape
- **RFC said:** `bloomery lineage <node-id> [--direction …] [--max-depth N]
  [--format text|json] [-d DIR] [--catalog PATH]`.
- **Built:** the convention's shape.
- **Because:** §5.5 was written against the *idea* of the command line rather than against
  `build_parser`. Three details are wrong at once — the directory's form, the format
  vocabulary, and the subject's position — and each would be a small surprise on its own;
  together they would make one command read like it came from a different tool. `explain`
  is the closest sibling (a directory plus a subject plus options) and it spells the
  subject `--metrics`, so `--node` matches the one command this most resembles.
- **Consequence:** a reader following §5.5 literally will type a command that does not
  parse. The document is not retired by this task, so §5.5 should take the proposed row.

## D-028 — near misses are `difflib` matches, capped and ordered

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-27T09:41:29Z
attempt: 1
claim: §5.5 requires an unknown id to be refused with "the near misses" and never says how they are chosen, how many, or in what order — and the message reaches stdout, so an unordered or unbounded list would break RFC 0003's same-input-same-bytes rule for the one output a user reads most
evidence: rfcs/0031-lineage.md:333
action: decided
proposal: ASSUMED — near misses are `difflib.get_close_matches(id, [n.name for n in graph.nodes], n=5, cutoff=0.6)`, emitted in the order it returns, which is by descending similarity and deterministic for a fixed input. Where it finds none, the refusal lists the node *kinds* present instead, so the reader learns the id scheme rather than reading "not found"
```

- **Touches:** RFC 0031 §5.5; no decision row covers the refusal's content
- **RFC said:** that the ids "are long, dotted and easy to mistype, and the graph is right
  there to search" — the *motivation*, with no mechanism.
- **Built:** the `difflib` form above.
- **Because:** the failure this refusal exists for is a typo, and `difflib`'s ratio is the
  standard answer for a typo over a known vocabulary; it is in the standard library, so it
  adds no dependency to a package whose install surface is deliberately small. The cap and
  the fixed cutoff are what make it deterministic **and** bounded — a graph with two
  thousand nodes must not print two thousand suggestions.
- **On the empty case:** a cutoff means "no suggestions" is reachable, and a bare
  "not found" would then be exactly the unhelpful message §5.5 is arguing against. Listing
  the kinds present is the fallback that still teaches the scheme — the reader learns that
  ids look like `metric.…`, `canonical.…`, or an unprefixed `<entity>.<field>`.
- **Consequence:** the refusal's text is asserted by test for both branches, since the
  empty one is the branch a happy-path check never reaches.

## D-029 — a bounded walk dropped edges between carried nodes

Found by patch coverage after the code was written, not by the sabotage sweep.

```divergence
decision: unlisted
grade: UNLISTED
class: drift
at: 2026-08-27T09:56:32Z
attempt: 1
claim: the P2 restructure returned on the *first* boundary edge whose far end was unseen, so any edge joining two carried nodes that had not yet been examined was dropped — the value then carried nodes it showed no connection between, and the same shape answered differently under different node names
evidence: src/bloomery/resolve/lineage.py:174
action: decided
proposal: ASSUMED — a bounded walk examines every boundary edge: those whose far end is already carried join the answer, and any that escapes sets `truncated`. The bound cuts the walk, never the sub-DAG
```

- **Touches:** RFC 0031 §5.1's depth boundary and D3; no row covers the interaction
- **RFC said:** `max_depth=N` carries "every edge whose *both* endpoints are included",
  and `truncated` is true "iff at least one edge was dropped for depth". Both hold; the
  code stopped implementing the first.
- **Built, then rebuilt:** P1 computed `edges` by filtering `graph.edges` over the carried
  set, which is complete by construction. D-026's restructure changed the rule to "edges
  the walk traversed" — correct, and it moved the boundary case into a loop that
  `return`ed as soon as it found an escaping edge.
- **Reproduced before fixing:** with `a → x`, `b → x`, `a → b` and `z → a`, walking
  upstream from `x` at `max_depth=1` carries `a`, `b` and `x` — and dropped `a → b`,
  because `a` sorts first, so the escaping `z → a` was examined before the internal edge.
  Reversing the names keeps it. An answer that depends on node names is not an answer.
- **Why `drift`:** the RFC covered this and it was built otherwise. §5.1 states the edge
  rule in one sentence and the restructure stopped satisfying it — no gap, no discovery,
  just a regression introduced while making a different case right.
- **Why the sabotage sweep missed it:** seven mutations, six killed, and none of them was
  *this* — the sweep only probes what its author thought to break, so a clean sweep
  measures imagination rather than tests. Patch coverage named the uncovered line
  (`crossed.add` at the boundary) and the reproduction followed from asking why it was
  unreachable. **Sabotage and coverage are not substitutes, and this is the instance.**
- **Consequence:** the `truncated` flag is now computed over the whole boundary rather
  than short-circuited, so a bounded walk costs one full pass over the frontier's edges
  instead of stopping early. That is the correct trade — the early return was buying
  nothing but the defect.

**Drift count: 1.** D-029, against RFC 0031 §5.1's edge rule, introduced by this task's
own restructure and found by patch coverage.

## D-030 — the indented tree is not built, and that is P2's answer to it

Found by the self-audit: §5.5 assigns this to P2 beside D4, and P2 answered D4 and left
this one silent. Choosing not to build something is a decision; leaving it unrecorded is
indistinguishable from not having read the sentence.

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-27T10:18:17Z
attempt: 1
claim: §5.5 says an indented tree "stays available as a *second* format" under a stated condition and calls it "a P2 question, alongside D4" — P2 settled D4 and shipped no tree and no decision about one
evidence: rfcs/0031-lineage.md:349
action: decided
proposal: ASSUMED — no tree format ships. The edge list is complete and lossless; a second format is added when a consumer asks for one, under §5.5's condition that a revisited node is marked as a reference rather than re-expanded
```

- **Touches:** RFC 0031 §5.5's second-format paragraph; no decision row covers it
- **RFC said:** the tree "may be added only if a revisited node is marked as a reference
  (`↪ order_item.unit_price (above)`) instead of re-expanded", and that this is P2's to
  settle.
- **Built:** nothing. The edge list is the only text format.
- **Because:** the condition §5.5 states is what makes a tree honest, and meeting it
  produces output that is *neither* a tree nor an edge list — a tree with reference stubs
  is read by following pointers, which is the edge list with extra steps. The tree's appeal
  is that it is easy to skim, and a reference-marked one is not. No consumer has asked for
  it, and D1's whole argument is that the shape of the answer should not be chosen for how
  it looks.
- **Consequence:** `--format` stays at `table|json` on this command as on every other. A
  future tree is additive, and §5.5's condition is the bar it has to clear — this entry
  does not lower it.

## Self-audit — 2026-08-27

Scope: 2 commits / 12 files / +848−51 against `main` @ `b3a76af`, whole branch — source,
tests, docs, the task log and the task file. Ten passes.

| # | Finding | Severity | Status |
| --- | --- | --- | --- |
| A-1 | **`--max-depth -1` crashed with an uncaught `ValueError`.** The library raises for a negative depth, `main` catches only `BloomeryError`, so it escaped as a traceback — neither the `1` that means the spec was refused nor the `2` that means the invocation was wrong. `--direction up` already exits `2` through argparse's `choices`, and a test pins it; the analogous case for the other flag with a constrained value was never written, and the path was live. Now validated by an argparse `type`, so the CLI never hands the library a value it will reject. | High | Fixed |
| A-2 | **An empty graph printed a malformed refusal.** A draft spec — an entity model with no mappings — loads, resolves, and has no nodes, and the kinds fallback joined an empty set: "its ids are of kinds  — an entity field is spelled…". That reads as a bug in bloomery rather than a fact about the project, and a draft is exactly the state someone runs `lineage` in. Now says the graph is empty and why. | Medium | Fixed |
| A-3 | **`Lineage.edges`' own docstring was made false by D-026.** It said "the sub-DAG **induced** on `nodes`: every edge of the graph whose two endpoints are both present" — true for the two directional cases and wrong for `BOTH`, which is the case D-026 exists for. The log recorded that §5.1's wording was wrong and left the docstring saying it, which is worse: a reader trusts the docstring beside the code more than a document elsewhere. | Medium | Fixed |
| A-4 | **§7 asks the reference to carry §5.3's closed label table; it did not.** The how-to gained a *kinds* table and the reference gained `Direction.BOTH` prose, and the label table — the thing a reader returns to — was in neither. | Medium | Fixed |

**Sabotage, re-run after the fixes** — the seven-mutation sweep over `lineage.py` plus
three over the new CLI paths (`_depth` accepting negatives, the empty-graph branch removed,
the near-miss cap removed). One equivalent mutant, explained under D-029; the rest killed.

**Rules distilled:**

- **A library's `ValueError` is a CLI's traceback.** Where a command line accepts a value
  the library validates, validate it at the parser too — the boundary that turns a bad
  value into an exit code is argparse, and anything reaching the library uncaught has
  already escaped the contract the CLI advertises.
- **A doc fix in the log is not a doc fix in the code.** D-026 recorded that §5.1's wording
  no longer held and left the identical wording in the docstring beside the code it
  described. When a decision invalidates a sentence, grep for the sentence.

**A-6 (Low, fixed) — the fix for A-1 shipped its own uncovered detection branch.**
`_depth`'s `except ValueError` — the `--max-depth abc` path — was unreached by any test.
It is a detection branch, so uncovered means *unproven*: neither shown to work nor shown
to be reachable. Verified reachable and correct (exit `2`, and the message names the flag
rather than argparse's default "invalid `_depth` value", which would name a private
function the reader cannot act on), then pinned by a test asserted red against the branch's
removal. Found by re-running patch coverage **after** the audit fixes, which is the pass
that exists because a fix is new code with the same defect rate as any other.

## Review round 1 — 2026-08-27

Two AI reviewers (CodeRabbit, CodeAnt) on [#53](https://github.com/morzecrew/bloomery/pull/53).
Four findings after dedup; two fixed, one refuted, one carried out of scope.

**Fixed — a bounded-to-empty walk called its root a leaf.** `--max-depth 0` on a node that
has lineage returns no edges *and* sets `truncated`, and the renderer decided those two
independently: it printed "this node is a leaf in that direction" and then "there is more
beyond this". Both halves of a contradiction, and the half a reader acts on is the false
one. [`trace-lineage.md`](../pages/docs/how-to/trace-lineage.md) states the distinction the
output collapsed — "bounding to nothing and finding nothing are different facts" — so the
page and the program disagreed, and the page was right.

The self-audit walked this renderer and missed it, because
`test_lineage_max_depth_zero_is_accepted` **pinned the buggy output**: it asserted
`"truncated:" in out` and never asserted what else was on the page. A test that checks one
half of a contradictory output passes happily and reads, in a coverage report, exactly like
a test that checked the whole of it.

**Fixed — `--direction`'s help glossed two of the three values it accepts.** `both` was in
argparse's `choices` and absent from the sentence beside them, which is the one value this
phase added.

**Refuted — the CLI cannot select the wrong node of an ambiguous id.** Both reviewers read
[`graph.py`](../src/bloomery/resolve/graph.py)'s D-025 comment, which says correctly that an
entity field id can collide with another kind's, and concluded `_find_node`'s first-match
loop can therefore return the wrong node. It cannot: `_find_node` is only ever handed
`resolution.graph`, and `resolve()` cannot return a graph containing a duplicate name.
[`order.py`](../src/bloomery/resolve/order.py)'s `toposort` builds `by_name` keyed by name
alone, so a duplicate pair collapses to one entry, `len(order) < len(graph.nodes)` holds
unconditionally, and the function raises before `resolve()` returns.

**Out of scope — that refutation found a worse, pre-existing bug.** The raise `toposort`
reaches is not the `CircularDerivation` it intends. `remaining` is the set of names with
indegree > 0, and a collision empties it while the count check still fires, so `_find_cycle`
calls `min()` on an empty set: an uncaught `ValueError` out of `resolve()` — every command,
not just this one. Reproduced on `main` @ `b3a76af` with an entity named `metric` carrying a
field `revenue` alongside a metric named `revenue`. `order.py` is not in this diff and the
fix is a design question (refuse colliding ids at validation, or key the sort by
`(name, kind)`), so it is reported rather than taken here.

**Rule distilled:** *asserting that the right line is present is not asserting that the
wrong line is absent.* Where two branches can both fire, pin the output that must **not**
appear alongside the one that must.

## Self-audit — S-0075/phasing (P-1), 2026-09-13

**Scope:** the branch against `main` at `e81fe936` — 5 commits, 12 files, ~855 lines, of
which the source is two files: `guardrails/evidence.py` (+112/−15) and `spec/entity.py`
(+11). The rest is the RFC, this log, docs and tests. Every pass walked; prose honesty (§7)

### Findings

**1 · The docs-drift guard covered one of two messages.** *Fixed, `9f4b0612` and `51c37a54`.* Severity:
a documented refusal free to drift from the code on the day it was written.

`test_the_documented_evidence_refusal_quotes_the_template` exists because
`what-bloomery-proves.md` drifted from `MESSAGE` twice inside one PR series. This branch
added `IMPORTED_MESSAGE`, quoted it on the same page, and left the guard reading only the
first — the guard's own failure class, arriving through the door it was built to close.
Parametrized over both; the new leg goes red under a one-word edit to the page.

**2 · Two tests passed for the wrong reason.** *Fixed, `9f4b0612` and `51c37a54`.* Severity: two
assertions that could not fail.

Both were sabotage survivors, and in both cases the survivor was the test.

`MAX_DERIVATIONS` is 2 and the cap branch returns unconditionally for a list that long, so
**every** multi-route column returns empty — a two-route test asserting "the strongest
route acquits" is asserting the cap. Measured: `weak_bases([weak, weak], imported)` is `()`.
The test now says which branch answers it and pins two weak routes, which is the assertion
that tells the two apart.

The `entity_key` test pinned an outcome whose stated cause is narrowing rather than a guard
— `imported` is keyed by relationship name, so a `None` via misses it whether or not it is
checked first.

**3 · The refusal named neither the relationship nor the artifact.** *Fixed, `b3056a74`.*
Severity: remedy-free advice, which S-0070/D-4 forbids by name.

Reusing `MESSAGE` produced "Fix: declare the relationship that carries X" for a column
carried by a relationship that *is* declared — by an importer, in a document the author may
not have read. S-0075/summary promises the refusal names the relationship and the artifact;
the first draft of the code did not. `IMPORTED_MESSAGE` is the second sentence, and the
`names` walk collects only the imported relationships actually traversed, so a project that
imports a relationship this column never goes through is not pointed at the wrong line.

### Residue — what a reader should still distrust

- **The acquittal branch is dead at the current constant.** "A column is as strong as its
  strongest route" is argued at length in the module docstring and decides no answer: the
  cap returns `()` for any list of two or more, and `closure` never produces more. It is
  *conditionally* dead — raising `MAX_DERIVATIONS` revives it — so deleting it would be
  wrong, and it is reported rather than fixed. Pre-existing, and outside P1: changing it
  changes what a shipped guard refuses.
- **The proof leaf still says `declared` for an imported hop.** `_dependency_proof` mints
  `SemanticFact(provenance=BASIS_PROVENANCE[basis])` and the planner reaching it holds no
  spec. It mislabels an account without changing a verdict, since `IMPORTED_VERIFIED`
  closes. P2 owns it — the unlisted entry above records why.
- **`imported_from: ""` marks a relationship imported.** Presence is the fact and an empty
  string is present, so the refusal would name `''` as the artifact. Not refused at parse:
  the key is written by a program that has a filename, and a validator here would be
  guarding against a hand-edit the design already says it cannot detect.
- **Nothing checks the key was machine-written.** S-0075/risks says so, and the docs repeat
  it. A hand-typed `imported_from:` silently lowers a relationship's grade — the safe
  direction, and still a wrong fact.

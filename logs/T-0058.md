## The plan

### What the matrix already has, and what it is missing

S-0056's corpus landed: twelve cases under `tests/fixtures/semantic_corpus/`, each with a
machine-readable outcome pinned against a stable rule ID, run in the default suite by
`tests/execution/test_semantic_corpus.py`. By D4 those cases **are** this matrix's rows, so
the rows exist and one column is already measured and gated.

What does not exist is any other column, or a bundle, or the table. `comparisons/` is
absent from the tree.

### Scope of this branch

§10 phases this one system at a time, one case at a time, and says a partially filled
matrix of researched cells is useful where a full one containing guesses is not. So:

| Piece | What lands |
|---|---|
| **D6, D7** | decided, with entries — both are `OPEN` and §9 says D6 must be decided *before* the first bundle |
| **the bundle layout** | `comparisons/<system>/<case>/` exactly as §3 specifies — directories and text, no harness |
| **one system, three cases** | MetricFlow 0.212.0 against 002-average-of-averages, 005-semi-additive-balance, 008-ratio-rollup |
| **the bloomery column** | all twelve rows, cited from the corpus (see the D3 entry below) |
| **every other cell** | `UNKNOWN`, which D2 makes an honest value |

**Why MetricFlow, and why those three cases.** `pages/docs/concepts/guardrails.md:163`
already asserts a semantic property of another system — "MetricFlow lowers additivity; it
does not stop you from modeling it wrongly" — with no reproduction behind it. D5 binds the
docs to what a checked-in reproduction supports, and retired S-0058/D-5 (`9ad7ac2`) says
the same of comparative statements specifically. The first cells this matrix owes are
therefore the three that sentence spends, and the three additivity cases are the ones that
can back it or refute it. Picking the first column by which claim is already live, rather
than by which system is most interesting, is the only ordering that makes the research
answer a question somebody has already asked.

**Why MetricFlow standalone is runnable.** `src/bloomery/runtime/hydration.py:128` builds a
`MetricFlowEngine` over a hydrated manifest, so the API for driving one from Python is
already exercised in this tree. The bundle does not import bloomery: it authors a manifest
the way a MetricFlow user would, renders with MetricFlow's own DuckDB renderer, and
executes the rendered SQL against the case's `data/`.

## Self-audit

Branch `research/semantic-capability-matrix` against `main`: 12 files, no change under
`src/bloomery/`. Scope walked whole — the three bundles, the matrix, the two READMEs, the
gate, the docs edit. Findings ranked, all fixed on the branch before this was written.

**1. Two version strings written from memory, inside the document that forbids it.** The
bundle READMEs said DuckDB `1.4.4` and `sources.md` cited a distribution called
`metricflow-semantic-interfaces`. Measured: DuckDB is `1.5.5`, and
`metricflow_semantic_interfaces` ships *inside* the `metricflow` distribution — there is no
such package to name. Both were typed while writing prose about a run that had already
happened, which is exactly how D2's failure gets in: the cell was researched and its
surroundings were not, and a reader cannot tell which half is which. Fixed, and the version
half is now a gate rather than a habit.

**2. `commands.txt` named an interpreter that does not reproduce the file beside it.** It
said `python comparisons/...`; the invocation that produced `observed.txt` was
`uv run python`. Fixed, and every `observed.txt` is now regenerated by running its own
`commands.txt` verbatim through `sh`.

**3. The evidence file asserted a command nobody here can run.** `observed.txt` opened with
`mf validate-configs: 0 error(s), 0 warning(s)`, and `sources.md` cited that CLI as what was
run. The `mf` entry point ships with `dbt-metricflow`, which is **not installed** — the
runner calls `SemanticManifestValidator.validate_semantic_manifest` directly. The label was a
guess at an equivalence, in the one file whose whole job is to be checkable. Renamed
everywhere to the entry point actually called. This is the same rule as T-0057's second
correction, one step earlier: there a citation named a program plus an invocation it did not
contain; here it named a program that is not installed.

**4. The matrix's own prose carried the claim shape D1 exists to prevent.** Two section
headings read "Where the correct model is asked for, MetricFlow is native and right" and
"Where the wrong model is asked for, nothing stops it" — both true of the three tested
configurations and both phrased as properties of the product. Rewritten to open on "In all
three, ..." and to name the version.

**5. The matrix flattered bloomery by omission.** The table put `NATIVE-PREVENT` beside
`NOT-REPRESENTED` with nothing saying that the two columns are not answering the same
question with different care — bloomery can refuse the naive model only because its spec
makes the author state additivity in the first place. D3 forbids favourable scoring, and an
omitted caveat scores just as effectively as a wrong cell. The paragraph is the row proposed
above.

**6. The plan's `pyproject.toml` change was unnecessary and was dropped.** The D6 entry cited
`tools/spikes`'s deptry exclusion as the mechanism for keeping third-party configuration out
of gates written for bloomery's source. Measured: `just quality` runs ruff and mypy over
`src` alone (`justfile:116-118`) and the pre-commit hooks are scoped `^src/.*\.py$`, so
`comparisons/` is already outside every gate and nothing needed excluding. The entry's
reasoning holds; its proposed mechanism was not needed. Recorded rather than quietly dropped,
because "no exclusion was added" and "an exclusion was forgotten" look identical in a diff.

M2 is the one worth keeping. The validator call is separate from the parse, and a parse that
already refused everything would have made the printed count vacuous — the strongest evidence
in all three bundles would have been a constant.

**M7 is the one that changes what this branch is.** D3 — bloomery scored by the same standard,
including where it loses — was a discipline until that test existed; it is now a gate that
refuses a cell edited in bloomery's favour. Editing the table to hide a loss is the single
most damaging thing anyone could do to this tree, and it was the thing nothing checked.

**M7 also ran twice, and the first run was worthless.** Its `sed` used `|` as the expression
delimiter against a markdown table row full of `|`, so the command errored, the file was never
mutated, and the test reported `1 passed` — a survivor that was really an unfired mutation.
Re-run through Python with an `assert old in orig` before the write, which is what makes the
green afterwards mean the mutation happened.

that produced M4 moved the date *backwards* only, so it measured the ceiling and never the
floor; a bound tested from one side is half a bound.

**F4 is the one worth naming for next time.** Row 9's sentence — "the tree is already
outside every gate" — was measured and true when the D6 entry was written, and the same
branch then added `tests/unit/test_comparisons_floor.py`, which reads `comparisons/`. The
decision is untouched, so the row's supporting sentence is corrected rather than superseded:

visible rather than inferred.

**F5 shows how the template failure gets in.** One `sources.md` was written and copied three

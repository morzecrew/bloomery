## D-171 — Postgres will not full-outer-join on a null-safe condition

```divergence
decision: RFC 0041 D13, D17 — the shape of the branch join, and where its dialect support is established
grade: ASSUMED
class: discovery
at: 2026-09-07T16:40:00Z
attempt: 2
claim: D13's `FULL OUTER JOIN … ON a IS NOT DISTINCT FROM b` renders on all three shipped dialects and runs on two of them. PostgreSQL parses it and then refuses to plan it — `FULL JOIN is only supported with merge-joinable or hash-joinable join conditions` — because `IS NOT DISTINCT FROM` is neither. The predicate is supported, as every reference says; it is supported everywhere except the position this decision put it in, which is exactly the gap D17 exists to catch and which no amount of reading would have closed
evidence: `uv run pytest tests/engines/test_branch_join_engines.py` against `postgres:16-alpine`, first run — `psycopg.errors.FeatureNotSupported: FULL JOIN is only supported with merge-joinable or hash-joinable join conditions`
action: departed
proposal: amend D13 to state the composition rather than one spelling of it. The branches become CTEs, their keys are `UNION`ed into the domain of groups the answer has, and each branch is left-joined back onto that domain on `IS NOT DISTINCT FROM`. The null semantics are unchanged and now stated twice by two constructs that agree: `UNION` deduplicates NULL against NULL, and the left join matches a branch's NULL group to the domain's. Every group present in any branch appears exactly once, which is what the full outer join was for — and the statement runs on all three dialects, asserted by execution rather than by citation
```

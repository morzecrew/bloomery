## D-165 — a coalesced key has no dunder name to keep

```divergence
decision: unlisted — what a composed statement projects a joined key column as
grade: UNLISTED
class: spec-gap
at: 2026-09-07T13:10:00Z
attempt: 1
claim: D15 widens the plan surface and D12 settles when two branches hold one dimension, and neither says what the composed SELECT calls it. Every emitted column today is a MetricFlow dunder keyed on the serving mart's primary entity, and a branch join has two of them for one dimension — `order__region` and `order_item__order_region` — so the composed projection can carry neither without naming one branch's spelling as the answer for both
evidence: `git show f79e8d1:src/bloomery/planner/names.py` (group_by_name, keyed on `entity`), and `ColumnDescriptor.sql_alias` in `git show f79e8d1:src/bloomery/planner/result.py`
action: decided
proposal: the composed statement projects **bloomery's own name** — `region`, the requested name — as the alias, and `ColumnDescriptor.sql_alias` reports it. The dunder spelling is MetricFlow's vocabulary and survives inside each branch subquery, where it is still MetricFlow's SQL; the composed statement is bloomery's, and RFC 0018 D4 already made `sql_alias` the binding contract precisely so the two need not agree. A caller binding by `sql_alias` is unaffected; one binding a hardcoded dunder was binding to a mart it no longer has
```

## D-166 — two branches is the smallest instance, not the rule

```divergence
decision: RFC 0041 §13a P1 — "two additive branches"
grade: UNLISTED
class: discovery
at: 2026-09-07T13:12:00Z
attempt: 1
claim: §1, §3 and D11 are all N-ary — D11 partitions every measure by its owning mart with no arity anywhere — while §13a's P1 sentence says two. Restricting the fold to two would be a check written to enforce a number no decision states, and the third branch is the same reduce over one more subquery
evidence: `git show f79e8d1:rfcs/0041-multi-grain-query-planning.md` §3 and §12 D11
action: decided
proposal: P1 composes N branches. "Two" in §13a reads as the smallest instance of the shape, and the test corpus asks for three so the fold is exercised past its base case
```

## D-169 — a date dimension is answered under its effective name, not its requested one

```divergence
decision: unlisted — refines D-165 for the one case where the requested name is not a column
grade: UNLISTED
class: discovery
at: 2026-09-07T14:05:00Z
attempt: 2
claim: D-165 decided the composed statement projects the requested name, and that is right for a categorical dimension. It is wrong for a date role: a request for `ordered_day` under `time_grain: month` is answered by a single-mart plan under `ordered_month`, and answering the same request under `ordered_day` because that is the string the caller typed would report a monthly number beneath a daily name. The first implementation had the opposite defect — it preferred a branch's local spelling, so a request for `tier` came back as `order_customer_tier` when neither branch mart carried `tier` directly
evidence: `uv run python` against `tests/fixtures/cross_mart_branches`, requesting `{shipping_count, line_discount}` by `tier` — the composed projection read `COALESCE(branch_0.order_item__order_customer_tier, branch_1.order__customer_tier) AS order_customer_tier`
action: decided
proposal: the requested name, except where the dimension resolved to a date role, which is answered under its effective name. Every branch agrees on that effective name whenever the composed path opens at all: two marts reaching one date column under different roles have different provenance, and D12 refuses them before a name has to be chosen
```

## D-170 — a chained flatten's join key is a dimension to the precheck and not to the manifest

```divergence
decision: unlisted — RFC 0013 D6's "refuse before delegating", against a mart column the emitter does not emit as a dimension
grade: UNLISTED
class: discovery
at: 2026-09-07T15:20:00Z
attempt: 1
claim: a mart that flattens a chain lists the chain's intermediate join key in `MartIR.dimensions`, and the manifest emitter writes that same column as a MetricFlow *entity* rather than a dimension. So the coverage precheck accepts a request naming it and MetricFlow then refuses one — which is precisely the belt-and-braces contract RFC 0013 D6 says must fail at the first net, not the second. No fixture in the tree chained a flatten before this branch, so no baseline row shows it; `ecom_basic` carries the same column name and accepts it, because there it is not a join key for a further hop
evidence: `emit_manifest` for `tests/fixtures/cross_mart_branches` writes semantic model `order_items` with dimensions ['added_day', 'discount', 'item_date', 'line_no', 'order_customer_customer_id', 'order_customer_signed_up', 'order_customer_tier', 'order_order_date', 'order_order_id', 'order_region'] and entities ['customer', 'order'], while the mart's own dimension list also holds 'order_customer_id' and 'order_id'
action: decided
proposal: not fixed here, and not silently absorbed either. It is a defect of the mart-to-manifest lowering rather than of branch planning: the composed path reports exactly what the branch reports, and the branch reports it identically at the merge base. Recorded as a finding, licensed as its own row in the parity baseline rather than folded into P1's conversion, and left for a change that can alter `MartIR.dimensions` or the emitter without carrying a planner phase with it
```

# T-0027 · RFC 0041 P2 — filters, row policy, order, and computation above the join

Executed on branch `feat/cross-branch-filters`, against RFC 0041 §13a's P2 as it stands at
`14e21b7`. Four capabilities: a filter and a row policy placed on every branch or refused,
`order_by`/`limit` moved onto the composed statement, and a metric whose components live on
different branches computed in the wrapper above the join.

Carries one pyright cleanup in the same branch, at the user's request:
`src/bloomery/planner/compose.py` and `src/bloomery/planner/metricflow_planner.py`.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the RFC's text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

## D-177 — the composed ORDER BY sorts a key that is NULL by construction

```divergence

grade: UNLISTED
class: spec-gap
at: 2026-09-07T16:52:00Z
attempt: 1
claim: D13 and D18 exist so a group missing from a branch survives the join as a NULL-keyed row, and P2 puts `ORDER BY` on the statement holding those rows. SQL does not fix where a NULL sorts, and the three shipped dialects need not agree; bloomery renders this ORDER BY itself, so the placement is bloomery's decision rather than an inherited one. evidence: `git show 14e21b7:src/bloomery/planner/compose.py | sed -n '131,139p'` -> the `\n  UNION\n`.join over each branch's keys, which is where a NULL group is minted and deduplicated
action: decided
proposal: the composed `ORDER BY` renders `NULLS LAST` explicitly in **both** directions, so a group a branch did not have reads at the end of the answer whichever way the caller sorted. ```
```

## Self-audit findings — 2026-09-07

Appended, not edited. Scope: the whole branch against `origin/main` at `14e21b7` — two
commits, ~1,700 lines across nine source files, six test files, three documents and the
parity baseline. The sabotage sweep is `scratchpad/sabotage.py` in the session scratchpad:
fifteen mutations, **13 caught, 2 survived**, and both survivors are findings 1 and 3
below rather than gaps left open.

### 1. A guard that cannot fire, and a test that said it did

`_composable` refuses a component whose leaf measures live on more than one mart —
D-181's rule, and the reason `nested_discount` is not answered. The sweep removed the
`len(homes) != 1` half and **nothing went red**.

The why, from the data rather than from reading: a component needing two marts has to
decompose, and a metric that decomposes is never `additive`. The additivity guardrail
says so itself —

```
uv run python -c "...fixture_ir('zz_additive_derived')"
-> GuardrailError: metric 'additive_span' is derived: but declares additivity
   'additive'. A derived metric has no measure to aggregate ... Fix: additivity:
   non_additive
```

— so `_composable`'s additivity test reaches every spanning component one line earlier,
and no request can separate the two while that guardrail stands.

Two things were wrong, not one. The guard is unreachable, which is tolerable and now
says so. The *test* was not: `test_a_component_spanning_branches_is_what_refused_the_nested_metric`
was written as a controlled pair specifically to isolate this check, and it isolated
the additivity check instead — a test passing for a reason its own docstring denies.

Fixed by moving the weight to where it can be carried. `_home` — which *places* each
component on its branch — previously took the first of the sorted names, so with the
guardrail relaxed a component computed half on each mart would have been read off one
branch and answered. It now refuses, is tested directly, and the sweep's
`home-takes-the-first-of-several` mutation is caught. The pair test keeps its place and
its docstring now says what actually fires.

### 2. Two identity checks that were dead on arrival

`resolve_branches` ran `_one_dimension` over the filter clauses and the policy dimension
as well as the requested dimensions, on the reasoning that checking identity only where
a name had to be translated is the asymmetry D12 exists to close. The sweep emptied both
loops and nothing went red.

They were dead by construction, and the construction is mine: a restriction whose
provenance no branch shares is refused *before* any branch resolves it, so every branch
takes the anchored path in `_resolve_branch_dimension` and cannot reach the local
fallback that is the only thing able to disagree. The requested dimensions differ
because their anchor may legitimately be `None`.

Removed rather than marked. A check that cannot fire reads as protection, and the next
reader budgets for it. `_one_dimension`'s docstring now says why the restrictions are
not run through it.

### 3. A composed answer never re-buckets a date, and the grammar is why

`composed_keys` answers a date-role dimension under its *effective* name
(`ordered_day` → `ordered_month` under a monthly `time_grain`), and P2 added the
matching translation so an `order_by` naming the requested spelling reaches the right
projected column. The sweep dropped the translation and nothing went red.

Not a missing test — an unreachable path, and reaching for one found the rule:

```
marts.order_items.flatten[3].date: date role 'ordered' names column
'order_order_date', which is not a column of base entity 'order_item'
```

A date role may only name a column of its mart's **base** entity. Two marts at different
grains have different base entities, so they cannot publish one date column as a role,
and two roles of different origin have different provenance and are refused by D12
before `composed_keys` sees them. So no composed request re-buckets anything, and both
the arm in `composed_keys` (P1's, D-165/D-169) and the translation beside it (P2's) are
unreachable while the mart grammar stands.

Both kept and both marked at the site. What forbids them is a rule in the mart grammar
rather than anything about the planner, and their absence would answer under the wrong
name rather than fail — which is the wrong way round for a thing to be missing.

### 4. A killed measurement leaves the tree mutated, and the next one inherits it

Process, and the most expensive of the four. The sabotage sweep was started while
`just test` was still running; both were killed on noticing. The sweep's `finally`
restores each file, and the kill landed between a write and its restore, so
`_composable` was left carrying the `composable-lets-a-component-span` mutation. The
check for leftovers missed it because the check grepped for the mutation strings it
remembered rather than diffing.

The next sweep then ran with that mutation as its **baseline** — it read the mutated
file as `original`, restored it faithfully, and reported 11 caught over a tree that was
already wrong. Finding 1 surfaced only because re-anchoring the "anchor not found" entry
meant reading the line.

The standing rule was "no edits during a measurement run". It is too narrow: a killed
mutating run leaves edits behind, and the measurement that inherits them looks clean. A
sweep verifies against `git diff`, not against a list of what it thinks it wrote.

### Noted, not a defect

**The composed ratio's division is rendered by bloomery, not by MetricFlow.** A
single-mart ratio is MetricFlow's, and it casts *both* operands —
`CAST(SUM(amount) AS DOUBLE PRECISION) / CAST(NULLIF(...) AS DOUBLE PRECISION)` — on
every dialect including DuckDB. The composed form goes through the dialect port, which
casts the numerator on PostgreSQL and Trino and neither operand on DuckDB. So the two
paths spell one metric differently and the composed one is no less exact; the engine
tier pins its numbers on all three.

### 5. A qualified name walked past the guard that exists to stop it

`_bound` refuses a computed measure's expression that references anything the branches do
not produce — the check that stops an authored expression reaching the SQL as a bare
identifier resolving against whatever the join has in scope. It ran **after** the
rebinding, over the columns that were still unqualified.

A qualified name is never a rebinding candidate and is not unqualified afterwards either,
so it was invisible to both halves:

```
disc - t.ship          -> branch_1.disc - t.ship
disc - branch_0.ship   -> branch_1.disc - branch_0.ship
```

The second is the bad one. It names a branch CTE directly, so the measure would be computed
from **another branch's column** — a number, not an error, and one nothing in the plan or
the explanation would contradict.

Reachable from a spec, checked rather than assumed. The metrics guardrail that refuses a
derived expression referencing an undeclared alias compares `Column.name`, and the name
half of `t.orders` *is* a declared alias, so it passes:

```
expr: "discount - t.orders"
-> COMPILED, expr = discount - t.orders
-> PLANNED  branch_0.line_discount - t.orders AS discount_less_orders
```

Fixed by checking before rebinding rather than after: every column reference must be a bare
name this measure declares, and the refusal names the offending reference in full. Three
parametrized cases pin it, and the two qualified ones were verified red by the run above.

**The guardrail's own blind spot is left alone and reported.** `_check_aliases` in
`guardrails/metrics.py` would refuse `t.orders` with one more condition, and that is a rule
governing every project's specs rather than this planner's SQL — a scope call for the
author, not for a phase that was asked for cross-branch planning.

### 6. Two detection branches with no test, and one claim that turned out to be wrong

`compose.py` 35/35, and `coverage.py` 70/73. The three:

* **a component naming a metric that does not exist** — unreachable: components are read off

## After convergence — two the audit missed, found in review — 2026-09-07

The convergence note above is left standing and is wrong about what it implies. The audit
terminated on a pass that produced nothing new, which is the stated rule, and two real
defects were still there. Both were surfaced by reviewers on the pull request; both are
recorded here rather than only in that thread, so the count of what this branch got wrong
is in one place.

### 7. A branch's plan named a column its branch does not have

`SemanticPlan` is lowered rather than shown, and each branch's `Filter` carried the
**requested** spelling of a restriction: `region = 'EU'` on the branch whose scan restricts
`order_region`. A consumer lowering that plan emits a predicate on a column the relation
does not have.

The evidence was inside the object the whole time and neither the sabotage sweep nor the
coverage pass looked for it: the `Aggregate` beside that `Filter` already names the
branch-local column, so one branch's plan contradicted itself — `dimensions=('order_customer_tier',)`
sitting under `predicates=("region = 'EU'",)`.

```
order_items -> ("region = 'EU'",)        # before
order_items -> ("order_region = 'EU'",)  # after, and what the SQL restricts
```

The cause is one argument. `_composed` built the merged explanation first and passed *it*
to `applied_predicates` for every branch, and merging is exactly where the requested
spelling replaces the per-branch ones (that substitution is deliberate — a reader is owed
one filter, not three). The per-branch explanations already carried the right names and
were being discarded. They are kept now and each branch reads its own.

**Why no pass caught it.** Pass 4 asks whether new code follows the discipline of its
surroundings, and the surrounding discipline was in the same object: `Aggregate.dimensions`
resolved, `Filter.predicates` not. I read the two fields in different passes and never
beside each other. A rule worth keeping: when one node's fields are built from two sources,
read them together and ask whether both name the same vocabulary.

### 8. One refusal for two failures that need different answers

`_shared_provenance` answers `None` both when no branch carries a name and when every
branch carries it and means something different by it, and the composed path reported the
first message for both. The second case is not exotic: an unqualified date bucket resolves
through each mart's own role, so a filter on `month` is `ordered_month` on one mart and
`added_month` on the next.

So a request whose filter both marts *can* evaluate — differently — was told the marts do
not carry it, which sends the reader to flatten a column both already have. Each branch is
now asked to resolve the name the ordinary way, and the outcome picks the message:
`_not_one_dimension` where they disagree, `_not_on_every_branch` where one cannot resolve
it at all.

**Drift count: 0.** (Unchanged. Both are defects in what this branch built, not departures
from what RFC 0041 decided.)

## Review findings — 2026-09-08

Two more the branch got wrong, both in code this round introduced, and both reported by
reviewers on the pull request. They are the same defect wearing two faces:
`_shared_provenance` answers `None` for three different situations and the composed path
had one answer for all of them.

### 9. An ambiguous bucket was reported as a missing one

An unqualified date bucket resolves through a mart's date role, so a mart with two roles
cannot answer `month` and says which two — `'month' has roles ['ordered', 'shipped']. Use
'ordered_month' or 'shipped_month'.` The composed path caught every resolution failure
alike, including that one, and reported "not carried by every mart" over a table in which
**both** marts read "not carried", because the table is built from column names and no mart
publishes a column called `month`.

So the author of a request that names a real ambiguity was told two marts lack a dimension
one of them has twice, and pointed at a flatten. `AmbiguousDimension` travels now; only a
genuine failure to resolve reaches the "not carried" message.

### 10. Two branches agreeing was refused as a collision

Worse, and the reason finding 9's fix is not enough on its own: the per-branch route
refused *every* restriction that reached it, by calling `_not_one_dimension` unconditionally
— including where the branches agree.

Two marts on one base entity, each carrying a different measure and each flattening the same
date under the same role, resolve `month` to the same column from the same source column.
The refusal printed the two identical rows, which is the tell:

```
dimension 'month' is carried by every mart this request needs, and they do not mean the
same column by it:
  orders               → ordered_month (from order.order_date)
  orders_wide          → ordered_month (from order.order_date)
```

`_one_dimension` — the check finding 2 removed from this path as dead — is what decides it
now, and on this route it is live rather than dead: the anchored route agrees by
construction, and this one has to be asked. Removing it was right for the code as it stood
and wrong for the code as it became, which is an argument for re-running the question rather
than for keeping dead guards.

### 11. The silence check had never run for this task

`logs/README.md` asks tasks executed from here on to ship a task file written *before* the
work; this one shipped none, so `log_check.py` reported SKIPPED on every run above. Every
task since T-0009 has done the same and this one had the least excuse: RFC 0041 is live and
its rows declare their own areas, so nothing had to be reconstructed.

`tasks/T-0027.json` exists now. **It proves nothing about this task** — paths chosen after
the fact by someone who knows what they touched cannot fail — and what it buys is that the
check runs at all, here and for the next change under `src/bloomery/planner/`.

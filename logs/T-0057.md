## The plan

§6 asks one question: **does a row admitted into a framework-maintained type 2 relation, by
any route, become visible to an as-of join at the entity's grain?** D3 makes the acceptance
an as-of join *finding* the row, never a row being present, so every route is measured by
running the join rather than by counting rows.

Three routes, on both targets, against one entity:

| Route | What arrives, and how | What it decides |
|---|---|---|
| **A — the control** | the shipped merge: entity columns only, straight into the framework's relation | reproduces §3's measurement, and is what "present and invisible" has to mean for the other two to be readable |
| **B — §5.2** | the row is written to the bronze relation and the ordinary pipeline runs | the leading candidate; if the framework versions it, D5 is settled |
| **C — §5.1** | the entity's source query gains a second arm reading a `__replayed` relation | the expensive candidate, measured by hand-editing the artifact rather than by building the emitter half |

`scd2_as_of` is the base: a type 2 `customer`, an `order` fact, and a mart already
flattening the first into the second with `as_of: order_date`. The as-of join D3 requires is
the fixture's own mart, not something written for the measurement.

No bloomery change, on purpose. Routes B and C are hand-edited artifacts in a temporary
project, which is what makes this a spike rather than a half-built candidate — §9's third
risk is that a partial fix reproduces the defect with a suite that says it is fixed.

### The apparatus was wrong twice, and both times it read as a result

Recorded because the failure mode is the one this measurement exists to avoid — a run that
abstains looks exactly like a run that answers.

**First attempt: every route reported "invisible", including the control.** The orders were
dated 2024 and both frameworks stamp the first version with their own clock, so
`order_date >= valid_from` was false for every row and the as-of join found *nothing*. Three
routes "failed" a join that could not reach any row. Fixed by dating the orders after every
version the frameworks will write, and by asserting the baseline row is found before reading
any route's verdict.

**Second attempt: routes B and C reported "invisible" on SQLMesh only.** The row never
reached the entity at all: `plan` compares code, and new bronze rows are not a code change,
so the model never executed. `run(ignore_cron=True)` was not enough either — with no missing
intervals there is nothing to process. It takes `run(execution_time=…)` advanced the way a
daily cron advances it. Fixed, and the report now asks *separately* whether the row reached
the entity and whether the join found it, because "the framework never saw it" and "the
framework saw it and the join cannot reach it" are different answers and only the second is
a verdict on the route.

## Correction — 2026-09-15

The second plan-gate entry decided the spike scripts would stay throwaway and the transcript
alone would live in this log. **That was wrong, and the log checker is what said so:**
evidence has to be a `path:line` or a backticked command with its output, and "the transcript
above" is neither. The rule is not a formatting preference — a measurement whose program has
been deleted is a claim about what once happened, and the four entries above rest on it to
settle two `OPEN` rows.

The scripts are now `tools/spikes/rfc0060_dbt.py` and `tools/spikes/rfc0060_sqlmesh.py`, with
a README saying what a spike is and is not: not a test, no marker, no CI, and a spike that
stops working is a fact about the tree having moved rather than a failure.

The earlier entry stands as written. What it got wrong is worth leaving visible, because its
reasoning — "ship the information, not the code" — is right about *tests* for a route nobody
chose and wrong about the program that produced the information.

## Self-audit — 2026-09-15

Whole branch: 2 commits, 5 files, ~523 lines added, none of them under `src/`. This branch
changes no product behaviour; what it produces is a measurement and four proposed rows.

**One finding, fixed on the branch. It is a finding against the measurement's own
instrumentation, which is the only thing here that could carry one.**

**The baseline guard did not defend the routes on SQLMesh.** The report asserts the
untouched row `c1` is found before reading any route's verdict, which is what caught the
first broken run. Sabotaged — orders re-dated 2024, the exact break that guard exists for —
and on SQLMesh it did not fire: that target stamps the initial load `valid_from` at the
epoch, so `c1` is reachable from *any* order date while the recovered row, stamped with the
run's execution time, is not. The mutant turned routes B and C from found to invisible and
the guard reported everything healthy.

The reported results were right — the committed seed dates orders 2099 — but a guard that
passes the break it was written for is not a guard. Replaced with one that compares the
order's own date against the interval the framework actually assigned, both read out of the
rows rather than held as constants. The first attempt at *that* held the date as a module
constant and missed the same mutant again, because a sweep changes the seed and not the
constant: the same defect one level up.

**Apparatus sweep: 3 mutants, 3 caught**, each reproducing a break that actually happened
during this task rather than one imagined afterwards — orders dated before every version, on
each target, and a refresh that compares code when the change is data.

**What was checked and found sound:** both spikes run from their committed paths and report
the same three verdicts; `just quality -s` is 9/9 with `tools/spikes` scoped out of the
dependency gate alone and every other rule still reading those files; no file under `src/`
is touched, so no test in the suite can be affected by this branch.

**What remains uncertain.** Route A is a *simulation* of the shipped replay merge — an
insert naming the entity columns — rather than the emitted artifact, because the artifact
only exists for a quarantining entity and that pair is refused at resolution. It matches the
outcome §3 recorded, so the simulation is consistent with the documented behaviour, but it
is not the statement bloomery would emit. And both candidates were measured on DuckDB
through both frameworks; neither was measured on an engine where a snapshot's physical
layout differs, which is where SQLMesh's view indirection already produced one surprise.

## Review round 1 — 2026-09-15

One finding, two halves, both valid and both reproduced.

**Row 10 outran its evidence.** All three routes admit a key the entity did not have, so
none of them corrects an existing version — and §10's second question is precisely whether
replay corrects or adds. The row cited SQLMesh's restatement refusal, which is a fact about
what an *operator* may ask for, not about what the route does. Both spikes now change an
existing row's value in bronze and re-run: dbt and SQLMesh each close the standing version
and open a new one, old version retained. The row is reworded to the claim that measures —
a correction arriving by §5.2's route adds and closes — with the restatement refusal kept as
the separate fact it is.

**The evidence named a command the committed script does not contain.** The restatement
probe was run in `probe2.py` during the task and never landed, so
`... rfc0060_sqlmesh.py` with `restate_models=[...]` was a citation nobody could follow —
the hedge "with" was doing the work a missing line should have done. The probe is now in the
spike and the citation names a command that produces the quoted output.

This is the same rule as the plan-gate correction above, one level subtler: there, evidence
pointed at a deleted program; here it pointed at a *present* program plus an invocation that
was not in it. A citation is only evidence if running it produces what it claims.

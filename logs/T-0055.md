# T-0055 · Exposure sinks and the additivity wording (RFC 0064 P3)

Executing RFC 0064 phase 3 (§12) against branch `feat/timeline-sinks`: the exposure sinks
from RFC 0056 on a `TimelineChange`, and the additivity facet "stated in RFC 0039's
provenance vocabulary". P3 is the last phase of the last document of the three-document
history sequence, so landing it retires 0064, and with it 0069 and 0062.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the spec's own text. The rows proposed below are put forward for
the author to accept or refuse; execution does not write them into a decision table itself.

## Self-audit — 2026-09-14

Scope: the whole branch against `main` — 1 commit at the time of the sweep, 15 files,
+461/−901 (`audit_scope.py scope --base main`); the negative line count is three retired
documents. Sabotage before coverage, ten mutants over `resolve/timeline.py` and
`cli/render.py`. First pass **8 killed / 2 survived**; both survivors were diagnosed rather
than assumed, and one was a real gap.

| # | Survivor | Why | Status |

| 1 | Sink lookup uses the readable name instead of the graph's adopted id | No fixture in the corpus adopts an `id:`, so the two spellings agree everywhere and every other test passes on either. | 2 | The explicit `sorted()` on the sinks removed | Equivalent. `Lineage.nodes` already arrives sorted by `(name, kind)`, so filtering it and taking `.name` is name-sorted without help | **Kept, with the reason in the code.** An emitted collection carries its own total key rather than inheriting a neighbour's documented order; no sweep can distinguish that, so the comment is the only place it can be recorded |

Second pass: **9 killed, 1 equivalent.**

Two findings from the read-through rather than the sweep:

- **A test asserted the opposite of its own name.** `test_a_change_reaching_no_consumer_names_none` asserted `all(change.reaches ...)` — it would have passed on an implementation that never returns empty. Rewritten against a project that declares neither a mart nor an exposure, paired with a populated case so "empty" cannot mean "the walk no-opped".
- **An unused helper shipped.** `_ecom(**edits)` was written, never called, and ruff does not flag a module-level function. Deleted.

Residue — audited and still not certain:

- The sinks are asserted on one fixture shape. `ecom_basic` has two exposures and one mart, and the transitive case rests on `finance_extract` naming only the mart; a project whose exposures and marts interleave differently is not exercised.
- The *after*-side choice is now pinned by a test, but only for an added exposure. A *removed* consumer is the mirror case and is not tested; it fails the same way if the choice is reversed, so the pin is one-directional.
- `--format json` carries `reaches` through the structural encoder rather than through a named field, so nothing asserts the JSON key beyond the encoder's own behaviour. That is the pre-existing contract the command's docstring relies on, not something this change introduced.

## Correction — 2026-09-14

The retirement sections appended to `T-0038`, `T-0043` and `T-0045` in this change, and the
ones in `T-0042` and `T-0046` before it, all describe the citations they correct as dead and
name a gate that would stop the corpus decaying. **Measured afterwards, that framing is
wrong.** All twenty such citations across the log corpus are `rfcs/` paths, all twenty name
a number that is in `RETIRED.md`, and all twenty resolve at the commit that table gives —
checked with `git cat-file -e <sha>:<path>` for each. Nothing has decayed. The line a
citation names is one `git show` away, by the route `INDEX.md` documents.

What is true is narrower: `log_check.py` tests the working tree and knows nothing of
`RETIRED.md`, so it reports a recoverable citation as missing. That checker is **vendored** —
`flag-dont-flip` is pinned in `skills-lock.json` — so the fix belongs upstream and not here;
patching it in this tree would be overwritten by the next sync, with the thread closed and
the defect back. It also gates nothing: it is in neither CI nor `just quality`.

So the gate proposed three times in these logs is not this repository's to build, and the
migration it implied — rewriting entries to a `git show <commit>:path` locator — would have
been churn against a record that was already sound. `INDEX.md`'s retirement section now
carries the fact instead, beside the table that makes it true, and says not to migrate.

Recorded here rather than by editing the five sections, which stand as written: what they
got wrong was the severity of their own finding, and that is worth leaving visible.

## Review round 1 — 2026-09-14

Three defects found in review, all in text this change added, all fixed on the branch.

**`rfcs/INDEX.md` said "Three consequences worth knowing:" over four bullets.** This change
added the fourth. Counted rather than eyeballed: the section now reads `Four`.

**`rfcs/INDEX.md` claimed 0062, 0069 and 0064 "cited only each other".** False as written —
each of the three cites RFC 0056, and 0062 also cites 0007, 0044, 0051, 0059 and 0063
(`git show 79658f4c:rfcs/0062-stable-node-identity.md | grep -oE "RFC [0-9]{4}" | sort -u`).
The sentence had the direction backwards: the rule it illustrates turns on who argues *in* a
document's vocabulary, not on what the document cites. That claim is true — at the branch
point the only files naming 0062 or 0069 were the three themselves and `INDEX.md`
(`git grep -lE "RFC 006[29]" 79658f4c -- rfcs/`). Reworded to state the incoming direction.

**A dead `load_fixture("ecom_basic")` call in `test_the_sinks_are_found_for_a_node_that_adopted_an_id`.**
Both bindings discarded; the catalog the test uses is loaded from text on the next line.
Removed. Nothing in the file's ruff configuration flags a `_`-prefixed binding, which is why
it survived the sweep that found the defect the test exists for.

A fourth finding — that `_sinks` rebuilds lineage adjacency per changed node, so a version
is `O(changes x |E|)` — is mechanically true and was measured rather than argued. One
`lineage()` call costs between 1/150th and 1/280th of the `_compile()` call the same version
already pays, held across graphs from 60 to 7,440 nodes:

```
nodes=   60 edges=   30  compile=     2.3 ms  lineage= 0.009 ms  ratio=   262
nodes=  440 edges=  220  compile=    14.9 ms  lineage= 0.054 ms  ratio=   275
nodes= 2520 edges= 1260  compile=    86.7 ms  lineage= 0.586 ms  ratio=   148
nodes= 7440 edges= 3720  compile=   283.1 ms  lineage= 1.590 ms  ratio=   178
```

The ratio does not invert with scale, so the walk overtakes the compile it rides on only in a
version where 150+ nodes each moved a facet. Removing it means either a new parameter on the
public `lineage()` to pass adjacency in, or a second downstream walk written inside
`timeline.py` — and a second walk over one relation is the drift this module's docstring
refuses by construction. Left as it is, to be revisited if a real history ever shows a
version changing that many nodes at once.

**Drift count: 0.**

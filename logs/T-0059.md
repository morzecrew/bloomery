## The plan

### What P1 is, and what it deliberately is not

D1 makes the boundary an explicit export list; §5.1 says what may be on it — an entity, a
mart or a metric, "never a mapping, a step, or a quality surface". P1 lands that list, the
validation that makes it an assertion rather than a claim, and its place in the IR. It lands
no consumer: nothing reads an export in this phase, which is what makes it additive.

The tree already carries this document's twin. S-0063's `ExposureSet` is an optional
single document of pure references, validated against the **authored** documents by a
guardrail, lowered to an IR node by a transcribing builder, and carrying a JSON-schema
golden. Every one of those shapes transfers, and where this plan chooses, it chooses what
`exposures` already does.

### Decisions the plan needs that the spec does not settle

Two, both entered below. Whether a **rollup** may be exported — §5.1's list names three
kinds and the deny-list names three others, and a rollup is in neither, while being a gold
relation a downstream could plausibly read. And whether **P1** is the phase that carries the
IR field and the version bump, or whether the list stays authored-only until a later phase
consumes it. Neither is a blocker; the readiness gate is three.

## Self-audit

Branch `feat/export-surface` against `main`: 18 files beyond the regolden, one new spec
document, one new guardrail, one IR field. Scope walked whole — the spec model, the loader
wiring, the schema registration, the IR node and its version, the builder, the guard, the
stage, the docs entry, the fixture, and the 185 regenerated goldens. Findings ranked, all
fixed on the branch before this was written.

**1. The corpus could not reach the change, and a gate said so.**
`tests/property/test_schema_agreement.py` asserts that every `SpecKind` appears in the
fixture corpus, and it went red: a new document kind with no fixture carrying one means the
schema/parser agreement properties never validate an exports document, never mutate one, and
report green over a kind nobody exercised. Fixed by giving `ecom_basic` an
`exports.yaml`, which turned out to pay three times over — see findings 2 and 3.

**2. The fixture found a real refusal in a test that had been passing.**
`tests/unit/test_plan/test_renames.py::test_a_delete_is_still_a_delete` deletes
`gross_revenue` and every reference to it — the mart measure, the derived ratio, the
exposure's dependency — and with `ecom_basic` now exporting that metric the compile was
refused: *"exports metric 'gross_revenue', which this project does not declare"*. The guard
was right and the test was incomplete. A metric deleted while still on the published surface
is the exact mistake D1 exists to catch, so the test now deletes it from the export list too,
the way an author would.

**3. "Nothing consumes it yet" is now measured rather than asserted.**
With `ecom_basic` carrying an export list, its dbt, SQLMesh and Cube artifacts are
byte-identical to before **except the fingerprint** — `git diff -- tests/golden/ecom_basic`
filtered of `blm1:` lines is empty. §12's claim for P1 is a property of the emitted
artifacts rather than a sentence in this log.

**4. A single-use public property was speculative surface.**
`Exports.is_empty` had exactly one caller — the validator two lines below it — and `Exports`
is re-exported from `bloomery.spec`, so the property was public API for the sake of one
internal branch. Inlined.

**5. Not a defect, recorded because a later reader will wonder.** `plan()` does not relabel
names inside an export list when a metric is renamed. That is correct for P1 and for the
reason `_relabelled`'s own docstring already gives about exposures: nothing reads the old
IR's copy, so an arm for it would change no answer and survive any sweep. The rename sweep
now reaches a project that *has* an export list, which is what makes that a measurement
rather than an assumption; a phase that ever diffs the surface needs the arm, and this
paragraph is what says so.

### What was not done, and why

- **No how-to.** §7 asks for "publishing a surface, and consuming one", and half of that
  sentence has no subject yet: nothing consumes an export in P1. A page teaching an author to
  publish a boundary no project can read through would be a page about a feature that does
  not work. `pages/docs/reference/errors.md` carries the new class because the docs floor
  requires every exported error to be documented, and that is the whole docs change.
- **No import side, no cycle check, no lineage component, no fingerprint composition, no
  emitted reference.** P2 through P5, in §12's order.
- **§5.3's fingerprint decision is untested here**, because there is no upstream fingerprint
  to compose yet. What P1 does move is every *existing* fingerprint, by the version bump, and
  the golden diff is 185 files of exactly one changed line each.
- **§9's naming-policy risk is untouched.** §10's first question asks whether the upstream IR
  should carry the policy it was compiled under; nothing here answers it, and nothing here
  needs to — the question becomes live when a downstream reads the IR.

## Review round 1

One finding, valid, fixed — and the argument I would have made against it was wrong, which
is worth more than the fix.

**`ProjectIR.exports` was inserted mid-list and silently rebound a positional caller.**
`exports` landed between `exposures` and `date_dimension`. Every field on `ProjectIR` has a
default, so a caller written before the field existed does not get an error — it gets a
`DateDimensionIR` bound to `exports` and `date_dimension` back as `None`:

```
ProjectIR(17, (), (), (), (), (), (), (), dim)
date_dimension -> None
exports       -> DateDimensionIR(name='dim_date', …)
```

Reproduced before fixing, `exports` moved to last, reproduction re-run and now correct.

**The reasoning worth recording is why the obvious rebuttal failed.** The first thing I
measured was precedent: `exposures` landed at version 13 in exactly this position, shifting
`date_dimension` and four fields after it, and shipped. That reads as the project having
already decided positional construction of a fourteen-field root is not supported — and it
is the wrong conclusion. The tree states the opposite rule for the same hazard one module
over: `tests/unit/test_advisories.py` asserts `advisories` is `SpecEvidence`'s **last** field
and executes a positional-construction regression beside it, citing S-0035/D-1 — "appending
is what keeps the addition additive". So version 13 is not a precedent; it is the same defect,
unnoticed because nothing checked. A repeat is evidence of a missing gate, not of a settled
decision.

The gate now exists for this node too: `test_exports_is_the_last_field` and a positional
regression that supplies **every** pre-existing field, because a call that stops before the
insertion point passes against a field inserted after it — the `SpecEvidence` test says so in
its own docstring, and that is the shape that let this ship once already.

Moving the field moved every fingerprint a second time; the goldens are regenerated and the
diff is again 185 files of one `blm1:` line each and nothing else.

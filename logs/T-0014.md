## D-072 — where the Tier 2 wrap belongs

```divergence
decision: RFC 0051 §5.3
grade: ASSUMED
class: discovery
at: 2026-09-04T09:05:00Z
attempt: 1
claim: §5.3 puts the wrap in `_sql_model_artifact`, which is SQLMesh's path — but dbt emits Tier 2 outputs too, through its own `_step_artifacts`, and a wrap in one path leaves the other emitting a silver model without `_quality_flags` while the shared quality mart selects that column off it
evidence: src/bloomery/emit/dbt/__init__.py:385-416
action: departed
proposal: the wrap moves into `step_output_body(step, output, ir, ctx)` in `emit.steps`, above the envelope split and beside the parameter substitution that is there for the same reason (RFC 0008 D4); both targets call it and neither decides
```

- **Touches:** RFC 0051 §5.3 (`ASSUMED` by §11 D9's placement, which names the function and
  not the site) — departed on placement only. D9's substance, that the wrap is
  `_quality_pipeline` and never a second copy, is what the move protects.
- **RFC said:** "`_sql_model_artifact` renders `_quality_pipeline(entity, ctx, body)`
  instead of the bare body".
- **Built:** `step_output_body` does, and `_sql_model_artifact` calls it. dbt's
  `_step_artifacts` calls the same function in place of the `step_body` it used before.
- **Because:** the pre-existing split was already exactly this — `step_body` existed so
  the SELECT could be target-neutral while the envelope was not. Putting the wrap below
  that line would have made the SELECT target-dependent for the first time.
- **Why `discovery`:** §3 named `_sql_model_artifact` after reading the SQLMesh emitter and
  never looked at dbt's Tier 2 path, which does not go through `emit.steps`' artifact
  builder at all. Nothing in the RFC's reading could have shown this without opening that
  file.

## D-073 — a flag rule takes a step project off dbt

```divergence
decision: UNLISTED — what a flagged step output does to the dbt target
grade: UNLISTED
class: discovery
at: 2026-09-04T09:20:00Z
attempt: 1
claim: `on_fail: flag` on a step output puts a data-quality mart in the project, and the dbt emitter refuses that mart outright (RFC 0008 §5.5) — so a project that compiled for dbt stops compiling for it when a step output gains a flag rule, and the dbt half of §5.3 is unreachable today
evidence: src/bloomery/emit/dbt/__init__.py:513
action: decided
proposal: ASSUMED — accepted unchanged. It is the quality mart that dbt refuses, not steps, and a flagged *mapped* entity has done exactly this since RFC 0016; a step output behaving differently would be the special case
```

- **Touches:** nothing stated — §5.3 discusses lowering and never asks what the two targets
  then do with the project.
- **Decided:** no refusal is added and none is suppressed. The existing message names the
  quality mart and points at the sqlmesh target, which is the accurate diagnosis.
- **Because:** the alternative is a rule whose meaning depends on which entity carries it,
  and there is no reading under which a step output should get a quality mart dbt is
  spared. It also means D9's dbt path cannot be exercised end to end yet, which is
  recorded in `step_output_body`'s docstring rather than left for a reader to discover.
- **Consequence:** `tests/unit/test_steps/test_dbt_and_cube_emission.py` pins the refusal
  rather than the emission, and says why in its docstring.

## D-074 — the manifest's artifact path

```divergence
decision: RFC 0051 D5
grade: OPEN
class: discovery
at: 2026-09-04T08:30:00Z
attempt: 1
claim: D5 delegates the manifest's path — root or a namespace — and §10 states the case for the root without settling it
evidence: src/bloomery/emit/metricflow/__init__.py:862
action: decided
proposal: `semantic_manifest.json` at the artifact root, as §10 argued: a MetricFlow project holds one top-level manifest, nothing else in the emitted tree competes for the name, and a namespace of one file names a grouping that does not exist
```

- **Touches:** RFC 0051 D5 (`OPEN`) — answered, not departed from.
- **Decided:** the root. `MANIFEST_PATH` is a module constant rather than an inline
  string, so the day a second MetricFlow artifact ships there is one place that says
  where they live.
- **Because:** the other targets namespace because they emit *many* files whose names
  collide across layers (`models/silver/order.sql` beside `models/gold/mart_orders.sql`).
  One file has no such problem, and `semantic/semantic_manifest.json` reads as a directory
  a reader should expect more in.

## Self-audit — 2026-09-04

Scope: the whole branch against `main` — 5 commits, 38 files, +1344 −402
(`audit_scope.py scope --base main`), source, tests, docs, RFC corpus and this log.
Read RFC 0051's decision table first, the diff second.

**F-1 — a refusal message claiming a collision that cannot happen. Fixed.**
`ReservedEntityName`'s message told an author their entity's field and "a source of that
name are one id". For `metric`, `canonical` and `step` that is exactly true. For `source`
it is not: a bronze extraction's id carries a third segment (`source.<relation>.<path>`)
and a field name is one identifier, so no entity field ever equals one. An author who
checked would have found the stated collision absent, and a refusal that overstates its
case is one people learn to argue with. The reservation itself stands — the rule worth
remembering is "an entity is never named after a node-id prefix", and one that held for
three of four names would be learned as four exceptions — so the message now says what is
true of `source`: every field of such an entity mints an id in that namespace.
`src/bloomery/guardrails/lineage.py`, pinned by
`test_the_source_refusal_does_not_claim_a_collision_it_cannot_show`.

**F-2 — a test whose docstring described the compiler it no longer tests. Fixed.**
`test_a_flag_or_quarantine_rule_on_a_step_output_is_still_refused` kept passing after the
refusal narrowed, and for a poor reason: it matched `"on_fail: fail"`, which both new
messages happen to contain in their *fix* clause. So it asserted that something was
refused without asserting what, and its docstring still said both dispositions fail
because a step relation has no SELECT — now half true. Renamed to name the tier it
actually wires, and each disposition is matched on its own message.
`tests/unit/test_steps/test_emission.py`.

**F-3 — two test obligations from §6 unmet. Fixed.**
§6 promised "a mart over a flagged step output flattens `has_quality_flags`" and "the
target is reachable ... through the CLI's `--target` parsing"; neither existed. Both were
the *only* checks of a `carries_quality_flags` call site and of the CLI path respectively,
so their absence was not redundancy. Added as
`test_a_flagged_step_produced_base_does_get_the_quality_dimension`
(`tests/unit/test_marts/test_flatten.py`) and
`test_the_metricflow_target_writes_its_manifest` (`tests/unit/test_cli.py`).

**Sabotage sweep — 9 mutations, 9 killed.** Each anchor asserted present before mutating,
each restored from a file copy rather than by `git checkout`. Never wrap a Tier 2 body
(2 failed, 4 errors); `carries_quality_flags` always True (9 failed) and always False
(22 failed); the lineage guard never firing (6 failed); dropping `step` from
`NODE_ID_PREFIXES` (1 failed); manifest `indent=4` (1 failed); martless project emitting
anyway (1 failed); the quarantine refusal removed (3 failed); the flag-on-Tier-3 refusal
removed (2 failed).

One survivor-shaped result worth stating rather than counting as a kill: dropping `step`
from `NODE_ID_PREFIXES` failed **only** the drift gate in `test_graph.py`, never
`test_lineage.py` — whose refusal cases are parametrized over that same constant and so
can never notice a name leaving it. That is sound only because the drift gate asserts set
*equality* against the ids the four builders actually mint, in both directions. Said here
because the pair is load-bearing and the parametrized test alone would prove nothing.

**Coverage.** `just coverage`: global 99.1% (floor 98), `guardrails/*` 100.0% (floor 100),
`steps/*` 92.5% (floor 92). Every line added by this branch is covered — the residual
misses in `emit/steps.py` (263-264, 341, 346, 351, 399) and `resolve/steps.py` (598) are
pre-existing and outside every hunk in the diff.

A first coverage run reported `guardrails/lineage.py` at 47.6% and failed the 100 floor.
That number was an artifact of my own doing: the run was in the background while I was
editing that file, so the traced line numbers and the file on disk were two different
things. Re-run against a quiet tree, it is 100%. **Never edit a source file while a
coverage run is in flight** — the report is not wrong-looking, it is wrong, and it points
at a real file with real line numbers.

**Residue.** What I would still distrust: an `expression` rule's `expr` is arbitrary SQL
over the output's columns and nothing checks the columns it names — a typo is a run-time
binder error, for a `flag` rule exactly as it already is for a `fail` one. Pre-existing,
not widened here, and not in this RFC's scope. And D9's dbt path has no end-to-end test
because no project can reach it (D-073); the shared function is what stands in for one.

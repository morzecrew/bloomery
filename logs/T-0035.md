## Plan

P3 is Cube. §5.3 asks for a `pre_aggregations` block on the parent cube, and
§12 scopes the rest away: §9's third risk — whether Cube's own query-time
matching agrees with the obligation bloomery discharged — is "measured into
RFC 0043's capability matrix rather than asserted here". So P3 emits the block
and records the comparison as owed; it does not build it.

Row 14 (`LOCKED`) holds without a filter, and that is the same argument P2
made in a different place: the block is a key inside the parent mart's existing
document, so the emitter still loops `ir.marts` alone. No new cube, no new
view, no new member, and `measure_owners` is not consulted about a rollup
because a rollup never becomes one of its candidates.

P3 completes the document, so RFC 0058 retires here — and with it RFC 0038 and
RFC 0040, whose ✅-root exemption names 0058 as their last dependant. RFC 0037
stays: 0039, 0042 and 0053 still argue in its vocabulary.

Out: the capability comparison itself (RFC 0043), MetricFlow — which has no
pre-aggregation surface and is not asked for — `assert:` on a rollup, chained
rollups (row 10 refuses them), and anything that makes a rollup selectable by
bloomery's own planner (row 14; §4 leaves the choosing to RFC 0040).

## Self-audit — 2026-09-09

Scope: the whole branch, 5 commits / 18 files / +679-711, against merge base
`efba2b6`. Four findings, all fixed on the branch.

**1 · The retirement orphaned two obligations, one of them `LOCKED`.** This is
the finding, and it is a defect in the retirement rather than in the emitter.
RFC 0058 D8 (`LOCKED`) says no plan transformation may merge two aggregate
branches without proving the merge preserves every measure's grain — and it was
*parked* in 0058, in those words, when RFC 0041 retired, "because this is the
live document holding a preservation obligation". §6 carried the property test
it owes, "named here so the obligation has a live home until then". Deleting
0058 deleted the only home of both, and neither the row nor the test is built.
The same paragraph of §12 that scopes P3 also sends §9's third risk to
RFC 0043's capability matrix, and 0043 did not carry it either.

Both are transferred rather than dropped, which is what 0041's retirement did
with the same row: D8 lands on RFC 0039 as row 9, because a merge is legal
exactly when it can *derive* that its aggregate is the one the detail would
have produced, and that is 0039's subject rather than the rollup mart's — the
two were one shape only while 0058 was the nearest live home. The Cube
comparison lands on RFC 0043 as row 8. Both rows keep D8's own transfer clause
and cite `efba2b6`, a commit 0058 is readable at.

This is the one finding worth a second reader: the *fact* that both were
orphaned is checkable from the deleted text, but which live document should
hold each is a judgement, and a different one is defensible.

**2 · A rollup storing no measure would have emitted `measures: []`.** The
empty case was inherited from a comprehension rather than decided. It cannot
arise through the compile path — R013 requires a ratio's operands be carried
and they are additive, so a proven rollup always stores a number — but
`CubeEmitter.emit` is public and takes any `ProjectIR`, so it is constructible,
and Cube rejects such a model at load without mentioning bloomery. Refused with
`UnsupportedByTarget`, verified red before the guard existed.

**3 · A sabotage survived twice, and named an untested capability.** `count`
building a `SUM`, and `min` and `max` swapped, both left every suite green.
`ROLLUP_AGGREGATES` has four entries and only `sum` was ever rendered — three
of the four produced SQL nothing asserted. That is not a blind check: it is the
gap the narrowing above walked past, and a swapped `min`/`max` is exactly the
failure D5 refuses to approximate, a rollup holding the wrong extreme and
answering quickly. One parametrized test over all four, and the sweep went from
10 of 12 to 12 of 12.

**4 · Prose.** The docs claimed every measure in the block was proved
*summable* over the dropped dimensions; `min` and `max` are re-aggregable and
never summed, which is why the proof asks about the aggregation instead of
assuming one. The function's docstring said the block lists "the ones the
rollup carries" where it lists what the rollup *stores* — the same list less
the computed ones, as its own last paragraph explains.

**Verification.** `just quality -s` 9/9. `just test` 4372 passed, 5 skipped.
`just coverage` 99.1% global against a floor of 98, guardrails 100%, steps
92.5%. `just build-docs` clean. Patch coverage 100% (26/26 added lines) on the
full profile, the new refusal branch included. Sabotage: twelve mutations
across `emit/cube/__init__.py` and `emit/lower/rollups.py` — twelve killed,
both files checksum-restored.

**Residue — checked and deliberately unchanged.** MetricFlow emits nothing for
a rollup, which is correct: it has no pre-aggregation surface and §5.3 asks it
for nothing. The double materialization is real and intended — Cube builds its
own copy from the parent cube's table and never reads the gold rollup model —
and it is documented rather than refused, because §5.3 asks for both targets.
And the thing this phase still cannot test is the one §9 named: whether Cube's
matching would use a pre-aggregation R013 did not authorize. That is now
RFC 0043 row 8, which is the whole point of transferring it.

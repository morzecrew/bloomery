## D-019 — `Direction.BOTH` is not declared in P1, because D4 says "the member"

```divergence
decision: RFC 0031 D4
grade: OPEN
class: spec-gap
at: 2026-08-26T14:17:42Z
attempt: 1
claim: §5.1's code block declares `BOTH = "both"` while D4 says "Deferring the *member* rather than guessing its shape is the point" — the snippet and the decision table disagree about whether P1's public enum has three members or two
evidence: rfcs/0031-lineage.md:191
action: decided
proposal: OPEN — D4 stands; §5.1's enum block is corrected to two members, and the `BOTH` line returns with P2 in whatever shape D4 settles on
```

- **Touches:** RFC 0031 D4 (`OPEN`), §5.1's `Direction` block
- **RFC said:** two things. §5.1 declares `BOTH = "both"  # P2 — its return shape is D4,
  still open`; D4 says P1 "ships `UPSTREAM` and `DOWNSTREAM` only" and that "deferring the
  **member** rather than guessing its shape is the point".
- **Built:** `Direction` with `UPSTREAM` and `DOWNSTREAM`. No `BOTH`.
- **Because:** the decision table is the contract and the snippet is illustration — and
  D4's own argument decides it either way. A declared `BOTH` is a member of a public
  `StrEnum` the moment D2 binds `Direction` to SemVer, so a caller may name
  `Direction.BOTH` in P1 and get whatever `lineage()` does with an unhandled member.
  Deleting it in P2 to change its shape would then be the breaking change D4 exists to
  avoid, and keeping it means P1 ships a name with no behaviour. Two members is the only
  reading under which D4's sentence is true.
- **Consequence:** `Direction` grows a member in P2, which is additive and needs no
  migration. §5.1's block is wrong as written; the corrected claim lives here and in the
  enum's docstring.
- **How it got there:** the round-3 review of #45 moved `BOTH` to P2 and rewrote D4, §6,
  §10 and §12 — and left the §5.1 snippet carrying a comment about the change instead of
  the change. A fix that updates a decision and annotates its illustration rather than
  editing it is the same shape as the stale `Edge.label` comment this RFC is partly about.

## D-020 — `lineage` itself joins the public surface, which D2 does not count

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-26T14:17:42Z
attempt: 1
claim: D2 enumerates four *types* and §2 and §12 both say "four names", but the function `lineage()` is named nowhere — a traversal that cannot be imported is not the capability the RFC argues for, and RFC 0018 D1's signature closure exists precisely to stop a documented call needing a deep import
evidence: rfcs/0031-lineage.md:8
action: decided
proposal: LOCKED — D2 covers five names, not four: `Graph`, `Edge`, `Lineage`, `Direction` and the function `lineage`. The function is exported from `bloomery.__all__` beside `resolve`, and from `bloomery.resolve.__all__`
```

- **Touches:** RFC 0031 D2 (`LOCKED`) — its count, not its decision
- **RFC said:** "four new names on `bloomery.__all__` (`Graph`, `Edge`, `Lineage`,
  `Direction`)" in §2, "the four `__all__` additions" in §12, and D2 names the same four.
- **Built:** those four **and** `lineage`, at both levels.
- **Because:** D2 says the four types *join* `__all__`; it does not say nothing else may,
  so this is a gap rather than a contradiction — which is why it is `unlisted` and not a
  departure from a locked row. The gap is load-bearing: `resolve()` is exported at the
  root (`src/bloomery/__init__.py:162`), `stability.md` binds both the root and each
  subpackage's `__all__`, and a `lineage()` reachable only by deep import is the exact
  defect RFC 0018 D1 was written to close. §2's own scope sentence calls the module the
  thing this RFC adds, and a module is not a surface.
- **Consequence:** five names bind under SemVer from this task, not four. The changelog
  says five.

## D-021 — the closed vocabulary lives in code, and the builder guard reads the AST

```divergence
decision: unlisted
grade: UNLISTED
class: spec-gap
at: 2026-08-26T14:17:42Z
attempt: 1
claim: §6 mandates "a separate test asserts the table's own rows against the builders" and does not say how; the only mechanism that catches a row added to a builder with no fixture reaching it is reading the builders statically, and a hand-maintained constant compared against itself proves nothing
evidence: rfcs/0031-lineage.md:409
action: decided
proposal: ASSUMED — the closed `(label, src kind, dst kind)` set is a constant beside the builders it describes, §5.3's table documents it, and two tests guard it: the corpus is a subset of the constant, and an AST walk over every `Edge(...)` construction in `graph.py` is a subset of it too
```

- **Touches:** RFC 0031 §6 and D6 (`ASSUMED`); no row says where the vocabulary lives
- **RFC said:** that the guard is keyed on the triple, that the corpus is a *subset* of
  §5.3's table, and that "a separate test asserts the table's own rows against the
  builders". It does not say what the test reads.
- **Built:** the set as a module constant in `resolve/graph.py`, and an AST-based guard
  over that module's own `Edge(...)` call sites.
- **Because:** the table cannot be the source. §5.3 is markdown in a document that is
  retired when RFC 0031 completes, so a test parsing it dies at retirement — and the
  corpus cannot be the source either, which is the finding D6 already records. A constant
  beside the builders survives retirement and is the thing both guards compare against.
  The AST walk is what makes the claim in §9 true rather than aspirational: it is the only
  reader that sees a shape no fixture exercises, which is the exact failure mode that cost
  this RFC two table rows.
- **Consequence:** a test now depends on the *shape* of `graph.py`'s edge constructions —
  keyword arguments with a literal `label=` and a node-constructor call. That is a
  coupling to source form, not to behaviour, and it is stated in the test's docstring so
  the next person to refactor `_step_edges` knows why it broke. If the walk proves
  brittle against a construction it cannot read, it fails loudly rather than skipping —
  an unreadable call site is reported, not ignored.
- **Deliberately not applied:** making the constant public. It describes an internal
  invariant of two private builders, and D2's surface is already growing by five names;
  a sixth that no caller needs is surface for its own sake.

## D-022 — the self-edge needs a relation that is *not* a declared entity

Appended while building §6's off-corpus projects. The first attempt at a
self-referencing binding produced no self-edge and no `CircularDerivation`,
which is how the branch's real condition turned up.

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-08-26T14:31:43Z
attempt: 1
claim: §5.3's row calls the self-edge "a self-referencing binding", but `_step_edges` reaches that branch only when the bound relation names no declared entity — a step whose output *is* an entity falls through to the entity branch, draws one edge per field, and produces an acyclic graph
evidence: src/bloomery/resolve/graph.py:233
action: decided
proposal: ASSUMED — §5.3's `step → step` row reads "a step reading another step's output — or, where the relation names no declared entity, a self-referencing binding whose self-edge exists for cycle detection to find"
```

- **Touches:** RFC 0031 §5.3's second `step_input` row; no decision row covers it
- **RFC said:** the row's gloss is "a step reading another step's output — or, as a
  self-edge, a self-referencing binding".
- **Found:** the second half holds only under a condition the row does not state.
  `_step_edges` tries `producer_of` first, then `entities.get(relation)`, and the
  self-edge is emitted in the `entity is None` arm. A step wiring
  `inputs: {itself: silver.looped}` / `outputs: {looped: silver.looped}` where `looped`
  **is** a declared entity draws `entity_field → step` edges for each of its fields and
  toposorts cleanly; the same wiring over `silver.scratch`, which is no entity, draws the
  self-edge and raises `CircularDerivation`.
- **Because:** the arm exists to keep a self-reference visible to cycle detection when
  there is no entity to hang input edges off. Where the relation *is* an entity, the
  entity edges already put the step downstream of something, and the step is not
  downstream of itself — so there is no cycle to find and nothing was lost.
- **Why `discovery`:** the branch reads as unconditional until you build a project that
  takes the other arm. Both arms are now covered by
  `tests/unit/test_resolve/test_edge_shapes_offcorpus.py`, including the negative case,
  which is what stops the next reader inferring a cycle that is not there.
- **Consequence:** the shape table is unchanged — both arms are still
  `step_input, STEP → STEP` and `step_input, ENTITY_FIELD → STEP`, which `_EDGE_SHAPES`
  already declares. What changes is the row's prose, and only in RFC 0031, which is not
  retired by this task.

# T-0044 · Stable node identity: plan() and display

Executing RFC 0062 P2 and P3 against branch `feat/node-identity-plan-and-display`.

## Plan

P1 kept the authored `id:` out of the IR, deliberately, so that an unadopted
project compiles byte for byte (D3). P2 and P3 both need the id *downstream* of
the IR, and that is the whole shape of this phase: the id reaches `plan()` as an
argument the caller derives, and reaches `lineage`'s rendering from the
`Project` the command already holds.

One new public function, `node_labels(project, catalog)` — node id to the name a
reader knows it by, for every node that adopted an id — built with the same node
constructors that mint the ids, so the inversion cannot drift from the
construction. `plan()` gains two keyword-only, defaulted parameters taking that
map for each side. `render_lineage` takes it too.

Out: any change to the IR (D3), any similarity heuristic (D1), any re-spelling
of an existing node id (D7), and the `explain` half of §5.4 — see the entry
below.

## Self-audit — 2026-09-11

Scope: the whole branch against `main` — 3 commits plus the audit's own fixes,
18 files, merge base `fc94ab0`. Every pass ran. **Four findings, all fixed**,
and three of them came from the sweeps rather than from re-reading.

1. **A rename onto a name the old version already used silently picked one of
   two nodes.** Relabelling `a` to `b` in the version that deletes `b` leaves
   two nodes called `b` in the relabelled IR, and every pass below keys by
   name — so one wins, and *which* one is an artefact of tuple order. §4 names
   the shape and says not to conflate it with a rename. Recorded as an entry
   above with its measurement; fixed by `_refuse_collisions`, checked after the
   substitution so a legitimate chain still lands in one version, and both are
   pinned.

2. **Two of `_relabel`'s five arms were dead, and the sabotage sweep is what
   said so.** Nothing reads the *old* IR's exposures or its unreachable
   metrics: `_citations` reads the exposures before the relabelling runs, and
   both `_affected_exposures` and `_diff_metrics`'s unreachable lookup read the
   new IR. Disabling either arm changed no answer anywhere. The cause is worth
   naming: the substitution list was drawn from **the IR's fields** rather than
   from what the diff actually reads — which is the "checking my own list
   against my own list" the corpus sweep was written to prevent, and the sweep
   did not catch it because a dead arm produces right answers. Both are gone,
   and the omission is a paragraph in `_relabel` so a pass that ever diffs
   either knows it needs them.

3. **The rendered walk was only half labelled and the test could not tell.**
   Un-labelling the left-hand column of the edge list survived: an upstream
   walk from the adopted node never puts that node in the *source* column, so
   the mutation was invisible for the only walk the test performed. A second
   walk — from the metric that composes it — is what kills it.

4. **The how-to's recipe could not have worked.** It read one catalog for both
   sides, and a metric defined by a `template:` lives in the catalog, so a
   rename moves text there too. Recorded as an entry above; found by executing
   the block rather than by reading it, which is the whole argument for the
   executable-snippet seam.

**Verification.** `just quality -s` 9 of 9; `pyright src` 0 errors;
`just build-docs` clean; 4614 passed / 15 skipped; global coverage 99.14% with
`plan/diff.py`, `resolve/graph.py` and `cli/render.py` all at 100%. Sixteen
hand-written mutants over the rename detection, the relabelling, the collision
guard, the label map and both renderings: **16 killed, 0 survivors** after the
three fixes above — two of which were survivors on the first pass.

**Residue.** Three things I would still distrust:

- **`depends_on` holds canonical-field names as well as metric names**, so a
  canonical field sharing a renamed metric's name would be substituted and
  cited. The ambiguity is the IR's — the same collection feeds
  `_downstream_impact` — and it is stated in `_citations` rather than worked
  around.
- **A step rename cannot be expressed in a spec.** A step node is keyed by its
  `ref`, and a wiring's ref is its `use:` — the manifest it runs — so the
  producer is exercised on hand-built IRs and by no fixture. It is written for
  the kind rather than for the metric because `node_keys` files three kinds,
  and a producer that handled one would be a rule wearing a special case.
- **The label maps are trusted.** Handing `plan()` maps from a different
  project reports renames that did not happen. So does handing `plan()` two
  IRs from different projects, which is the trust the function already places
  in its arguments.

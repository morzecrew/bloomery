## D-157 — the rule's verdict is the decision, and the proof is not kept

```divergence
decision: RFC 0061 D8 — whether R009's proof is retained anywhere or produced on demand
grade: OPEN
class: discovery
at: 2026-09-07T09:05:00Z
attempt: 1
claim: D8 prefers on demand and names the difficulty — a conversion happens once at compile time and nobody asks later, so an on-demand proof has no caller. Retaining one instead would mean growing a proof channel out of the guardrail stage, which the same halt already found has no consumer either (logs/T-0024.md, D-153). Both readings end in a rule that only labels an outcome something else computed, which is RFC 0042 D5's "a rule that converts nothing has no demonstrated purpose" arriving from the other direction
evidence: src/bloomery/semantic/closure.py:718-724
action: decided
proposal: neither. `prove_conversion` is called *at* resolution and its verdict is what accepts or refuses, exactly as the planner reads `prove_rollup` — the `Refutation` carries the obligation the refusal message states, so the rule is load-bearing rather than descriptive, and the `Proof` on the accepting path is discarded rather than stored. Retention stays unbuilt because nothing reads a stored proof; what P1 settles is that R009 decides, not that it is filed
```

## D-158 — two of the three shapes cannot convert, and the third is a key

```divergence
decision: RFC 0061 D7 — whether `currency_in:` extends to recipe and macro mappings
grade: OPEN
class: discovery
at: 2026-09-07T09:20:00Z
attempt: 1
claim: the question dissolves for both, and reappears somewhere the RFC did not look. A `Recipe` is `{id, requires, expr}` — a SQL expression over aliases, with no transform chain — and a `MacroFieldMapping` is a Tier 1 `sql_macro` body, also not a chain. Neither can carry a `convert` step, so neither can hold a conversion whose input would need declaring, and neither call site even reaches `_resolve_conversions`. What does reach it, and what the RFC never mentions, is `KeyField`: it carries `from:` and `transform:` exactly as a simple field mapping does, it is walked for conversions on purpose, and the comment saying so calls a converted key "a strange place to convert" while keeping the walk because a decimal key is legal
evidence: src/bloomery/resolve/build.py:1003-1008
action: decided
proposal: `currency_in:` lands on `SimpleFieldMapping` and on `KeyField`, and on neither of the other two, where it would be a key an author can write and nothing can read. D7 is answered "no" for the two it asks about and "yes" for one it does not, which is worth a row of its own: a conversion in a key column is refused for an undeclared input like any other, or the walk that exists to catch it is decoration
```

## D-159 — two stable-id vocabularies, and the corpus gate knows one

```divergence
decision: RFC 0061 §5.4 — case 004's converted arm re-pins from `RFC 0023 D11` to `R009`
grade: UNLISTED
class: spec-gap
at: 2026-09-07T10:30:00Z
attempt: 2
claim: the re-pin is refused by a gate neither RFC mentions. `test_every_cited_rule_names_a_decision_that_exists` requires every corpus citation to match `RFC NNNN Dn` and resolves it against that document's decision table, live or retired. So RFC 0042 D3's "stable rule ID" is implemented as *an RFC decision id*, while RFC 0039 D8 calls `RULES` "the public contract" with append-only R-ids — two vocabularies for one requirement, and the gate knows the older one. My plan asserted the opposite, that no such gate existed and adding one was out of scope; it exists, and it is the reason the re-pin fails
evidence: `uv run pytest tests/execution/test_semantic_corpus.py -q` -> "004-currency-mix/converted: rule 'R009' is not `RFC NNNN Dn`. A section number is not a stable ID"
action: decided
proposal: the gate accepts either form and checks each against its own register — `RFC NNNN Dn` against the decision table as now, and `R0nn` against `bloomery.ir`-adjacent `RULES`, where membership is verifiable in-process rather than by opening a document that may since have been retired. An R-id is the *stronger* citation on D3's own terms: it is machine-readable, append-only by D8, and never reused. Widening rather than replacing, because every existing case cites the older form and the two registers say different things
```

## Self-audit — 2026-09-07

**Scope.** The whole branch against `03d3ade`: 3 commits, 29 files, +1448/-38 — 4 source
files, 17 test files, 7 docs, 1 config. RFC 0061 re-read first (§5, §6, §9 and the decision
table) before the diff, and RFC 0038 D9/D10, which this branch also wrote.

**What ran.** `just quality -s` 9/9 · `just test` 3963 passed, 6 skipped · `just coverage`
exit 0 · `just build-docs` clean · a 13-mutation sabotage sweep, **13 caught** after the
three tests D-160 describes; 8 caught / 2 survived / 1 stale before them.

**Findings, worst first.**

1. **Two of §6's five tests were unbuilt and unrecorded** — resolved, in D-161. One of them
   should stay unbuilt and the document is where that belongs: the monotonicity property
   §6 asks for is one this phase declares itself an exception to. The per-row name check
   moves to P2. The third gap was real and is now tested — a converting column whose catalog
   declares no currency, verified red against an unconditional comparison.
2. **`Conversion` was the one mutable node in a package of frozen ones** — fixed. Every
   other node in `semantic/` is a frozen slotted dataclass; this was a hand-written class
   with `__slots__` and a docstring justifying the shape by an argument about SQLGlot that
   was really an argument for the *type*, not against being a dataclass. A prover whose
   input can be mutated is a prover whose answer depends on when it is read.

**Checked and clear.**

- **A name in both `key:` and `fields:`** would make `_declared_input_currency`'s `or`
  silently prefer one. It cannot happen: resolution already refuses *"field 'amount_usd' is
  mapped both under key: and fields:"*, checked by probe rather than by reading.
- **Decision-table conformance.** RFC 0061's D1-D6 are implemented as written; D7 and D8,
  both `OPEN`, are answered in D-158 and D-157 with the evidence that decided them. No row
  is departed from, and no `OPEN` row is silently filled.
- **The two registers.** RFC 0039 D8 governs `RULES` as append-only; R009 is appended, never
  repointed, and `SUPERSEDED` is untouched.
- **Determinism.** The prover builds facts in chain order and `Proof` sorts on construction;
  nothing reads a set where order can reach output.

**Residue — what I would still distrust.**

- **`_declared_input_currency` reads `getattr(source, "currency_in", None)`.** Duck-typed
  across three mapping shapes, two of which do not have the attribute and cannot reach this
  code (D-158). If a later change routes a recipe mapping here, it will read as *undeclared*
  and refuse with a message about a key nobody can write on that shape, rather than failing
  as the unhandled case it would be.
- **R009's proof is discarded on the accepting path.** D-157 decided that deliberately and
  P1 is consistent with it, but it means the only evidence an accepted conversion carries is
  that resolution did not refuse — which is the shape this whole document criticises,
  narrowed to a place where nothing yet asks. RFC 0044's `bloomery check` is where it would
  first have a reader.
- **Per-row denomination parses and refuses.** Nothing exercises what a P2 lowering would
  need from the declaration, so the `{column: ...}` shape is pinned only as far as being
  refused for the right reason.

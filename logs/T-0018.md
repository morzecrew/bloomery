## D-096 — a case bloomery does not yet catch has no expressible outcome

```divergence
decision: RFC 0042 §4 — problem.md states "expected bloomery behaviour — refuse, or prove and plan"
grade: UNLISTED
class: spec-gap
at: 2026-09-05T11:20:00Z
attempt: 1
claim: two of the five phase-one cases are not refused today and are not correct either — an average declared `additivity: additive` and a snapshot balance declared the same both compile clean, because `check_additivity` inspects only metrics declared non_additive or semi_additive and nothing verifies that an `additive` claim is true; with only "refuse" and "prove" available, such a case can be written as a fiction or left out, and leaving it out drops exactly the cases RFC 0038 exists to convert
evidence: src/bloomery/guardrails/additivity.py:135
action: decided
proposal: §4 and §5 gain a third outcome, `unguarded` — valid SQL, wrong answer, no refusal today — and §8's design gate is read in both directions: a new rule names the cases it converts from refusal to acceptance *and* the cases it converts from unguarded to refused
```

- **Touches:** §4's outcome vocabulary, §5's artifacts, and D8's design gate.
- **The state is not documentation.** An `unguarded` expectation must cite a rule whose RFC
  is still **live** in `rfcs/`, and every other outcome must cite one that has been retired
  — which is to say, shipped. That makes the distinction mechanically checkable, and gives
  it the property §8 wants: when the owning RFC lands and is retired, the suite goes red
  until someone revisits the case.

  ```
  $ grep -n "def test_unguarded_cases" tests/execution/test_semantic_corpus.py
  102:def test_unguarded_cases_name_a_rule_that_does_not_exist_yet() -> None:
  ```

- Without it the two cases would have had to be written as `refused` — a claim that is
  false today — and the corpus would have been asserting what it wished were true.

## D-101 — `unguarded` was asserted by proxy, and the proxy hid a mis-modelled case

```divergence
decision: RFC 0042 §6 — execute naive.sql and correct.sql, "demonstrating that the corrected semantic plan returns the expected one"
grade: UNLISTED
class: drift
at: 2026-09-05T13:05:00Z
attempt: 2
claim: the first execution ran the two hand-written queries as standalone SQL and never planned anything, so `accepted` and `unguarded` asserted identically and the difference rested on whether the cited RFC was still in rfcs/ — a fact about the repository, not about the case; §6 asks for the planned SQL, and running it shows the two apart directly
evidence: `PYTHONPATH=tests uv run pytest tests/execution/test_semantic_corpus.py -q` -> 17 passed, with every non-refused expectation asserted against the planner's own number
action: decided
proposal: §5's semantic_outcome gains no field — `accepted` means the planner returns the case's `correct` result and `unguarded` means it returns the `naive` one, which is the definition rather than an annotation
```

- **Class `drift`, and it is mine.** §6 asked for the corrected *semantic plan*, and the
  first pass ran hand-written SQL instead. The proxy that filled the gap was then described
  as what made `unguarded` mean something, which was not true when it was written.
- **The proxy would have passed a mis-modelled case.** Case 002 originally declared the
  naive metric over line-grain rows, and the planner returns `32.50` for that — the *right*
  answer, because `AVG(unit_price)` over lines is right. The average-of-averages bug needs
  an average that has already been taken, so the case now carries the per-order rollup the
  upstream system publishes. Nothing but running the planned SQL could have found that:
  the spec compiled, nothing refused it, and the cited RFC was live.
- **A type-2 relation is supplied, not derived** — the second thing running it turned up.
  `materialize` rebuilt `silver.customer_tier` from bronze, losing the versions, and the
  as-of join then failed on a missing `valid_from`. It takes a `supplied` set now, derived
  from the relations a case creates in `silver` itself, because that is where an operator's
  snapshotting puts them.
- **The liveness check is kept, demoted.** It can disagree with the number in the one case
  worth catching: an RFC that lands, retires, and does *not* convert the case leaves the
  planner still returning the naive number — green — while the citation goes red and says
  the rule you named shipped without fixing this.

## Self-audit findings — 2026-09-05

Whole branch against `main`: one commit plus this one, five case directories, the loader,
its guard, the execution module, a corpus README, and RFC 0042's status. Departures the
executor *noticed* are the fenced entries above; these are the ones it did not.

Ranked by severity. All fixed on the branch.

### 1 — a new directory under `tests/fixtures/` joins every corpus-wide sweep

Twelve tests went red on the first full run, none of them the corpus's own. Every
fixture-sweeping test — `test_every_spec_fixture_resolves`, the edge-vocabulary corpus
checks, the unresolved-work sweep — enumerates `tests/fixtures/` and treats each directory
as a spec project. `semantic_corpus/` is not one: its specs live a level down under
`<case>/bloomery/<expectation>/`, and **half of them are meant to be refused**, so a sweep
asserting "every spec fixture resolves" would fail on exactly the cases the corpus exists to
hold.

Named in `NON_SPEC_FIXTURES` beside `dirty`, whose comment already argues for naming rather
than discovering: a spec fixture that stops loading should fail its caller by name instead
of quietly leaving the sweep.

Worth recording as a property of the tree rather than a mistake in the corpus: adding a
directory here is not a local act.

### 2 — a case that pins nothing loaded silently

The loader checks that `semantic_outcome.json` and `bloomery/` name the same expectations.
An **empty** outcome map and an empty `bloomery/` agree perfectly, so a case with no
expectations at all loaded, contributed its two SQL assertions, and said nothing about
bloomery. That is the exact failure the loader's docstring claims to prevent — "a corpus
whose harness silently skips half of it is worse than no corpus" — reached by the one path
the agreement check does not cover.

Reproduced against a planted case before fixing:

```
loaded: [('900-empty', 0)]
```

Now refused, with `test_a_case_that_pins_nothing_is_refused` as its guard.

### 3 — a mistyped RFC number read as "retired", and so as shipped

The check that gives `unguarded` a mechanical meaning asked whether the cited RFC is live in
`rfcs/`. Anything else was treated as retired — which is what a typo looks like. `RFC 9999
D4` on a `refused` case would have passed. Both registers are consulted now: a number must
be live *or* listed in `RETIRED.md` before the live/retired question is asked at all.

A defect in the round's own new check, which is where they concentrate.

### 4 — `Outcome` could grow a fourth member that inherits an assertion written for another

`test_bloomery_does_what_the_case_says` branches on `REFUSED` and lets `ACCEPTED` and
`UNGUARDED` fall through to "nothing refused" — right for both, since what separates them is
asserted separately. A fourth member would fall through too and silently take its
neighbour's meaning. Same shape as a `match` ending in a catch-all, and the same fix as last
branch's: a canary asserting the enum's membership, so the addition fails loudly and points
at the two places that have to decide.

### What I would still distrust

- **`unguarded` is asserted by proxy.** What the suite checks is that the cited rule has not
  shipped, not that the answer is actually wrong — the wrongness is demonstrated by
  `naive.sql` beside it, and nothing mechanically ties the spec to that query. Tying them
  needs a planner, which is RFC 0040.
- **The three-expectation shape is exercised by one case.** 001 is the only case with all of
  representation, rollup and refinement; 002–005 have two each. D4's claim that this carries
  a case across the validator-to-planner evolution is argued, not yet demonstrated — the
  demonstration is RFC 0039 and 0040 landing without the fixture changing.
- **Five of ten cases.** 006–010 are unbuilt, and two of them (009's many-to-many bridge,
  010's timezone boundary) are the ones whose tier answer D7 deferred.

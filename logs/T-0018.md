## D-096 — a case bloomery does not yet catch has no expressible outcome

```divergence
decision: RFC 0042 §4 — problem.md states "expected bloomery behaviour — refuse, or prove and plan"
grade: UNLISTED
class: spec-gap
at: 2026-09-05T11:20:00Z
attempt: 1
claim: two of the five phase-one cases are not refused today and are not correct either — an average declared `additivity: additive` and a snapshot balance declared the same both compile clean, because `check_additivity` inspects only metrics declared non_additive or semi_additive and nothing verifies that an `additive` claim is true; with only "refuse" and "prove" available, such a case can be written as a fiction or left out, and leaving it out drops exactly the cases RFC 0038 exists to convert
evidence: src/bloomery/guardrails/additivity.py:135
action: decided
proposal: §4 and §5 gain a third outcome, `unguarded` — valid SQL, wrong answer, no refusal today — and §8's design gate is read in both directions: a new rule names the cases it converts from refusal to acceptance *and* the cases it converts from unguarded to refused
```

- **Touches:** §4's outcome vocabulary, §5's artifacts, and D8's design gate.
- **The state is not documentation.** An `unguarded` expectation must cite a rule whose RFC
  is still **live** in `rfcs/`, and every other outcome must cite one that has been retired
  — which is to say, shipped. That makes the distinction mechanically checkable, and gives
  it the property §8 wants: when the owning RFC lands and is retired, the suite goes red
  until someone revisits the case.

  ```
  $ grep -n "def test_unguarded_cases" tests/execution/test_semantic_corpus.py
  102:def test_unguarded_cases_name_a_rule_that_does_not_exist_yet() -> None:
  ```

- Without it the two cases would have had to be written as `refused` — a claim that is
  false today — and the corpus would have been asserting what it wished were true.

## D-097 — `bloomery/` holds specs, one per expectation

```divergence
decision: RFC 0042 §9, second unresolved question — whether bloomery/ holds specs or a recorded outcome
grade: UNLISTED
class: discovery
at: 2026-09-05T11:25:00Z
attempt: 1
claim: §5 already gives the outcome a home in expected/, so a recorded outcome in bloomery/ would be the same fact twice and would test nothing; it holds a spec directory per expectation instead, which is what D4's three-expectations-one-fixture requires — a single spec cannot be refused and accepted at once
evidence: tests/support/semantic_corpus.py:162
action: decided
proposal: §9's second question closes as "specs, one subdirectory per expectation". The stated cost — a case breaking when unrelated spec syntax changes — is the exposure every fixture in tests/fixtures/ already carries, and it is the exposure that makes them tests
```

## D-099 — no `proof.json` or `refusal.json`

```divergence
decision: RFC 0042 §5 — expected/ holds result.json, semantic_outcome.json, proof.json, refusal.json
grade: UNLISTED
class: spec-gap
at: 2026-09-05T11:35:00Z
attempt: 1
claim: §5's four files assume one outcome per case, and D4 requires several; one refusal.json cannot hold three different outcomes, and splitting it per expectation duplicates what semantic_outcome.json already keys by the same names, so the outcome map carries the error class and the rule id and the other two files are not written
evidence: tests/support/semantic_corpus.py:55
action: decided
proposal: §5 keeps result.json and semantic_outcome.json; proof.json arrives with RFC 0039, when there is a proof value worth serializing, and refusal.json is dropped in favour of the per-expectation entry
```

- What §5 asks for that is *kept* is D3's requirement: a machine-readable outcome against a
  stable rule ID, never prose. Each entry pins an error class and a decision citation, and
  no diagnostic text is asserted anywhere in the corpus.

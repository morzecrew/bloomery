# T-0009 · RFC 0023 §5.3 — the as-of join

Executed on branch `feat/as-of-joins`. RFC 0023's Phase 2 half that unblocks historical
dimensions: the anchor, the validity columns, the predicate, and the narrowing of the
P1 refusal that D1 left in place. §5.4 (currency as a declared relation) is untouched
and stays unscheduled.

**Drift count: 0.**

Where building this disagreed with the design for it, written at the moment it happened.
Nothing here is revised afterwards to agree with what was later settled, and nothing here
has been folded back into the RFC's own text. Rows proposed below are put forward for the
author to accept or refuse; execution does not write them into a decision table itself.

| Class | Test | Meaning |
| --- | --- | --- |

| `spec-gap` | Could have been known; the RFC was silent or at the wrong altitude | The design process missed something |

## D-036 — the anchor is `as_of:` on the flatten entry, naming a base column

```divergence
decision: RFC 0023 D8
grade: OPEN
class: spec-gap
at: 2026-09-01T20:05:00Z
attempt: 1
claim: D8 leaves the anchor's spelling and location to whoever builds P2; §5.3 proposes `as_of:` on the flatten entry and names a mart-level default and a relationship-level declaration as defensible alternatives
evidence: src/bloomery/spec/marts.py:61 — `as_of: str | None` on ViaStep, beside the `via:` it qualifies
action: decided
```

Taken as §5.3 proposes: `as_of:` on the `ViaStep`, naming a **date or timestamp column
of the mart's base entity**.

The location follows from §5.3's own two-hop analysis rather than from taste. Its worked
example has the fact `order_item`, the anchor on the fact, and the foreign key on
`order_` — a dimension reached through another flatten. The anchor is therefore *always*
a base column even in the case the RFC calls harder, because the fact is the base. That
makes "a column of the base" a rule with no exceptions rather than a first
approximation, and it makes the mart-level alternative strictly worse: a mart-level
default would still have to name a base column, while losing the ability to read two
historical dimensions as of two different dates.

The relationship-level alternative was rejected on a different ground: a relationship is
declared once and flattened by many marts, and the date one mart wants to attribute on is
not a property of the relationship.

## D-037 — the interval column names are shared constants, not an `EntityIR` field

```divergence
decision: RFC 0023 D7
grade: ASSUMED
class: discovery
at: 2026-09-01T20:20:00Z
attempt: 1
claim: D7 places the validity-interval column names on EntityIR so the two targets agree on them; measured, the names are the same two strings for every type2 entity and absent for every type1 one, so a per-entity field would be a constant wearing a field and derivable from `scd` alone
evidence: src/bloomery/ir/nodes.py:136-140 — VALID_FROM/VALID_TO as module constants; both emitters configured from them (src/bloomery/emit/dbt/__init__.py:459)
action: departed
```

D7's *purpose* is met exactly: the names are bloomery's, written down once, and both
emitters are configured from them. What moved is where they live — `VALID_FROM` /
`VALID_TO` in `ir/nodes.py`, beside the other generated-column names, rather than as
fields on `EntityIR`.

The reason is what reading the emitters turned up. Neither target was *told* the names
before this change: SQLMesh took its own defaults (`valid_from` / `valid_to`) and dbt took
its own (`dbt_valid_from` / `dbt_valid_to`), each privately, which is exactly the
mechanical fact D7 diagnoses. But the fix that makes them agree is to *configure both
targets*, and a configuration value that is identical for every entity has no per-entity
axis to vary along. `EntityIR.scd` already says whether the columns exist.

What does vary per join, and therefore does earn an IR field, is the **anchor** —
`MartJoinIR.as_of`.

The dbt half of this was not free and is worth recording: dbt's snapshot meta columns are
renameable only through `snapshot_meta_column_names`, which exists in dbt 1.9+. The pinned
floor is `>=1.10.8` (RFC 0008 D22), so the config is available across the whole supported
range and no version gate was needed.

## D-038 — the open interval end is `IS NULL`, not a sentinel literal

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-01T20:35:00Z
attempt: 1
claim: §5.3's illustrative SQL closes the interval with COALESCE(valid_to, TIMESTAMP '9999-12-31'); a sentinel has to be a literal of the interval's own type, which differs between a date anchor and a timestamp one across three dialects
evidence: src/bloomery/emit/lower/marts.py:128-157 — the emitted predicate, `IS NULL` on the open end
proposal: add a decision row fixing the open interval end as `valid_to IS NULL`, half-open against `valid_from`, and mark §5.3's COALESCE spelling illustrative
action: decided
```

Emitted as `valid_to IS NULL OR anchor < valid_to`.

§5.3's SQL is illustrative and no decision graded it, so this is a choice rather than a
departure. The sentinel form needs a literal whose type matches the comparison —
`TIMESTAMP '9999-12-31'` against a `date` anchor is a coercion each dialect resolves its
own way, and the RFC's example happens to show the timestamp case. `IS NULL` needs no
literal, no coercion and no maximum date, and both targets write NULL for the current
version, which is the fact the branch actually reads.

The interval is half-open (`>= valid_from`, `< valid_to`) so a version ending exactly
where the next begins matches one of them rather than both. That is not a choice — it is
what both targets' snapshot machinery produces.

## D-039 — a join miss stays a `LEFT JOIN` miss; `unknown_member` is not reused

```divergence
decision: RFC 0023 D9
grade: ASSUMED
class: discovery
at: 2026-09-01T20:50:00Z
attempt: 1
claim: D9 assumes a fact whose anchor matches no version takes the existing unknown_member disposition; reading RFC 0016's implementation, unknown_member rewrites a single string foreign key inside the silver SELECT before any mart exists, and a mart-side miss is absent right-side columns with no rule object and no disposition to carry
evidence: src/bloomery/quality/predicates.py:718 — unknown_member_case rewrites a fk value from a QualityRuleIR, a surface a mart join has none of
action: departed
```

An anchor that precedes every version yields NULLs across the joined columns, which is
what a `LEFT JOIN` already does for every other unmatched flatten in a mart.

D9 reads as prior art rather than as a mechanism once the two are put side by side.
`unknown_member` is a **silver-layer value rewrite**: it replaces a foreign key with the
reserved `'__unknown__'` member in the entity's own projection, it is keyed off a
`referential` quality rule, and it is guarded to single, string-typed keys. A mart join
miss has no rule, no key to rewrite, and produces absent columns rather than a wrong
value. Reusing the name would have meant inventing the machinery it names, on the mart
side, for a case that already has consistent semantics.

The consequence is stated in the docs rather than left implicit: a fact whose anchor
precedes its dimension's history reports NULL attributes, and that is a `LEFT JOIN`'s
answer, not a silent substitution.

## D-040 — the P1 refusal's two sides stop sharing one fix line

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-01T21:05:00Z
attempt: 1
claim: D1 and D2 shared one `_HISTORICAL_FIX` because there was one shipped answer; the as-of join gives the flatten side a better one and leaves the base side (D2) with the old one, so a shared line would route a base-side author to a clause with nowhere to go. Neither D1 nor D2 grades the fix sentence, and neither refusal moves
evidence: src/bloomery/marts/flatten.py:163-171 — the two fix constants, one per side
proposal: note under D1/D2 that the two refusals route to different fixes once §5.3 exists, and that only the flatten side may name an anchor
action: decided
```

D1 is `LOCKED` and nothing here departs from it: an unanchored flatten of a `type2`
entity is still refused, with the same class and the same source path. What changed is
the sentence after the diagnosis.

The flatten side now reads *"Fix: declare an anchor — as_of: …, or declare the entity
scd: type1"*. The base side keeps the current-view answer, because a `base:` has no join
to qualify and D2's grain lie is untouched by a predicate. A single line naming `as_of:`
would have been actively wrong on one of the two sides — which is the failure mode the
shared constant was originally introduced to prevent, now inverted by the feature.

## D-041 — a refusal elsewhere cited these columns as unmodelled

```divergence
decision: unlisted
grade: UNLISTED
class: discovery
at: 2026-09-01T21:20:00Z
attempt: 1
claim: RFC 0024 D23 refuses scd: type2 plus multi-source merge with a message whose stated reason is that telling a version from a collision "needs validity columns nothing models yet (RFC 0023 §5.3)" — a clause this change makes false while the refusal itself remains correct. D23's decision is untouched; nothing here grades its wording
evidence: src/bloomery/resolve/build.py:1174-1181 — the refusal, with its reason restated to name the audit rather than the absent columns
proposal: amend RFC 0024 D23's prose to state the surviving blocker (the collision audit does not read the interval) rather than the absence that shipped
action: decided
```

The refusal stands; its reason is restated.

D23's *decision* is unaffected — a merged historical entity is still refused — but its
message named an absence that no longer holds. The columns are modelled now. What is
still missing is narrower and is what the message now says: the union's collision audit
does not read the validity interval, so it cannot tell a second version from a second
source's collision. Lifting the refusal is RFC 0024's work, not this change's.

The same stale clause appeared in `merge-sources.md` and in a test docstring; both are
corrected. Recorded here because it is a general hazard of building a thing another
document refused *because* it did not exist: every citation of the absence becomes a
false claim on the day it ships, and none of them fail a test.

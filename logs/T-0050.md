## Self-audit — 2026-09-13

Scope: `main...HEAD`, 3 commits, 211 files, +1894−196 at the start of the sweep (195 of
those files are regenerated goldens). Findings, all fixed on the branch.

**1. Two things §6 asks for were not built.** The RFC names a golden per target carrying
all three annotations, and an e2e `dbt parse` over a project with `+grants` and `meta`.
Neither existed: the annotations were exercised only by unit tests over ad-hoc in-test
projects, so no artifact's *bytes* were pinned and nothing had asked dbt whether it
accepts the emitted `schema.yml`. `ecom_basic` now carries owner and classification and
`minimal` carries grants — on `minimal` because Cube refuses a granted project and
`ecom_basic` has a Cube golden, and because `minimal` is already in the dbt-parse tier.

**2. And `dbt parse` passing would not have been the check §6 wanted.** That module's own
docstring records the overclaim: parse validates the *shape* of a `schema.yml` entry and
accepts entries whose contents mean nothing to it. The `config: grants:` placement was a
guess. Asserted on dbt's manifest instead — `config.grants`, `meta.owner`, and the
column's `meta` — which is the only thing that says the block reached dbt's model config
rather than sitting in the file being ignored.

**3. My own tests were coupled to the corpus being un-annotated.** Six built their inputs
by *adding* annotations to `ecom_basic`, so annotating the fixture turned them into
duplicate-key parse errors. They broke loudly only because YAML refuses a duplicate key;
a fixture gaining an annotation in the other order would have left them quietly comparing
a project with itself. There is now one `unannotated()` helper that strips instead, and
it asserts it removed something.

**4. The stripper hit a word that is not this RFC's.** `owner:` has been a *required* key
on a dbt exposure since RFC 0056, so stripping it made the project unloadable rather than
un-annotated — the second time on this branch that grepping for "owner" found something
older. It is scoped to the three documents this RFC annotates.

**Checked and clean:** a step-produced entity cannot carry these annotations at all (it is
not authored — RFC 0017 D21 refuses mixing a step output with a mapping), so there is no
silent drop there. Every emitted SQL body is byte-identical with the annotations present
and absent, at both SQL targets, which is D1.

**5. A sabotage survived, and it was a lying test name.** Making *every* classified
column `public: false` — `internal` and `public` included — passed
`test_pii_and_secret_leave_cubes_api_surface_and_internal_does_not`. The test used
`ecom_basic`, whose only classification was `pii`, so its closing assertion read
"unclassified columns are served" rather than "internal columns are served", which is a
much weaker claim and not the one the name makes. The fixture now carries an `internal`
column that flattens into the mart, and the mutant dies.

**Sabotage:** 15 mutants over the change surface, 14 killed on the first pass and the
survivor above killed after the fixture gained the case it was missing; 2
behaviour-preserving controls survived both times, so the sweep can report SURVIVED.

**Coverage:** patch 110/110 lines; global 99.17%, guardrails 100%, steps 92.5% — all three
floors met.

**Residue — what I would still distrust.** Phase 3 is not built, so `pii` and `secret` are
metadata that route to Cube and refuse nothing: a spec can mark a column `secret` and
publish it in a mart today. `grants` is verified against dbt's manifest and SQLMesh's
loader, never against a warehouse — §5.3's adapter matrix (pre-existing grants, replace
semantics, Snowflake's `copy_grants`) is documented as the narrower claim rather than
tested, because no adapter here can exercise it.

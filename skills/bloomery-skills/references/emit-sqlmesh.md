# Emit SQLMesh

Compile a project to SQLMesh models and audits and run it: what appears, the fingerprint
header, model kinds and SCD2, audits, and composing across projects. SQLMesh is the
primary target: it expresses everything the IR can say.

## Compile

```console
$ bloomery compile specs/ --target sqlmesh --dialect duckdb --out my_sqlmesh_repo
```

`--out` points at the SQLMesh repository root; the paths already follow its `models/`
and `audits/` layout. Then, on the SQLMesh side:

```bash
sqlmesh plan
sqlmesh run
```

bloomery emits; planning, scheduling and backfills stay with SQLMesh. Deploy the whole
artifact set together, never model by model: marts and the calendar assume their silver
models exist.

From Python, the loaders take YAML strings and `compile_project` returns artifacts
(`path`, `content`, `kind`, `checksum`) without writing anything:

```python
from pathlib import Path

from bloomery import Target, compile_project, load_catalog, load_project

project = load_project({"entity_model.yaml": entity_model, "mapping.yaml": mapping})
catalog = load_catalog(catalog_text)
artifacts = compile_project(project, target=Target.SQLMESH, dialect="duckdb", catalog=catalog)
for artifact in artifacts:
    destination = Path("my_sqlmesh_repo") / artifact.path
    destination.parent.mkdir(parents=True, exist_ok=True)
    destination.write_text(artifact.content)
```

The catalog is passed separately; it is deliberately not part of the project. Pass
`naming=` to override namespaces (`silver`, `gold`, the `mart_` prefix).

## What appears

| Path | What it is |
|---|---|
| `models/silver/<entity>.sql` | one `MODEL (...)` block and `SELECT` per entity |
| `audits/<entity>_<column>_<kind>.sql` | one custom audit per `min`, `max`, `regex`, path-conflict reconcile |
| `models/gold/mart_<name>.sql` | the wide gold table per mart, with joins and date-role buckets |
| `models/gold/dim_date.sql` | a generated calendar, when the catalog declares a `date_dimension` |
| `models/silver/<entity>__reject.sql`, `replay/<entity>.sql` | quarantine and replay, with a quality surface |
| `models/gold/mart_data_quality.sql` | the quality mart |

For this entity:

```yaml spec=entity_model
spec_version: 1
entities:
  payment:
    grain: one row per payment
    key: [payment_id]
    scd: type2
    fields:
      payment_id: {type: string, required: true}
      order_id: {type: string, required: true}
      amount: {type: "decimal(12,2)", assert: {min: 0}}
```

the silver model reads:

```sql
-- Generated by bloomery — do not edit.
-- fingerprint: blm1:6d7538120d74ec7ce9d6561623a53e8ef6e61b82bf40cc01f47210e6f19e57b6
MODEL (
  name silver.payment,
  kind SCD_TYPE_2_BY_COLUMN (unique_key (payment_id), columns *),
  grain (payment_id),
  audits (payment_amount_min)
);

SELECT
  CAST(amount AS DECIMAL(12, 2)) AS amount,
  CAST(order_id AS TEXT) AS order_id,
  CAST(id AS TEXT) AS payment_id
FROM bronze.psp__payments
```

## The fingerprint header

Every artifact opens with a do-not-edit marker and the `blm1:` fingerprint of the whole
compiled project. Artifacts are regeneration-only: edit specs and recompile, never the
SQL.

- **Drift.** Compare the deployed header with the fingerprint of the specs you believe
  are deployed; a mismatch means they have diverged.
- **Change.** Same fingerprint, byte-identical artifacts, on any machine.

```console
$ bloomery fingerprint specs/
```

```python
from bloomery import build_project_ir, project_fingerprint

print(project_fingerprint(build_project_ir(project, catalog=catalog)))
```

## Model kinds and SCD2

| Materialization | SQLMesh kind |
|---|---|
| `full` | `FULL` |
| `incremental_by_key` | `INCREMENTAL_BY_UNIQUE_KEY` |
| `incremental_by_partition` | `INCREMENTAL_BY_TIME_RANGE` over the first partition column |

The first partition column becomes `time_column`, so it must be a date or timestamp; a
non-temporal leading column is refused. With no `materialization:`, an entity with
`partition_by` defaults to `incremental_by_partition`, otherwise `full`.

`scd: type2` uses `SCD_TYPE_2_BY_COLUMN (unique_key (...), columns *)`: change tracking
by comparing all columns, since the specs declare no updated-at marker. Composite keys
work here, unlike on dbt.

## Audits

- `not_null` and `enum` become builtin audits inline in the `MODEL` block:
  `not_null(columns := (...))`, `accepted_values(column := ..., is_in := (...))`.
- `min`, `max`, `regex` and the path-conflict reconcile each become a custom audit file
  selecting violating rows from `@this_model`, named in the `MODEL` block.
- Quality rules: `on_fail: fail` is a blocking audit; `flag` audits carry
  `blocking false`, and nothing at the invocation overrides that.

## Composing across projects

SQLMesh has no cross-project reference, so an imported relation is named directly: a
mart over an imported `order_item` selects `FROM silver.order_item`, and no model is
emitted for it. That makes the naming policy a hard constraint: compile both projects
under the same policy, and deploy the upstream's models first. The compile cannot see a
mismatch, because the upstream IR does not record the policy it was compiled under.

```console
$ bloomery compile platform/ --emit-ir /tmp/platform.json --out build/platform
$ bloomery compile shop/ --target sqlmesh --upstream platform=/tmp/platform.json --out build/shop
```
